## 🎭 Copy Modes

The copy target is global: one instance can “become” only one target at a time, although copying occurs only in the group where the command was issued. `/copy stop` can stop the current copy state from any group.

| Command | Behavior |
| :---: | :--- |
| `/copy` | Reproduce messages unchanged |
| `/copy reverse` | Reverse text and captions by grapheme cluster |
| `/copy nya` | Append “喵~” to text and captions |
| `/icon steal` | Copy only the avatar |
| `/icon reset` | Restore the bot's own default avatar |
| `/copy stop` | Stop the global copy state and restore the avatar |

**How echoes are sent** (the same for `/copy` modes and random echo): text and captions are handled as plain strings, and text with links or @mentions is transformed like any other text. Plain text is sent again, Telegram re-detects links and @usernames, and the original link-preview settings are kept; bold, hidden links, spoilers, custom emoji and other formatting are not kept, so spoiler text appears in the clear. Photos, video, files, stickers and similar media are copied server-side by Telegram, with the caption replaced by the processed text when there is one; nothing is downloaded locally. Paid media cannot be copied, so only the text is sent. Messages with neither text nor a file, such as polls, dice, locations and contacts, are copied as they are. A transformed result over Telegram's text or caption length limit is not sent.

Choose a target by replying to their message or providing `@username`. Put the mode before the target, for example `/copy reverse @username` or `/copy nya @username`; use `/icon steal @username` for the avatar alone. `/copy stop` and `/icon reset` accept no extra arguments.

Target resolution follows these rules:

- **Username lookup depends on the bot having observed the account previously**; rename, username removal, or username reassignment immediately invalidates the old alias. For destructive operations such as `/block … enable` and `/block … disable`, prefer replying to the target or passing the user id directly (those two commands additionally accept a bare id) rather than relying on historical usernames.
- **When an anonymous administrator speaks as the current group, that group identity is the copy target**, so copy modes can obtain the group avatar and reproduce that “skin”; `/block` rejects the current group identity as a member target.
- **`/copy`, `/copy reverse`, `/copy nya`, `/icon steal`, and `/icon reset` share a global five-minute cooldown**. Only `SUPER_ADMIN_USER_ID` itself is exempt; allowlisted identities still observe the cooldown. `/copy stop` does not consume it.

## 🌐 Per-group translation

Translation handles text and captions independently of the global copy target, the five-minute cooldown and avatar operations. An identity with `isCanControllTranslatePermission` must first run `/translate enable` (disabled by default). A valid `g-auth.json` is required. When the translation target is another bot, enable Bot-to-Bot Communication Mode for this bot in @BotFather; otherwise the other bot's ordinary messages never arrive (see [01 Getting Started](01-getting-started.md)).

| Command | Behavior |
| :--- | :--- |
| `/translate ja` | Reply to the target to translate subsequent text into Japanese |
| `/translate cn @username` | Select an observed username and translate into Simplified Chinese |
| `/translate en` | Reply to the target to translate into American English |
| `/translate uk` | Reply to the target to translate into Ukrainian |
| `/translate ru` | Reply to the target to translate into Russian |
| `/translate list` | List languages supported by the regex checks in a JSON code block |
| `/translate stop` | With no reply or target, stop all sessions in this group and retain the switch |
| `/translate stop @username` or `/translate stop 123456789` | Stop one target; replies and negative channel IDs are also supported |
| `/translate disable` | Remove all sessions in this group and disable translation; requires translation-management permission |

Every direction accepts a reply or `@username`, including user and channel identities. Group members can start and stop sessions. Each group supports up to five distinct identities with independent directions, across at most 25 groups. Capacity rejects new sessions without evicting existing ones; stop an identity before changing its direction. Conflicting reply and argument targets are rejected without stopping the group. `/copy stop` does not stop translation. Translation takes precedence for an identity also targeted by copy; other copy targets operate independently.

`/translate list` returns the following content using a Telegram `pre` entity labeled `json`; the group message is deleted after 30 seconds:

```json
{
  "ja": "日语",
  "cn": "简体中文",
  "en": "美式英语",
  "uk": "乌克兰语",
  "ru": "俄语"
}
```

Text and captions are translated as plain strings, including text with links, @mentions or formatting entities. Text matching the target script, or containing only numbers, punctuation and emoji, is sent as the original without an API call. Japanese requires kana; Simplified Chinese excludes traditional characters with simplified variants in Unicode Unihan; English accepts ASCII letters. Ukrainian accepts its alphabet and apostrophes, excluding Russian `ёъыэ`; Russian accepts `Ё/ё` and excludes Ukrainian `єіїґ`. Shared Han words, unaccented Latin phrases and shared Cyrillic phrases can remain ambiguous; regex checks do not identify language semantically.

An API failure sends the original text. Text messages go out as plain strings with the original link-preview settings and without formatting; photos, video, audio and files with a caption are copied by Telegram as they are with the caption replaced by the translation, without any local download; paid media sends the translation only. Pictures, stickers or files without text, and messages such as polls or locations, are not sent, including when the same identity is a copy target. A translation over the text or caption length limit is not sent. American English uses [Google Translation LLM](https://docs.cloud.google.com/translate/docs/languages#translation-llm) with `en-US`. Outputs retain the topic and reject renderable commands; command notices are deleted after 30 seconds.

Sessions are stored as the `translate` array of this group's SQLite `chat_states` row; see [07 Operations](07-operations.md) for the format and cold migration. Stopping one identity cancels only its session. Adding or stopping another identity preserves an in-flight translation for the current target. Disable and chat teardown remove all sessions in the group; asynchronous results recheck their own session object before sending. `/bot_status` shows this group's translation count as `count/5`.

An automatically populated forum-topic creation message is treated as no explicit reply, so command arguments can still select the target. An explicit reply to that creation message follows the same rule. Replies in linked-channel discussion threads remain intact. Identity mutations and member actions that depend on target policy must finish policy prefetch first; failure sends a temporary notice and stops execution.

The `/qa set` question is trimmed raw message text; Telegram `pre` formatting does not add literal fences. Answers preserve code-block fences. Query, removal, and direct answers match the same question text.

These four command families use `/copy`, `/qa`, `/mood`, and `/icon` as their chat menu entries, with their arguments listed in the descriptions. After the admission gates pass, `/qa`, `/mood`, and `/icon` return usage when the subcommand is missing or invalid. `/qa set`, `/mood query`, and `/mood switch` accept no extra arguments. `/qa query` lists all entries when the question is omitted; `/qa remove` requires a question. Queries and removals preserve spaces and line breaks within the question.

> **How to read the permission column**: rows naming an `isCanXxx` key are authorized by that key, and the `SUPER_ADMIN_USER_ID` identity itself always holds **every** permission key — so it can use all of them without an entry in the SQLite allowlist table. Rows naming `SUPER_ADMIN_USER_ID` are the ones that depend on the identity alone and cannot be granted through the allowlist.

### Behavior details

- **`/prompt` and persona status**: in an initialized group, `/prompt config <prompt>` stores the complete multiline body, trimming outer whitespace while preserving internal spaces and newlines. `/prompt remove` clears this group's override and uses the project's `prompt/persona.md`. `isCanConfigAiPrompt` defaults to false; the super administrator can use it directly or delegate through `/permission`. After SQLite confirms persistence, the Worker receives the update for subsequent reply rounds; a round already underway retains its captured persona. `/bot_status` reads the chat cache and reports configured/unset in the selected group style, without disclosing the body. Both configuration receipts are removed after 30 seconds.
- **Group notice style and menus**: custom-persona groups use ordinary command notices, permission help, buttons and automatic notices. Unset or removed personas use `atmosphere` from `config/static/bot.json`: `mesugaki` is the default teasing style and `normal` is ordinary. The AI switch does not affect this choice. A durable `/prompt` change synchronizes the group menu; removing a persona deletes its chat scope and restores the configured Bot menu from `all_group_chats`. Inline fortunes have no target chat context and use the Bot style. Startup clears the default menu scope; private chats show no menu and respond only to the super administrator's `/send` command.
- **`/bot_status` memory**: each command calls `Bun.unsafe.memoryFootprint()` to display the current memory footprint of the whole bot process, including Workers. Linux reports PSS, which apportions shared resident pages between processes. The percentage uses the container memory limit, or total physical memory when unconstrained; unavailable samples display “不可用”.
- **`/bot_status` context capacity**: the sliding hot memory is measured against `VERBATIM_CONTEXT_MAX` (256 messages) and the cold summaries against `MAX_SUMMARY_ROUNDS` (7 rounds); the two ratios are combined with a 7:3 weighting and **only that single percentage is shown** — the raw counts belong to the memory-tiering mechanism, which stays invisible to group members (see [04 Authoritative Invariants](04-invariants.md)). The AI Worker carries both counts on every memory snapshot report (`AI_SNAPSHOT_INTERVAL_MS`, 30 s) and seeds them in full once hydration finishes; the main thread keeps a read-only mirror. A pending summary is not counted as cold memory because its verbatim text is still in the hot window, a missing mirror entry always displays as zero, and the reading therefore lags by at most one report interval.
- **Subcommand-word case**: the subcommand words of `/copy stop|reverse|nya`, `/icon steal|reset`, `/qa set|remove|query`, `/translate <direction>|stop`, `/mood query|switch`, and `/h_image add` are all case-insensitive, matching `/block`, `/white`, `/init`, and `/prompt`. Target arguments and question text after the subcommand word keep their original case.
- **Button payloads**: the number inside the `callback_data` of join verification, `/wed`, and `/qa query` board paging is parsed as strict canonical decimal — no plus sign, leading zero, whitespace, decimal point, or exponent. The bot only ever produces canonical decimal, so any other spelling is externally constructed and is answered on the spot as an expired button.
- **Command entry gates**: group commands uniformly pass through `/init`. An uninitialized group accepts only the super administrator's `/init`, so `/permission` and `/white` must also run in an initialized group. `/send` is the only slash command admitted in private chat.
- **Action commands**: both names render as `first_name last_name` and link to the profile when a public username exists; the target is picked the same way, by replying to their message or by `@username`. Successful action results are retained like `/permission help` and `/permission query`; missing-target, invalid-argument, and `/x` usage hints still self-delete after 30 seconds.
- **Chat Q&A**: the `/qa set` form collects its text from **formatted messages**. Opening the form is gated on `isCanControllQaPermission`; after that the only check is whether the sender **is the identity that opened it** — which is why **channel identities and anonymous admins can set Q&A**: the command side and the delivery side both see the same `sender_chat`, so the two ids match by construction. A delivery is a line starting with `问题:` or `回答:` (half-width and full-width colons both count, `答案:` is a synonym); the value may span newlines, and the two fields normally arrive as two messages, though both in one message is accepted too. A ```` ```json ```` block in the answer is stored **as literal fences** and unwrapped back into a code block when the answer is sent, so the fences themselves count toward the 3840-character limit. Once claimed, the delivery message is deleted and never reaches the AI or echo pipelines, and the form itself is rewritten in place so that its 「已收到的问题」 and 「已收到的回答」 lines carry the current state (when every field in a message is refused for length the session is unchanged, so the form is left alone); when the two fields together would overrun Telegram's 4096-character single-message limit, the **answer inside the echo** is truncated to the remaining budget with an ellipsis while the question is listed verbatim — only the display on this form is clipped, and the full text is still what gets registered. The form is one per chat and expires after fifteen minutes. **Starting over mid-form** has three shapes: re-sending the same field simply overwrites the previous value and the form keeps waiting for the other one; **the same person** running `/qa set` again discards the old form together with its message and starts from both fields empty; **a different person** running `/qa set` while someone else is mid-form is refused outright rather than silently displacing them — the displaced person would only see their form vanish with nothing to trace. Once the form settles, further formatted messages are no longer claimed and flow into the normal message pipeline. Any chat teardown collects an unfinished form. **Registered Q&A rows follow the chat**: `/init disable` and the bot being removed from the group delete every row for that chat, so a later `/init enable` starts from an empty set; an admin demotion deletes none of them, and direct answers resume the moment the rights come back. Removing a single row still requires `/qa remove`.

  A failed form send closes the session. Deliveries that finish after TTL expiry, reopening, or teardown cannot register an answer; messages already entering deletion remain claimed by the form ingress. A form message ID returned after closure is handed back to state-machine cleanup.

- **Q&A board paging**: `/qa query` packs three rows per page; past one page it adds "‹ Prev / page / Next ›" buttons that rewrite the same message in place. The page number lives in no session state — every click repacks from the hot table using the page in `callback_data`, so an old board converges on current facts after a restart, after `/qa remove` changed the rows, even after every row was deleted. Answers on the board are truncated to 256 characters with an ellipsis; **questions never are**, because a question is the argument to `/qa remove` and a truncated one deletes nothing.
- **Direct Q&A answers**: when the chat is `/init enable`d and a message's text matches a registered question **exactly**, the bot answers straight away without involving the AI and regardless of the usual @/reply/random triggers — replies to the bot and @mentions included. A leading `@bot ` is stripped before comparing; the username match is case-insensitive (as Telegram itself is), while the question text still has to match exactly. Semantically close but textually different questions do not take this path; they are left to the `group_qa_query` and `group_qa_answer` query tools inside an AI round, neither of which consumes the round's visible action budget and neither of which exists when the chat has no entries.
- **`/gag` speech restriction**: at most five targets are active globally; one chat may hold several targets, but an identity cannot be duplicated within that chat. Entries are created only in initialized groups where the bot can delete messages. A regular user first gets a public status with no button, followed by a temporary “发言” entry restricted by `ephemeral_message_parameters.receiver_user_id`; a channel target instead gets one public status with the button. An ordinary `@bot` query always enters fortune only. Both buttons prefill only `gag:<target Telegram id>` (positive for a user, negative for a channel). Before the first space, no MD5, digest, random token, group id, or other metadata is allowed. Telegram inline queries do not expose the exact current chat id or a bot-side pre-send interception hook, so such extra fields cannot authenticate the actual input chat; the normal entry uses a current-chat button. A generated result carries `<target profile>#<session chat id>` in a hidden text link. That public URL is verification material, not a secret or authentication token. After the message lands, the bot must jointly verify the linked target and session chat, actual `from.id`/`sender_chat.id`, and actual `message.chat.id`; an identity or chat mismatch is deleted immediately. Channel candidate titles never expose the group title. Every `gag:` query is owned exclusively by the gag domain; invalid, stale, or identity-mismatched input returns an empty result and never falls back to fortune. Start-state messages bypass the ordinary 30-second command deletion. The session replaces speech entries during refresh; targeted `/ungag`, timeout, or chat-runtime teardown stops refresh and cleans up every state message using its own id. Any failed deletion retains bounded ending state and receives finite retries; the same target cannot be gagged again until every state message is actually gone. `/ungag` therefore requires a reply, `@username`, or identity id. Speech rendering samples per grapheme: 75% takes the filler branch and appends 3–6 dots after that grapheme (each gap independently gets an ASCII space with probability 1/3), while the remaining 25% replaces the whole grapheme uniformly with one of six fillers. The same operation may apply to at most two adjacent graphemes, and a third candidate is blocked by the gate, so 75% is the sampling probability rather than the filler share of the final text; short texts also carry minimum-operation tiers (2–3, 4–7, 8–31, and 32–64 graphemes get at least 2, 3, 7, and 15 operations respectively).

  Each session counts group messages independently and refreshes its entry after **7 messages**. Direct target text that gag deletes does not count; valid inline speech and retained media without text do. User-only entries also schedule another send **30 seconds** after activation and after each refresh settles, including when the group is quiet. No timer is scheduled when at most 30 seconds of gag time remain. If the target has not spoken for **45 seconds**, their next message in that chat triggers an immediate resend and restarts the 30-second interval after the refresh settles. Only target speech resets the idle interval; timed and message-count refreshes do not. Before the first message, silence is measured from activation. Same-topic speech below the idle threshold does not reset the resend timer. All three triggers share one refresh task: send the new entry before deleting the old one, without extending the gag deadline. A target speaking in another forum topic moves the entry through the same process. A failed send retains the existing entry until another message threshold or timer retries; an in-flight request has no queued duplicates. The 30 seconds here is a resend interval, separate from ordinary receipt deletion. [Telegram ephemeral messages](https://core.telegram.org/bots/api#ephemeral-messages-and-commands) may still disappear automatically or after a client restart, and delivery to an offline user is not guaranteed; resending does not guarantee permanent visibility of one popup.

- **`/block` blocklist**: the action goes last, the same convention as `/white` — `/block <target> enable` blocklists and `/block <target> disable` lifts it; when replying to the target only the action is written. A missing or unknown action gets a usage hint (deleted after 30 seconds). The two actions require `isCanBlock` and `isCanUnBlock` respectively. Name the target by replying to their message, by `@username`, or by passing a user id directly (a positive integer; the negative ids of groups and channels do not count) - the id form is the most reliable one, since a released username can be re-registered by somebody else while this command is irreversible. Once the id lands in the persistent blocklist, the target is kicked on sight from any join update in any watched group. The moment a group has both an administrator bot and an enabled `/init` — in either order — anyone from the list already sitting there gets swept out too. If every lookup and ban for a user in one chat's sweep is rejected with `PARTICIPANT_ID_INVALID` (how Telegram answers for deleted accounts), that counts once; finding or banning the user in any chat resets the count, and after 5 the account is treated as deleted and removed from the blocklist and the pending-removal queue automatically. `/block disable` transactionally deletes the target from the authoritative SQLite blocklist and lifts the target's ban in every bot-managed group by default; it still performs the cross-chat unban when the target is absent from the dynamic list. `/block disable` accepts one target form `/block` does not: **the negative id of a channel**. Channel vests enter the list as a `sender_chat` (a `/block` on a reply to a channel message, or an ad-detection hit), and since ad detection deletes the original message while a channel without a public username is never in the cache, refusing negative ids would leave such entries permanently unremovable. The reverse is not opened because a mispasted chat id in `/block` bans a whole chat identity, irreversibly.
- **Notices about the bot's own missing rights**: the reason follows the bot's permission snapshot for the chat. When the bot is confirmed not to be an administrator, the notice says so and names the right to grant; when it is an administrator without one right, the notice names only that right; when the snapshot cannot be read, it only says the rights could not be confirmed yet. `/gag` and `/ungag` refuse this way when "delete messages" is missing. After Telegram rejects `/mute` or `/unmute`, the notice names the reason only when the snapshot confirms the bot is not an administrator or lacks "restrict and ban members"; if the snapshot is unavailable or the right is present, it still mentions both possibilities (missing right or an administrator target). When `/block` does not ban in the current chat, it states whether the bot's rights could not be confirmed or the bot is not an administrator.
- **`/batch_kick` slow-wave cleanup**: only the super administrator may use it, and only in an initialized supergroup. Its sole argument is a window such as `30m`, `2h`, or `1d`, capped at 24 hours. It reads the join log, keeps each user's latest join in the window, and kicks those still present with bounded concurrency and no blocklisting. The super administrator, allowlisted identities, and permanent-blocklist members are not treated as ordinary targets; each chunk confirms those identities directly from the database before it starts, so cache eviction caused by other groups during the run does not affect the decision.
- **`/ad_detect` ad detection**: messages are bundled per sender (`chatId:senderId`), and a one-second queue tick keeps handing batches to the model configured in `agent.ad_detect`, so a continuously posting sender is judged roughly every tick plus one classification round trip. The 90-second window bounds only post-hit disposal suppression and the retention of already-consumed context; it is not "how often one sender is judged". a non-protected hit gets the same disposal as `/block` and announces the reason in the triggering chat. Detection only fires while the bot is an administrator there. Once the message ordinals are stripped, a bundle consisting solely of optional ordinary names and links (including `vless://`, `vmess://`, `trojan://`, and `ss://` proxy nodes or subscription links) with no promotional, recruiting, or trading copy in names or body is never judged an ad. The remaining criteria live in [`config/dynamic/ad_samples.json`](../../config_example/dynamic/ad_samples.json). Personal candidates include `first_name` and `last_name` alongside the body, each bounded to 128 UTF-16 code units outside the body budget; a normal body does not exempt promotional names.
- **Join verification and Anti-Raid**: off by default per chat; any identity holding `isCanControllAntiRaidPermission` (the super administrator always does) enables both with `/antiraid enable`. The two pipelines share this one switch because they consume the same join events — splitting the switch would only produce combinations like "verification off, private mode still kicking". While it is off neither pipeline fires a single event: no verification window opens, no reminder is sent, no timeout kick happens, and join rates are no longer counted; windows already open are discarded together with their pending terminal dispositions: the two verification reminders already posted are deleted, because their buttons are dead by then and must not stay in the chat forever, while the join announcement and the member’s own messages are left alone and nobody is kicked; a private mode still in effect hands the invite right back. Ad detection, flood muting, instant blocklist kicks and the join log `/batch_kick` depends on all share the same Worker and are unaffected.
- **Flood muting**: off by default per chat; any identity holding `isCanControllFloodControlPermission` (the super administrator always does) enables it with `/flood_control enable`. 15 messages from one person within one minute in one supergroup gets them muted for 3 minutes, with a one-line notice that self-deletes 30 seconds after successful sending. Telegram lifts the mute on its own; nothing is blocklisted and no message is deleted. It only fires when the bot actually holds the "restrict members" right; owners/administrators, channel identities and anonymous administrators are never counted. The bypass depends on `isCanBypassFloodControl` alone — it defaults to `true` on an allowlist entry, and an identity counts only once it is explicitly `false`; `SUPER_ADMIN_USER_ID` always holds it and is therefore never counted.
- **`/send` relay**: reachability is probed before starting, every message the super administrator sends is relayed to the target group once, and the session ends with a notification if the target becomes unreachable.
  - **Voice relay**: send the JSON below as a whole code block (comments and trailing commas allowed); instead of relaying the message, the bot synthesizes `text` into voice and sends it to the target group as a voice bubble. `tone` is optional and sets how this line is spoken, appended after the fixed base voice style. The text limit is 256 and the tone limit is 64, both measured in UTF-16 code units (a typical emoji uses two). Exceeding a limit returns a format hint without truncating and sending the text.
    ```json
    { "type": "tts", "tone": "desired tone", "text": "text to speak" }
    ```
    Messages that are not a whole code block, do not parse as JSON, or whose `type` is not `tts` are relayed as usual; a `tts` request with invalid fields gets a one-line format hint. It requires `agent.tts` in `config/dynamic/agent.json` and fails outright without it. Synthesis is slow, so the request runs in the background and the voice may arrive after text sent right after it; a full executor replies "try again later"; a synthesis or send failure only replies with a one-line notice; when the daily voice quota (`agent.tts.daily_limit`, default 100, shared with AI voice and cron) is used up it replies with a quota notice; the relay session stays open either way. Relay state persists in SQLite `chat_states.status.isProxySendEnabled` across restarts, with at most one target globally; `state.json` holds only global settings. The command is omitted from Telegram's command menu and remains silent in groups or when invoked by any other user.

> [!TIP]
> **CJK action commands need no registration** — any one or two Chinese characters work. Telegram only accepts ASCII command names (Latin letters, digits, underscores), so:
> - These commands never appear in the command menu and get no autocompletion. The menu carries a single placeholder entry `/x` instead — the name `x` is the variable, prompting you to swap it for any one or two Chinese characters. Invoking it returns a usage hint and terminates the chain rather than falling through into the AI/copy pipeline.
> - Forms of three characters or more, such as `/咬人人`, are not action commands and fall through to normal message handling.
> - Precisely because anyone can invent one without registering it, these commands share a global sliding-window limit of 450 responses per 90 seconds, counted across all groups and users; anything over the quota is dropped silently with no notice.

> [!TIP]
> **`/luck_challenge` is not a slash command**: type `@bot_username [query]` in any chat to use Inline Mode. Enable Inline Mode in BotFather, and enabling 100% result feedback through `/setinlinefeedback` is recommended. Inline queries share a global sliding-window limit of 300 responses per 90 seconds.

## 💍 Random Group Partner: `/wed`

After `/init enable`, a member can send `/wed` in the group as a personal account, without arguments. The bot replies with the selected user's avatar and the Chinese caption “caller，你的群友老婆是 member!”, followed by one row of three buttons:

| Button | Behavior |
| :--- | :--- |
| 移除 | Delete the result and release its session |
| 娶老婆! | Confirm the current result; the middle button becomes “已确认♡”, while changing remains available |
| 换一只 | Replace the avatar and caption in the same message, excluding the caller and current target, and restore the confirmation button |

Results are controlled only by their original caller. Clicks from an earlier target cannot affect a newly selected target. Sending `/wed` again draws randomly, deletes the previous result, and replies to the new command; each user has one result per group. Forum results stay in the command's topic. Channel identities, anonymous group administrators, private chats, and channel posts are unsupported.

Each group reuses one independent **`Set<number>` with up to 150,000 members**. Only personal-account speech in initialized groups adds IDs; channel senders, reply targets, forwarded origins, automatic channel forwards, and anonymous group identities do not add candidates. Repeated speech leaves the set unchanged. Full sets retain existing members and pause additions until departures free space. Departure updates remove IDs first, including updates received while the group is disabled. A drawn candidate only has its avatar read by ID, and its name comes from the private-chat profile returned by that avatar read's `getChat`; no `getChatMember` is called, so drawing works even when the bot is not a group administrator. Presence is not judged and the set is never written back, so departed members are cleaned up by departure updates and the daily review instead; the review also removes deleted accounts whose ID Telegram rejects with `PARTICIPANT_ID_INVALID`. The caller is excluded from their own draw. Each draw checks at most eight candidates whose avatar is confirmed unusable; unfinished queries do not count toward that budget and abandon the draw once three of them accumulate. Insufficient candidates or unavailable avatars produce a retry notice.

The avatar path checks the current photo with `getChat`, then matches its `big_file_unique_id` against sizes in the first 100 photos returned by `getUserProfilePhotos`. A match lets both sending and replacement reuse `PhotoSize.file_id`, without downloading or uploading image bytes on the bot host. A missing match or failed photo-list query retains the current ChatPhoto download path. When needed, it uses the public username returned by that `getChat` and reuses `/icon steal`'s public-profile avatar fetcher. Both names in the caption use user-mention entities. Downloads have size limits and cancellation boundaries. The command neither changes the bot's own avatar nor consumes the copy-command cooldown.

Commands and buttons share a main-thread executor with **32 active operations** globally. A slot covers queries, downloads, and completion of photo outbound requests. Up to **512 additional operations** wait in FIFO order; overflow receives a retry notice. Admission releases serial update handling so other updates can proceed; waiting operations do not prefetch images. Photos, text, and button API calls use the shared Telegram outbound queue and category-specific 429 waits, without a `/wed` outbound limiter. Normal shutdown closes admission and drains interactions before closing outbound work. Chat teardown cancels that group's queued operations and active sessions.

Member IDs are stored as numeric arrays in `memory/wed/<chatId>.json`. Only actual additions or deletions mark a group dirty. The shared DiskIO thresholds batch full replacements after 300 changes or 30 seconds from the first change; unchanged sets do not write. Missing files are created automatically, and process startup restores each group's set from JSON. Invalid filenames, IDs, duplicates, or capacity violations refuse startup before networking. Normal shutdown submits remaining changes; abrupt termination may lose changes that have not reached disk.

Every day at 00:00 Tokyo time, the unified Bun cron notifies the main thread to review every stored member set at a shared limit of five IDs per second across all groups. IDs confirmed absent from their corresponding group are removed from the original Set and saved through the batch path above; failed or timed-out queries retain records. The review relies on `getChatMember`, which is only guaranteed when the bot is a group administrator. **In groups where the bot is not an administrator, `/wed` may draw someone who has already left**: the review removes nobody, departed members are cleaned up only by leave service messages, and Telegram may not send those in larger supergroups or when the member list is hidden, so anyone whose message never arrived stays a candidate. Grant the bot administrator rights in groups that need departed members cleaned up promptly. An unfinished round continues without an overlapping round. Shutdown cancels the review and submits remaining changes; process restart waits for the next midnight notification.

Sessions and image bytes remain in memory, with images held only for the current operation and at most 512 sessions per group. Interactions can only be created for groups that already have member records, and the member table is limited to 25 groups and rejects new groups at capacity, so interactions are also limited to 25 groups and are never evicted. Result messages belong to buttons and chat teardown, without fixed 30-second deletion; usage and failure notices use the shared 30-second cleanup. `/init disable` and the bot leaving the group cancel interactions and delete that group's member records and persisted file. Losing administrator rights retains member records. After restart, old buttons ask the caller to send `/wed` again.

## 🔎 Profiles: `/info`

Once the group has run `/init enable`, anyone can look up an identity's public profile with `/info`: reply to their message with `/info`, or send `/info @username`, `/info <user id>`, or `/info <channel or group id>`. Channels, other bots, and the bot itself are valid targets.

- **Contents**: the name (`first_name` and `last_name` joined for users, the title for channels and groups), the username (or "无" when there is none), and the id (tap to copy). The avatar is attached when there is one; otherwise the reply says there is no avatar.
- **Source**: looked up every time — a user's membership in this group, a channel's or group's chat info, and the bot's own profile from startup for itself. When the lookup fails the bot falls back to the identity it remembers, and answers "not found" when it has nothing. The avatar uses the same reader as `/wed` (a user's avatar is reused by file_id, a channel's is downloaded and uploaded, with the t.me page as a fallback); without one the reply carries no picture. Group lookups return text fields without fetching a group avatar.
- **Retention and concurrency**: the reply and every hint are deleted after 30 seconds. The lookup runs in the deferred command executor without holding up update processing, is limited to 30 seconds (on timeout it replies with what it has), and a full executor answers "try again later". `/info` in a private chat gets no reply.

## 🖼️ Random Picture: `/h_image`

**Library configuration**: `random_h_image_dir` in `config/dynamic/assets.json` is a dedicated directory, defaulting to `./h_image` relative to the runtime data root. Collect through `/h_image add`; manual files must use content SHA-256 names. Invalid names, subdirectories, file symlinks and leftover temporary files refuse startup. See [07 Operations](07-operations.md) for paths, permissions and manual maintenance.

Once the group has run `/init enable`, anyone can send `/h_image` (no arguments); any other argument only gets the usage hint. The bot draws one picture uniformly from `random_h_image_dir` in `config/dynamic/assets.json` (by default `h_image/` under the data root, created at startup if missing) and posts it to the group as a reply to the command; in forum groups it lands in the command's topic.

- **Source**: only `jpg`, `jpeg`, `png`, and `webp` files directly inside the directory count; hidden files, subdirectories, and symbolic links do not. The directory is listed afresh on every use, so adding or removing pictures needs no restart. A drawn picture over 10 MB is skipped and another is drawn from the rest, so a few oversized files in the directory do not disturb normal drawing.
- **Blur**: the picture is always sent with Telegram's spoiler (`has_spoiler`), so the chat shows it blurred until someone taps it.
- **Retention**: the posted picture stays; it is not deleted after 30 seconds. The usage hint for extra arguments, the busy hint, and the three failure hints (directory missing, no pictures, no picture within 10 MB) are deleted after 30 seconds.
- It shares the drawing implementation (`packages/infra/randomImage.ts`) with cron tasks' `rand_image`.
- **Concurrency**: the command returns as soon as it is accepted and does not hold up update processing; drawing and uploading run on the main-thread deferred command executor with at most 2 in flight and 16 waiting slots, and a full executor answers "try again later".
- **Rate limit**: `/h_image` and `/h_image add` share one global sliding-window quota of at most 5 accepted calls per second, counted across all groups and users. Calls beyond it are dropped outright: nothing is drawn, nothing is collected, and no message is sent back.

### Adding pictures: `/h_image add`

An identity with `isCanAddHImage` (the super administrator always has it; others get it through `/permission`) replies to a message with a picture and sends `/h_image add`. The bot adds the picture to the random image library, where `/h_image` and cron `rand_image` can draw it.

- **What is collected**: the picture in the replied message (largest size), or a `jpg`, `png`, or `webp` sent as a file. When the replied message belongs to an album, the album's other pictures the bot has seen are collected too (at most 10 per album). Album records live only in memory for the latest 256 albums and are cleared by a restart, after which replying to an album collects only the replied picture.
- **Names and duplicates**: the file is named after the **SHA-256 of the picture's content** plus the extension detected from its header (`.jpg`/`.png`/`.webp`) — for example `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855.jpg`. The name is the content digest, so a repeated name is a repeated picture: the same image lands on the same file name no matter who forwards it or whether Telegram's `file_unique_id` matches, an existing target is reported as already present without writing again, and nothing ever overwrites different content. **Deduplication happens after the download**, because computing that name needs the bytes; the same picture is downloaded once more in exchange for catching re-forwards. Manual images match an existing target only when their content-digest name and saved extension match; collection does not scan or rehash existing files. Pictures in other formats or over 10 MB are not collected.
- **Dimensions**: `sendPhoto` requires width + height to be at most 10000 and the aspect ratio to be at most 20, and the byte cap does not cover this — a 12000×40 strip is only a few tens of kilobytes. Dimensions are read once at collection time, and a picture failing either rule is not collected; collecting it would only mean that a later `/h_image` or cron `rand_image` draw fails silently with no feedback in the group.
- **How it is written**: the picture is downloaded into memory (10 MB cap), written to a dot-prefixed temporary file, and renamed within the same directory, so drawing never sees a half-written file. The service account needs write access to the library directory.
- **Replies**: a missing reply, a replied message without a picture, or a missing permission gets a single hint; when done, one summary line reports how many were added and how many pictures the library held before (counted the same way `/h_image` picks candidates), plus how many were skipped as already present, rejected for their dimensions, or failed when there are any (the dimension line names which rule was broken). All hints are deleted after 30 seconds.
- **Duration**: collection runs in the deferred command executor's background lane, behind interactive requests, and uses at most 120 seconds per command; pictures left after that count as failed. On shutdown the batch in progress is dropped silently, and files already written stay.

## ⏰ Scheduled Posts: `cron.json`

Operators configure `config/dynamic/cron.json`, which hot-reloads and has no in-chat editing command. Tasks can send text, images, files and voice to explicit chats, all enabled groups with send permission, or that set minus excluded groups. They support time zones, one-shot execution and random intervals. Fixed images use a `url` or file `path` array of 1–10 items; 2–10 become an album with a caption only on the first image. Random mode draws one image and accepts a separate directory. `is_blurred` controls spoilers for every image. `send_voice` synthesizes `content` with the optional `tone` and sends it as a voice bubble; it requires `agent.tts` in `config/dynamic/agent.json`: startup refuses when it is missing, and hot reload rejects adding such a task at runtime.

Scheduled messages remain in the chat and go to General in forum groups. One-shot records and random timers are memory-only and restart with the process; missed occurrences are not replayed. See [deployment configuration](../../config_example/README/en.md#cronjson) for fields, examples, target selection and retries.
