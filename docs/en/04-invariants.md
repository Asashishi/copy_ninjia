## Startup and Import Boundaries

### Startup Order and Resource Acquisition
<a id="startup-sequence-and-resource-acquisition"></a>

- **The default time zone is a process startup snapshot**: Optional `time_zone` in `config/static/bot.json` accepts an IANA name and defaults to `Asia/Tokyo`. After trimming, validation checks Intl, Temporal, and Bun cron before external connections and keeps the Temporal-normalized name (case folded; aliases such as `Japan` are not folded); empty values, invalid types, and unknown zones refuse startup. The main thread owns the authoritative snapshot. AI, Anti-Raid, and Disk I/O Workers adopt it through existing `init`, `agentConfig`, and `load` messages, and reconstruction replays it. Each isolate's `cache/perThread/time.ts` holds the zone, a formatter, and one UTC-offset segment: the offset is constant between two adjacent zone-rule transitions, so day indexes, date keys, local time strings, and hours use only comparisons and integer arithmetic inside the segment, and Temporal rebuilds the segment from the offset and the surrounding transitions only on a miss. Date and time strings accept integer timestamps within years 1000–9999 only. Calendar operations reject uninitialized state. There is no hot reload or per-message synchronization. Fortune, logs, ad activity, join logs, AI clocks, and daily maintenance share this zone. Cron tasks inherit it unless they specify a zone. Native Temporal determines the first real instant of each local day without assuming 24-hour days. The Tokyo weather tool is registered only when the startup zone is `Asia/Tokyo`, including the omitted default, and queries Tokyo. Other zones omit it and return an unknown-tool error for calls.
- **The data root is bound to its time zone**: `initializeStorageDatabase` writes the configured zone as the `time-zone` marker in `storage_metadata` (`{"timeZone":"<canonical IANA name>"}`). Disk I/O startup compares it with the configured zone right after the schema-version gate and before any day-based validation, and the installer runs the same comparison before registering the service; a mismatch refuses startup and names `storage_metadata.time-zone`. Runtime code never adds or rewrites the marker. Changing the zone of an existing data root is not supported.

- **Side-Effect-Free Import**: Importing a production module must not start Workers, timers, network requests, or shared-directory writes.
- **Data-Root Preflight and Exclusive Lock**:
  - The main process first creates the runtime data root recursively and preflights write, file-fsync, hard-link, atomic-rename, and directory-fsync capabilities before attempting to acquire `bot.lock`.
  - **Path and Permission Invariants**: The data root and sensitive top-level directories `memory/`, `logs/`, and `database/` must be real physical directories; an `lstat` symbolic-link result fails closed. With an explicit `COPY_NINJIA_DATA_ROOT`, permissions for data root, `memory/`, and `logs/` must be no broader than `0755` (no group or other write bit); `database/` retains `0770` for collaborative group writes to SQLite sidecars, and when owned by a different UID it must belong to an effective group with all `rwx` bits. Existing directories are validated but never chmodded automatically.
  - **Cleanup and Cold-Start Recovery**: Remove orphaned top-level temporary files, reject legacy 14.x `state.json`/`state.json.bak`, and strictly restore `memory/global/state.json` before network access or Worker creation.
  - **Instance Lock Boundary**: Hard links publish the `bot.lock` guard and recovery files atomically, but checking and deleting stale files is not atomic. If two processes start on the same data root while both stale files remain, each may believe it owns recovery. Ensure only one process starts against a data root at a time (see `infra/storage/instanceLock.ts`).
- **Lifecycle Execution Order**:
  1. Strictly validate all deployment inputs that already exist.
  2. Initialize the Disk I/O Worker and completely load/recover persisted state.
  3. Initialize Telegram clients, complete handler mounting, command menu registration, and the `bot.init()` handshake.
  4. Initialize and hydrate the AI Worker and Anti-Raid Worker.
  5. Start the acknowledgement-safe runner to begin pulling and consuming updates.
- **Unified Lifecycle Convergence**: Both initialization failure and normal exit converge on `ApplicationLifecycle`; only resources that were successfully acquired may be cleaned up, released, or flushed.

### Optional Credentials and Strict Configuration Preflight

- Configuration parsers perform no I/O. Before creating Workers or external connections, the main thread strictly validates every existing deployment input through `validateExistingDeploymentInputs`; disabling a feature never exempts malformed configuration. A truly absent optional file does not prevent startup. `packages/config/readiness.ts` and feature availability boundaries refuse the corresponding capability. The main thread holds the authoritative configuration snapshots: `assets.json`, `ad_samples.json`, `agent.json`, `mood.json`, `stickers.json`, and `cron.json` have their content replaced at runtime under the "`config/dynamic/` hot reload" rules below, while every other deployment input requires a restart after a change.

  Consumers read their own capabilities from `config/dynamic/agent.json`: ad detection uses `agent.ad_detect`, while AI chat uses `text`, `summary`, `media`, and optional tools. Startup validates every capability present in the file; feature readiness independently checks its own requirements.

  Disk I/O recovery receives a nullable sticker whitelist through `stickerPacksForRecovery()`: absence sends `null`, strictly reads every existing catalog, and performs no whitelist-based deletion. An explicit empty array still reconciles against an empty whitelist. Present but invalid or unreadable configuration aborts startup.

- Allowlist, blocklist, temporary-ad-bypass activity, and pending-removal state share `database/storage.sqlite` as their authoritative source; runtime code no longer reads or writes policy JSON. On startup, the Disk I/O Worker validates SQLite integrity, JSONB storage class, migration lineage, the schema version and data-root time-zone marker (`storage_metadata` holds exactly the `schema-version` and `time-zone` rows), every strict row codec, disjointness between the blocklist and both allowlists, and outbox references. Any failure aborts instead of serving partial state. Production startup never creates or migrates a missing database; offline migration scripts own structural changes.

  **Synchronous authorization reads only three bounded main-thread LRUs**: permanent allowlist, blocklist, and temporary-ad-bypass activity each hold at most 8,192 positive or negative entries, where `null` is an explicit negative cache. Disk I/O startup returns permanent-policy counts rather than copying all three tables. An update preflight batches the identities the update will need, with at most 4,096 primary keys per cross-thread cold read; commands and join checks then read synchronously without request/reply at each decision. Prefetch refreshes the recency of identities that are already cached, so the cold keys written by the same prefetch cannot evict them. A failed cold read leaves ordinary paths fail-closed, while destructive bulk paths must cancel rather than treat unknown identities as unprotected. `/batch_kick` does not rely on cache residency: before each chunk it cold-reads the permanent-policy verdicts for every identity in the chunk and keeps them locally, deciding on "local verdict ∪ live cache", so LRU eviction caused by other traffic during the run cannot turn an allowlisted identity into an ordinary target.

  Single-target identity commands must also confirm policy prefetch success; a failed cold read rejects execution instead of applying default permissions to a mutation. `/permission query` prefetches both self and explicit targets; failure sends only a query-failure notice subject to the 30-second cleanup, with no default-permission board. Temporary ad bypass activity is counted only when the blocklist LRU explicitly contains `null`; listed and uncached identities do not accumulate activity.

  **The temporary ad bypass counts ordinary ad-detection messages across chats by visible sender identity.** A real user or channel persona is counted only when ad configuration is ready and the current chat explicitly enables detection; service messages, automatic forwards, the bot itself, the current chat's anonymous-admin persona, and permanent allowlist members are excluded. The eighth message in one configured local calendar day qualifies that day once, and the first qualified day immediately grants `TEMPORARY_AD_BYPASS_PERMISSIONS`, which contains ad bypass only. Seven consecutive qualified days promote the identity into the permanent allowlist with the same ad-only permission set. Accumulation is recalculated by configured local calendar day, never by a rolling 24-hour window. A row that qualified on the day that just ended survives into the new day so temporary ad bypass and the consecutive-day count continue; the first eligible message of the new day resets `send_count` to 1 and clears that day's `qualified_at`, and the eighth message qualifies the day again. Once the day qualifies, later messages on the same day no longer rewrite the row: `send_count` and `counted_at` freeze on the qualifying message, so `counted_at` equals `qualified_at`; day rollover, the retention decision, strict decoding, and midnight cleanup all read exactly the same facts. If the new day does not qualify, the next configured local midnight deletes the complete row and its message accumulation; older rows are deleted as well, while current-day rows remain. Midnight maintenance first commits pending final values in the shared SQLite transaction and refuses cleanup if a failed transaction leaves temporary-ad-bypass writes pending. An old-day write arriving after cleanup is normalized against the same day boundary; an expired value is acknowledged as a tombstone at its original revision and cannot reinsert the old row. Main-thread LRU reads and Worker recovery apply the same boundary, so an expired cache entry grants no bypass and an expired unacknowledged value replays as a tombstone. An applicable true ad verdict, blocklisting, or permanent promotion explicitly clears the complete temporary accumulator; a stale verdict arriving after the grant cannot revoke it. A wall-clock rollback to before `counted_at` rebuilds the counting timeline from the current message while retaining an already granted temporary membership instead of trusting future counts; for a row that already qualified today `counted_at` is `qualified_at`, so a rollback landing after that instant continues the same configured local day; the membership is retained in both cases.

  **Writes use capacity admission, write-through, and exact revision ACKs.** Identity writes check pending-key, byte, and transport budgets before publishing the final LRU value, registering its revision, and posting to Disk I/O. Each main-thread policy table updates its byte total by replacement delta; only an exact ACK releases that final value's budget, while stale ACKs leave newer revisions intact. Each main-thread domain allows at most 8,192 unacknowledged keys and 32 MiB of estimated payload; each of the six Worker SQLite tables reserves against the same limits (`storagePendingBudgets` in `cache/workers/diskIO/storageDatabase.ts`), so writes the main thread has admitted always fit when a rebuilt Worker replays them, and a successful transaction clears every domain's budget. Permanent-policy, temporary-ad-bypass, and outbox writes trigger a synchronous transaction at 128 changes, chat state at the managed-chat limit, QA at `CHAT_QA_WRITE_BATCH_MAX_ENTRIES` (32) changes, or any first change after 30 seconds. A successful transaction clears pending values before exact ACKs. Failure retains all pending values, retries after 30 and 60 seconds, and signals fatal after three consecutive failures to stop new business. Explicit shutdown flush may retry again. Late reads cannot overwrite unacknowledged final values; recovery replays by revision. Critical `/white`, `/permission`, and `/block` receipts wait for domain durability; commands report rejection, timeout, and missing ACK locally. Domain barriers (`flushDiskIODomain` / `flushDiskIODomainOutcome`) use the domain name as the flush scope: the Worker flushes only that domain and leaves other domains' batching windows untouched. The six SQLite tables and the AI context share one transaction, so a barrier on any SQLite domain (including `aiMemory`) commits the pending values of every table. Anti-Raid durable delivery (`postAntiRaidDurably`) passes a domain barrier only for the mirrors that changed in this round: a pending-verification mirror change flushes `verification`, a private-mode record change flushes `chatState`, and no flush is issued when neither changed; the shutdown drain (`drainAntiRaid`) still uses the unified flush.

  **The super administrator's permissions come from the identity itself, not a SQLite row.** `getEffectiveWhitelistPermissions` in `packages/infra/identityPolicy/whitelist.ts` returns the all-true `SUPER_ADMIN_WHITELIST_PERMISSIONS` for `SUPER_ADMIN_USER_ID`. Other identities read the permanent allowlist first and receive `TEMPORARY_AD_BYPASS_PERMISSIONS` only from a temporary membership still inside the local-day retention boundary. The super-administrator override is read-only and never persisted, so changing the configured identity cannot leave an old all-true row behind. `/white` and `/permission` both reject the current chat's own identity. `isCanWhiteOther` may delegate `/white enable`, but only to add another identity with default permissions; membership removal and permission mutations remain super-administrator-only.

  `/permission query` and `/permission help` are read-only. `query` may inspect self, a replied target, or an explicit target and returns a complete default-filled view without creating a row. Both render JSON that remains permanent: it is a permission board meant to be checked key by key, and the 30-second cleanup would take it away before it can be read. Target-resolution failures, mutation refusals, and usage hints still use the shared 30-second cleanup.
- **Process-wide Telegram identity comes strictly from `config/static/bot.json`**: `bot_token` and `super_admin_user_id` are mandatory before network access, and missing, unknown, or invalid fields abort startup. Every AI key belongs to a capability in `config/dynamic/agent.json`, together with that capability's provider, endpoint, and model. There is no credential default, cross-capability fallback, or runtime override. `base_url` accepts `https` only, plain `http` is limited to `localhost`/`127.0.0.1`/`::1`, and neither userinfo nor a `#` fragment is allowed — that field sits right beside the same capability's api_key. A google-provider capability may also declare `headers` (1 to `AGENT_HEADERS_MAX_ENTRIES` (8) request headers: each name is an HTTP token, unique case-insensitively, and not `x-goog-api-key`; each value, after trimming leading and trailing whitespace, is non-empty printable ASCII), passed verbatim to `GoogleGenAI`'s `httpOptions.headers` so that both the generateContent and Interactions request paths carry them; an openai- or anthropic-provider capability with this field is rejected. `provider` accepts only `google`, `openai` and `anthropic`; `image` and `tts` have implementations only for the first two, and config parsing rejects anthropic for them. Provider credentials go only through api_key; third-party gateway authentication goes through headers.

  **Only the main thread reads the AI configuration from disk.** The main thread parses `agent.json` at the startup gate and re-parses runtime edits strictly through `config/dynamic/` hot reload; the AI chat Worker receives the snapshot currently in effect on the main thread through `init`/`configReload`, and the Anti-Raid Worker through `agentConfig`. Both Workers only read their thread-local holder — no Worker path touches the disk — and a respawn replays the main thread's current snapshot. When `ad_detect` is unconfigured the snapshot is an explicit `null`; the classifier fails closed instead of reusing a previous instance's value.

  AI chat requires `text`, `summary`, and `media`. Missing `image` or `tts` removes only that tool, while missing `ad_detect` disables only ad detection. `tts` has two more main-thread consumers: `/send` relay TTS requests fail outright when `tts` is absent; when `cron.json` uses `send_voice`, `tts` (together with the three chat core capabilities) must exist, and when it uses `send_web_digest` the three chat core capabilities must exist; the startup gate validates `agent.json` first and `cron.json` second, refusing startup when one is missing (`assertCronAgentSupported` in `packages/config/cron.ts`). Startup preflight strictly validates deployment inputs that exist. Missing optional inputs make the corresponding feature unavailable through readiness; persisted chat switches retain their values.

  **Optional capabilities are decided by member presence, never provider name.** Gemini and OpenAI expose voice transcription and Anthropic does not (the Messages API has no audio input; when media selects it, voice falls back to a placeholder and startup logs one diagnostic); but whether the configured media model accepts vision or voice is probed independently on the first real request. Each modality permits one in-flight probe; retries follow the provider SDK's budget, and waiters consume shared waiting capacity without occupying media-runner execution slots. The verdict has four states: `supported`; `unsupported` (the endpoint explicitly rejects that modality); `misconfigured` (404/405 — a wrong model or base_url, which logs one diagnostic pointing at `$.agent.media` when it settles); and `unknown` otherwise. `unsupported` and `misconfigured` prevent new downloads and requests for that modality. A request already in flight in the same configuration generation can still restore `supported` and clear backoff if it succeeds. When hot reload replaces the `media` capability, both modalities enter a new configuration generation and return to `unknown`; late verdicts from the previous generation are discarded. Endpoint failures — timeouts, 408/429/5xx, network errors — only drive a bounded exponential backoff (30s base, capped at 10 minutes); inside the window the call returns a shared result without a download or an executor slot, and one success clears the counter. Ordinary 4xx parameter errors, file-format or encoding errors, corrupted media, download failures, and empty responses concern only that one piece of media: they neither settle the modality nor advance the backoff. Both providers also implement speech synthesis (the OpenAI package dispatches audio/speech or xAI `/tts` by `speech_protocol`); the voice tool is still mounted or omitted by `provider.synthesizeSpeech === undefined`, and a capability that is configured but unimplemented by the selected provider logs one diagnostic when the Worker initializes and again after each agent configuration hot reload.

  A cold probe's download, parameter, or empty-response failure belongs only to that media request; waiters continue probing their own media serially. Concurrent requests for a supported modality capture the capability state object at admission. Requests admitted under one state advance endpoint-failure backoff at most once; late transient failures cannot override success or repeatedly increment the failure count. The main thread fills `replyTelegramBackpressured` once in each media event: `undefined` disables commentary, while a boolean permits commentary and carries that message's Telegram backpressure snapshot. The Worker uses it for random triggering and reply concurrency without another cross-thread query.

  `packages/aiChat/ai/utils/mediaSupportError.ts` classifies media errors centrally. HTTP 400/415/422 yields `unsupported` only when the message explicitly rejects media input, includes evidence about model, endpoint, or input-modality capability, and contains no evidence of an individual file-format, encoding, size, corruption, or similar input error. `Unsupported media type` alone does not close a modality. HTTP 404/405 takes precedence as a configuration error; 408/429/5xx and network failures without an HTTP status are endpoint failures.

  **The OAI-compatible image wire protocol comes from `agent.image.image_protocol` in `config/dynamic/agent.json`; it is never guessed and has no default.** Current values are `openai`, `openai-standard`, and `xai`. A mismatched profile is never retried as another profile. Adding one requires synchronized union types, canvas tables, exhaustive dispatch, and tests.

  **Translation session availability is centralized in `activeTranslateStateIn` in `packages/translate/message.ts`**: a session must exist, the chat’s `isTranslationEnabled` must be true, and `g-auth.json` must be usable. Commands refuse start or enable requests using the same configuration verdict. Missing credentials leave sessions inactive; actual API failures return null from `translateText` and the caller sends nothing.

  The command path names `g-auth.json` and refuses; the automatic path falls back to a plain copy. Neither may pretend a translation happened.

  **Whether AI chat is live right now has exactly one decision point, `packages/aiChat/availability.ts`** (the conjunction of credential presence and the per-chat opt-in), and every new call site must go through it: spell that conjunction out at each call site and sooner or later one of them checks only the per-chat toggle — landing on the startup hydrate path, that is data loss, because that path treats "this chat is off" as grounds for deleting the on-disk memory, and without a credential every chat looks off.

  **So when the credential is missing, `hydrateAiMemory` / `hydrateStickerCatalog` must bail out wholesale and delete nothing**; the snapshots under `memory/` stay untouched until the key comes back.
- **The configuration directory layout is checked before any deployment file is read.** `packages/config/bot.ts` calls `assertDeploymentConfigLayout` in `packages/config/layout.ts` before reading `config/static/bot.json`: a legacy `telegram.json` at the top level of the config root, or any deployment file at the top level of `config/` or in the other subdirectory (including dangling links and same-named directories, never read), fails startup, and `config/dynamic/` must be an existing directory. `config/static/` (`bot.json`, `g-auth.json`) is read only at startup; hot reload watches only `config/dynamic/`. A new deployment file must be assigned its subdirectory and registered in the placement table of `layout.ts`. Before filling in examples, the installer runs the same `assertNoMisplacedConfigFiles` check for misplaced files.
- **The startup gate validates only deployment inputs that already exist; whether one is absent is left to feature readiness.** The startup gate calls `validateExistingDeploymentInputs` in `packages/config/readiness.ts`: `bot.json` is process-level mandatory, and every other optional input (`stickers.json`, `mood.json`, `ad_samples.json`, `agent.json`, `assets.json`, `cron.json`, `g-auth.json`, `prompt/persona.md`, `prompt/voice_tool.md`) **must parse strictly whenever the file is present**, so invalid content is never masked by the matching feature currently being off. A genuinely absent file does not block startup. The same gate adopts `prompt/persona.md` and `prompt/voice_tool.md` together with the process-wide notice style (`ensurePromptFiles`): when `persona.md` is present its text becomes the persona, otherwise the built-in persona applies; when `voice_tool.md` is present its text becomes the `send_voice` instruction, otherwise the snapshot is `null` (the built-in instruction applies). Notices prioritize explicit `atmosphere` in `bot.json`; when omitted, custom personas use ordinary copy and the built-in persona uses teasing copy.

  `packages/config/googleAuth.ts` strictly parses Google credentials and requires an RSA PEM private key for RS256; EC, Ed25519, and RSA-PSS keys are rejected. The main-thread `googleServiceAccountKey` owner publishes the complete readonly snapshot at startup. Translation clients consume it through `credentials` without rereading the file. `closeTranslate` only closes the client; missing credentials remain unavailable for that process, and configuration changes require a restart. See [01 Google credentials](01-getting-started.md#prerequisites) for field rules.

  **SQLite `chat_states` does not participate in startup credential checks**; switches are decoded at persistence recovery. Missing prerequisites are handled by each feature: `packages/aiChat/availability.ts` keeps the AI Worker down, skips memory hydration and refuses enable; `activeTranslateStateIn` leaves translation sessions inactive while commands name `g-auth.json` and refuse start or enable; `adDetectConfigReadiness()` stops ad submissions.

  `deploymentInputExists` treats only ENOENT as "genuinely not configured": a dangling symlink or an inaccessible path counts as "configured but invalid" and still refuses startup. Only the first broken input is reported: several breaking at once is far less likely than "fix the first, restart", and stacking them only obscures the one that actually needs fixing.
- **`config/dynamic/` hot reload replaces the configuration in effect file by file; adding or removing files or sections changes feature availability directly.** The main-thread owner is `packages/app/configReload.ts`: only after AI chat and Anti-Raid have initialized does it watch only the `config/dynamic/` directory (files under `config/static/` need a restart) with `node:fs` `watch`, reconciling once as soon as the watcher exists. Every directory event re-arms a 500 ms debounce timer; when it fires, a latest-value runner executes one round serially, and events arriving while a round is in flight coalesce into at most one follow-up round. The watcher and timer are both unref'd. When the directory itself is renamed, deleted, or replaced (the event filename equals the directory name), after one debounce window the old watcher is closed, the same path is watched again, and one reconcile pass runs immediately; while the directory is missing, re-watching retries with `CONFIG_RELOAD_REWATCH_RETRY_DELAYS_MS` back-off (1, 5, 30 seconds, then every 30 seconds), logging an error only on the first failure. If the watcher cannot start in the first place or fails while running, one error line is logged and the process stops hot-reloading for the rest of its lifetime while the configuration already in effect keeps running. The shutdown maintenance quiesce (`quiesceLifecycleMaintenance`) stops accepting events, and a read still in flight no longer distributes anything.

  The decision lives in `packages/config/reload.ts`, covers `assets.json`, `ad_samples.json`, `agent.json`, `mood.json`, `stickers.json`, and `cron.json`, and uses the same strict parsers as the startup gate; each file takes effect or is rejected as a whole. A file that cannot be read or parsed is rejected entirely and its holder keeps the last validated snapshot. A truly absent file is a valid state: deleting `assets.json` restores built-in asset defaults; deleting any other watched file sets its holder to `null`, a file that appears at runtime is filled from its new content, and the `ad_detect` section and the `text`/`summary`/`media` core of `agent.json` are decided independently. Content deep-equal to the current snapshot is not replaced, and the holder keeps its object identity. Each rejection logs one English error line containing only the file path, field path, and expected shape. Adding or removing optional capabilities such as `image`/`tts` is a plain content replacement. The only cross-file constraint is that `send_voice` in `cron.json` depends on `agent.tts`: `agent.json` and `cron.json` are each decided on their own and cross-checked before any holder is replaced — a new task list that uses `send_voice` while the agent configuration in effect for this round has no `tts` rejects the `cron.json` change; while the task list in effect still uses `send_voice`, an `agent.json` change that removes `tts` is rejected; each file still takes effect or is rejected as a whole.

  After each round applies the holders, `packages/app/configReload.ts` recomputes the AI chat and ad detection readiness from the holders (`aiChatReadinessFromHolders` / `adDetectReadinessFromHolders` in `packages/config/readiness.ts`, using the same criteria as the startup probes) and replaces the verdict object in `cache/main/configReadiness.ts` wholesale when availability or the failing file changes; the per-message gate still reads the holder once and allocates nothing. Everything after the disk read — decision, publication, and distribution — completes synchronously. A switch to unavailable publishes the verdict first, which closes feeding and the matching enable command at once; persisted per-chat switches keep their values, and the AI Worker is not terminated but stays idle while memory keeps persisting. A switch of AI chat to available first restores the Worker through `resumeAiChat` in `packages/aiChat/hydration.ts` — a running Worker receives a full `configReload`, a Worker that never started receives `init`, the speech-synthesis counter, and the memory and sticker-catalog mirrors in startup order — and only then publishes availability; on failure it stays unavailable, logs an error, and retries on the next `config/` event. A change in ad detection availability re-posts `agentConfig`, with a `null` sample list while unavailable. When AI prerequisites are missing at startup, the restored memories and sticker catalogs only enter the main-thread mirror and are neither posted nor deleted; `/clear_context`, `/ai_chat disable`, and chat teardown still remove mirror entries through `requestAiMemoryDelete`, and resumption posts or deletes them according to each chat's switch. `g-auth.json`, `prompt/persona.md` and `prompt/voice_tool.md` are not hot-reloaded; the translation verdict is decided only at startup.

  Distribution uses only existing Worker protocols: the AI chat Worker receives `configReload` (carrying only the changed domains), and the main thread rewrites `lastInitState` to the current snapshot before posting; the Anti-Raid Worker receives `agentConfig`. A rejected post is made up by the Worker respawn replay; when a Worker never started or gave up restarting, only the main-thread holder is updated. On the Worker side the holder is replaced wholesale first and the state derived from the old snapshot is invalidated afterwards, while in-flight requests keep their old facade and client until they settle. AI chat drops its capability facades and the three SDK clients, keeps the quota lanes whose protocol, endpoint, and credential are still referenced by the new snapshot and removes the rest, resets input-modality probing when the `media` capability changes, and logs the "configured but unimplemented" diagnostic again. The single global mood is swapped to the same-named tier of the new snapshot; if that tier was removed, it is redrawn on the next read. After the sticker whitelist is replaced, catalog reconciliation starts for newly added packs (not while shutdown is draining); packs removed from the whitelist no longer appear in the sticker tools, and their catalogs wait for Disk I/O recovery to reconcile them against the whitelist. Anti-Raid drops the three ad-detection SDK clients and clears its system-prompt cache when the sample list is replaced.

  Each thread stores one complete readonly credential snapshot in the `current` holder in `cache/perThread/logger.ts`. On first use or a change in any configuration object's identity, it builds the raw credential list, JSON-escaped fragments, and traversal callback together, then replaces the snapshot. Each emit captures that snapshot; reentrant serialization cannot change the outer snapshot. Current credentials (the Telegram token, each capability's api_key, and each google-provider `headers` value) precede retired credentials, with at most `LOGGER_MAX_REDACTED_SECRETS` (128) entries in total; the earliest-retired entries are dropped when full. A rebuilt Worker fills its own snapshot from its configuration.

### Data Root and Background Tasks

- Source execution resolves the project root from module locations; binary execution uses the deployment working directory. Configuration, assets, and the default data root derive from it. All three Worker entry points are centralized in `packages/consts/paths.ts`; binaries use embedded Workers with the same thread ownership, message protocols, and shutdown order.
- `bot.lock`, `logs/`, `memory/` (including the global state `memory/global/state.json`), and `database/` are all derived from one runtime data root. Production defaults to the project root. Before any production module is imported, the test preload injects a separate temporary root per isolate, making it impossible for real file I/O to touch production caches or the identity database.
- Low-priority group-title maintenance starts only after the command menu, `bot.init()`, Worker hydration, and acknowledgement-safe runner are ready. Its owner calls `getChat` chat by chat through `runBoundedSettledBatch` with concurrency capped at `STATE_MANAGED_CHAT_LIMIT` (chat state covers only managed chats, so each managed chat is queried once), settles each chat independently, and accepts lifecycle quiesce/abort signals.

### Outbound Requests and Message Safety

- grammY receives cancellation signals as its final optional positional argument. `libs/telegramSignal.ts` only adapts the installed SDK's Node type declarations and passes the native Bun signal unchanged, without argument arrays or signal conversion. Project APIs that accept native `AbortSignal` receive it directly.

- **The main thread and Workers share the outbound chain.** `bot.api`, `bot.api.raw`, `ctx.api`, `ctx.api.raw`, and `ctx.reply` all use the same transformers installed by `initTelegramClients`. Every send action in `cron/delivery.ts` enters its chat's lane in the send scheduler like any other send; membership and chat-permission queries in `cron/targets.ts` use the `query` category. `getUpdates` is inbound long polling and bypasses the outbound gate; `app/updateFetcher.ts` owns its backoff and cancellation.
- **Avatar and file downloads share the `download` category.** Telegram file-CDN requests, public avatar pages and images, and the default avatar's URL source all queue and replay through `runTelegramCategorizedRequest`. Waiting, 429 replays, and body reads share each download's timeout budget. The default avatar uses its deployment-configured URL and follows redirects; the CDN and public-profile paths for copying a target avatar disable redirects. Both avatar paths retain bounded reads and JPEG/PNG signature validation before upload; a local default-avatar file makes no download request. Cancellation removes queued jobs and reaches the actual fetch, while the outbound gate releases discarded 429 response bodies.

- **Telegram network capability exists only on the main thread.** The real grammY Bot, Bot API HTTP, and Telegram file-CDN downloads all originate there. AI and Anti-Raid may request only structured, allowlisted capabilities through `supervisedDuplexWorker`; they may not import the grammY runtime, `mainClient.ts`, or the Bot token. A dead Worker generation aborts its requests and settles waiters, while a synchronous response-post failure revokes that generation instead of leaving a Promise suspended. `check:conventions` enforces this against each Worker's runtime import closure; type-only imports are not runtime edges.

  The Worker proxy implements the readonly `TelegramWorkerApi` subset. Only the main thread's complete `TelegramApi` exposes `copyMessage`, `deleteEphemeralMessage`, `editMessageText`, and `unbanChatSenderChat`; these methods are absent from the Worker protocol and dispatch. The shared facade rejects them locally in Workers. Available methods still pass through `requestMainThread`, the main-thread owner allowlist, and the unified outbound gate, including uploads and CDN downloads.

- **Messages a Worker sends through the duplex proxy are registered as self-sent by the main thread at the proxy boundary** (`markWorkerSentMessage` in `infra/telegram/workerRequests.ts`). `infra/selfSentTracker.ts` is per-thread: the Worker's own `markSelfSent` lands in its isolate, while the actual Bot API call happens in `bot.api.raw.*` on the main thread, bypassing the shared action layer's registration. Without this step the main thread cannot tell such a message is its own — a channel echo would be fed to the AI and echo pipelines as fresh content, or claimed by the `/qa set` delivery entry. Registration happens before the response is handed back to the Worker, and the test is **the shape of the result** (a `message_id` plus a numeric `chat.id`) rather than a switch over method names, so any future capability that produces a Message is covered automatically. It reads the result rather than the payload's `chat_id` because the latter may be an `@username` string (the only method returning a bare `MessageId` with no chat, `copyMessage`, is in neither Worker's capability allowlist). Registration precedes the moment the Worker receives the message id, and neither Worker reports back what it sent, so this boundary is the sole registration point for every Worker-sent message.

  **That registration narrows the echo race but does not remove it**: it happens when the send's response lands, while the echo may be returned first by a concurrent long poll. Every entry that both produces output and can receive channel posts or channel auto-forwards must therefore pair the synchronous `isBotOwnMessage` with the bounded `needsBotOwnMessageWait` + `waitForBotOwnMessage` rendezvous (`auto/message/index.ts`, `commands/cjkAction.ts`, `commands/qa/ingress.ts`). The rendezvous only waits while the target chat has an in-flight own send: every outbound request that registers self-sent messages (shared-action sends that pass `selfSentChatId` to `runTelegramAction`, and message-producing requests at the proxy boundary's `executeTelegramWorkerRequest`) calls `beginSelfSentSend` for its chat before it goes out and `endSelfSentSend` once it settles, always in pairs. When the chat has no in-flight send, `waitForBotOwnMessage` returns false immediately (the bot's own post would already be registered by then); when the chat's last in-flight send settles, every still-unmatched waiter settles false as well; `SELF_SENT_RENDEZVOUS_TIMEOUT_MS` is only the upper bound. The update runner is strictly serial, so the whole process is stalled while a wait is pending.
- **The per-chat send scheduler sees only methods that create actual chat messages** (`isTelegramMessageRequest` in `infra/telegram/outboundRetryPolicy.ts`). The outbound gate hands `sendMessage`, media/file/media-group/sticker sends, copy, and forward calls to `infra/telegram/sendScheduler.ts` (runtime state in `cache/main/telegramSend.ts`). Inline answers, chat actions, queries, kicks, restrictions, deletions, reactions, callbacks, edits, and management calls do not enter it. The scheduler proactively paces sends to the published limits in the Telegram FAQ and sends only when all three allowances are met: a per-chat token bucket that refills one token every `TELEGRAM_SEND_CHAT_REFILL_MS` (1 second) with capacity `TELEGRAM_SEND_CHAT_BURST` (3); at most `TELEGRAM_SEND_GROUP_LIMIT` (20) messages per group-like chat (negative ids and `@username`) in any `TELEGRAM_SEND_GROUP_WINDOW_MS` (60 seconds); and at most `TELEGRAM_SEND_GLOBAL_LIMIT` (30) messages across all chats in any `TELEGRAM_SEND_GLOBAL_WINDOW_MS` (1 second). Albums are charged per item and batch copy/forward per message; a single request larger than the bucket capacity is released once the bucket is full, and the remaining debt carries forward. The chat key comes from `payload.chat_id`: numbers as is, `@username` lowercased, numeric strings converted to numbers. Each chat has one FIFO with at most one request in flight, preserving its send order; lanes short only of the global allowance join a global round-robin queue and are released in turn, so a busy group cannot starve other groups. Allowance is charged only when a request is actually sent; cancelling a queued request dequeues it in O(1) without charging. An idle lane is deleted once its minute window, cautious period, and freeze have all ended. Queue limits (excluding the in-flight request) are 128 per group, 256 per private chat, and 8,192 across all chats; beyond them new requests are rejected immediately with `TelegramSendQueueFullError`, so a queue fed faster than Telegram drains it can never grow without bound. These three limits neither count toward nor borrow from the 32,768 429 capacity. Inline Mode has no published send limit here and uses only its adaptive `inline` 429 category.
- **Every Telegram outbound request still catches 429; sends freeze only their own chat, and everything else freezes only its own category.** When a send hits 429, that chat's FIFO stops until `retry_after` ends, then its burst capacity drops to 1 for `TELEGRAM_SEND_CHAT_CAUTIOUS_MS` (60 seconds), a further 429 in that period extends the freeze, and other chats keep sending; the task returns to the head of its chat's queue, is counted as a 429 waiter, and is counted as in flight again when resent. For the `message` category, `activeCount` counts admitted, unsettled sends (including those waiting for allowance) and `pendingCount` counts sends waiting to be resent after a real 429; AI backpressure reads these two counts. `inline`, `download`, `kick`, `query`, `restrict`, `delete`, `chatAction`, `reaction`, `callback`, `edit`, `profile`, `management`, and `other` each own a FIFO and `retry_after`; one category may never freeze another. Normal requests start directly and do not count toward queue capacity. Only 429-retry waiters and arrivals to an already cooled category count toward the shared 32,768 ceiling; overflow is rejected back to the domain owner. Safety work remains durable in verification snapshots or the blocklist outbox and must never treat retry memory as persistence. Recovery probes one request first and grows concurrency only after success; cancellation unlinks an intrusive FIFO node in O(1).

- Telegram 429 requeueing preserves each task's original `admissionSeq`, maintaining FIFO within its category. A repeated 429 must not overtake an earlier task. Ordinary tail insertion and abort unlinking retain their constant-time paths.

  The gate also owns a re-initializable lifecycle generation. Every accepted job combines its caller signal with the owner's `AbortController` and passes that signal to the actual grammY/fetch boundary. Drain atomically closes admission first; on budget expiry it aborts active requests, cancels every 429 timer, rejects pending nodes, and settles drain waiters. Counters must be zero afterward, and late callbacks may neither count nor schedule again. A new generation may initialize only when the old generation has no active jobs, pending jobs, timers, or waiters. An already accepted kick retry may perform its private membership revalidation after quiesce, but ordinary callers are not given that bypass.
- Generic JSON API requests may reach only HTTPS origins explicitly listed in `JSON_API_ALLOWED_ORIGINS`, with redirects disabled. A new caller must explicitly extend that allowlist. Telegram avatar downloads use a separate Telegram-owned asset-domain suffix allowlist while reusing the same HTTPS/no-credentials/label-boundary URL policy. Both the Bot API `file.getUrl()` primary path and the `t.me` page/image fallback must disable redirects and keep reads bounded. They must neither be routed through the JSON allowlist nor regress to accepting arbitrary HTTPS images.
- Rich text in an outbound message has exactly two forms, and a message uses one of them (the Bot API makes `entities` and `parse_mode` mutually exclusive, and the send boundary's `SendMessageFormat` enforces this in the type system):
  - the caller assembles the text segment by segment and supplies `entities` itself (offsets follow Telegram's UTF-16 code unit convention, equivalent to JavaScript's `String#length`; a zero-length entity makes Telegram reject the whole message);
  - the message sets `parse_mode`, and the only mode used anywhere is `MarkdownV2`. Every piece of text placed in the body — display names, model output, configuration values and fixed copy — must be escaped through `libs/telegramMarkdown.ts` for the context it sits in (body text, inside `code`/`pre`, and link URLs each have their own character set, never mixed), and unescaped text must never be concatenated in. One unescaped reserved character makes Telegram reject the whole message; a rejection is an ordinary send failure logged through the unified Telegram error log and is never retried as plain text.

  A message that uses neither is sent as plain text: display names and message content participate as plain text only and must never get a chance to be parsed into formatting or links.
- **The echo command guard must inspect the string that is actually sent, not the pre-transform original.** `applyCopyModeTransform`'s `reverse` flips the whole sentence, so `d1 kcik_hctab/` becomes `/batch_kick 1d` — a guard that only looks at the original lets it through, and the bot itself posts a clickable mass-kick command that a super admin only has to tap. `startsWith("/")` is not enough either: Telegram's `bot_command` entity is not anchored to the start of the text (a `/` preceded by the start of text or whitespace and followed by a command-name character qualifies), so one trailing space in the original moves the command to position two and slips past. On a match the echo is dropped entirely rather than degraded to sending the original.
- **Echo leaves through one outlet** (`sendEchoPayload` in `copy/echo.ts`): text and captions arrive already processed as plain strings; plain text goes through `sendMessage` (no entities, no parse_mode, the original `link_preview_options` kept), paid media sends only the text, and everything else is `copyMessage`, replacing the caption through `caption` when there is text and passing `show_caption_above_media` and the video `start_timestamp` along; files, thumbnails, spoilers and covers are copied server-side, with no local download. Callers check the length limits (`TELEGRAM_MESSAGE_MAX_CHARS` for text, `TELEGRAM_CAPTION_MAX_CHARS` for captions) and drop over-long results. `check:conventions` forbids replacing a caption with `copyMessage` outside `sendEchoPayload`. The original-text guard stays as it is (including a media message's `caption`); the two guards judge two different strings. Translation does not use this outlet: `translate/message.ts` sends only the translation through `sendMessage` and never copies media.

  **There is exactly one such check, and it must cover every exit through which the bot emits text it authored itself** (`containsRenderableCommand` in `libs/renderableCommand.ts`). Beyond the echo pipeline there is a second exit under the same threat model: the AI reply toolset's `send_message` body, its typo variant, and the image caption — that body is influenced by the trigger message, so a member only has to say "repeat this verbatim: /batch_kick 1d" and the model complies. The typo path needs its own check: the replacement character comes from the model, and `/` is neither whitespace nor an emoji, so it clears every `buildCharacterTypo` validation — a body of `nya xbatch_kick` with `x→/` composes a tappable command, while the body-level guard inspected the string **before** the substitution. Guard and guarded value must be the same string; that holds for both pipelines. On the AI side a match is rejected with a retryable `toolError` so the model can rephrase (drop the leading slash) instead of forfeiting the whole round.
- **`/mute`'s `until_date` cap must leave headroom instead of hugging the Bot API boundary.** The Bot API evaluates "more than 366 days from now means banned forever" against **the moment it receives the request**, and command handling, `restrict`-category 429 backoff, and the network round trip all push that difference forward, while rounding up to whole seconds adds up to one more. At the cap all of that headroom spills past 366 days and the restriction is silently promoted to permanent — this process schedules no restoration timer and persists no state, so nothing but a manual `/unmute` ever lifts it, while the reply cheerfully says it will end on its own. `MUTE_MAX_DURATION_MS` is therefore 365 days, which moves the boundary out of reach entirely.

  **The 30-second lower bound is enforced by a dispatch deadline, not by the rounding.** Rounding up only covers sub-second truncation, while `until_date` is an absolute instant computed before the request is queued and a `restrict`-category 429 parks it in its own lane for an unbounded `retry_after`. `muteChatMemberWithOutcome` therefore makes `dispatchTimeoutMs` **required**, composes it with the caller's signal inside the wrapper and passes the result all the way down; once it expires the mute is abandoned. Putting the contract in the type is what keeps a third call site from forgetting it. Each caller supplies its own budget, sized to its own shortest duration: flood control passes `FLOOD_MUTE_DISPATCH_TIMEOUT_MS` (a fixed 3-minute mute, leaving 60 seconds), `/mute` passes `this duration - MUTE_DISPATCH_MIN_REMAINING_MS` (its floor is one minute, so leaving 60 seconds would squeeze that tier's dispatch window to zero — hence 45 seconds). Giving up costs one missed mute, far less than a restriction only a human can lift.
- Non-functional command text in groups goes through `sendCommandMessage` and is deleted 30 seconds after a successful send; private chats are unaffected. Only the user-authorized `/permission help`, the `/permission query` permission board, the `/qa query` Q&A board, and successful CJK action results may pass `preserveInGroup: true` and remain. Action-command target-validation failures and the `/x` usage hint still self-delete. Every new exception must be marked explicitly at both its call site and in tests. `check:conventions` requires this tier to pass `messageThreadId` as well; see the next entry.
- **Placement in forum (topics) groups is decided by what triggered the message.** Omitting `message_thread_id` is the same as posting to General, and attaching a reply is not enough — `allow_sending_without_reply` downgrades the send to a plain message once the replied-to message is gone, and only this parameter still keeps it in the topic.
  - **Messages triggered by a user command or interaction land in the triggering message's topic**: conversational output (echoes, translations, AI replies, the bath-trigger reply, the Q&A direct answer), the `preserveInGroup` exceptions listed above, and state-machine-owned messages that no fixed-delay cleanup owns (the `/qa set` form, gag speak notices) pass it explicitly; the visibility of gag entries also follows Telegram's ephemeral-message rules. When the options of 30-second command receipts and usage hints have no `messageThreadId` key, `sendCommandMessage` and the photo-receipt boundary fill it from the current update's triggering topic (`updateTopicThreadIdFor` in `infra/updateContext.ts`, reused only for the same chat as the triggering message); an explicit `undefined` means General and is not filled from the scope — background work still runs inside the scope of the update that started it, and the topic recorded at submission must take effect unchanged.
  - **The triggering topic travels with the update scope**: `app/updateRunner.ts` records the triggering message's topic for every update (`updateTopicOf` in `libs/forumTopic.ts`: the message, channel post, or the message holding the button; nothing is allocated when it is not in a topic), and deferred commands and wed interactions restore the topic captured at admission when they are dequeued. Receipts sent outside the update scope record the topic when they are submitted: avatar-update receipts, AI rate-limit notices, and gag end receipts.
  - **Proactive bot notices carry no topic**: the flood-mute notice, ad warnings and ad-ban announcements, the lockdown announcement, and `cron.json` scheduled tasks (they land in General in groups with topics).
  - **Join-verification reminders are also proactive bot notices**: the reply-style reminder anchors on the pending member's message and falls into General when that anchor is deleted; the state machine removes it at settlement (bounded by `VERIFICATION_TIMEOUT_MS`, or `VERIFICATION_REMINDER_UNDELIVERED_MAX_MS` in the undelivered case). Carrying the topic would require persisting the topic id in the pending-verification snapshot format and would consume the single available cold-migration edge. The re-evaluation trigger lives in the module header of `packages/libs/forumTopic.ts`.
- **A reply must never report a state change that did not happen.** All six toggles — `/init`, `/ai_chat`, `/ad_detect`, `/flood_control`, `/antiraid`, `/translate` — read the previous value before writing, and running one twice in the same direction must say so rather than reuse the sentence for an actual change; otherwise an administrator cannot tell whether the first attempt took effect. The four outcomes live in `ToggleCommandTexts` (`packages/types/commands.ts`), a structure whose four fields are all required, and `toggleReplyText` performs the selection: a new toggle command that supplies only "on" and "off" does not compile. `/quiet`, `/unquiet`, `/white`, and `/permission` are existing implementations of the same rule.

  The decision looks only at the target state and the previous state, **not at whether persistence or runtime cleanup ran**. Those cleanups are best-effort and only log on failure (`clearAdDetection`, `clearFloodControl`, `invalidateAiChat`, and `teardownChatRuntime` behind `/init disable` — when it fails the master switch is already durably off, so the reply switches to the wording that names the leftovers instead of throwing; throwing would withhold the offset, and on the replay `wasEnabled` is already false, so the admin is told "it was already off"), so "disable it again" is the natural manual retry once the Worker is back: a same-state repeat must still persist and re-run the cleanup, and only the reply states truthfully that nothing changed. `/init` still does not invalidate the cached admin status on a repeated `enable` for an already-enabled chat, because doing so would make `recordBotChatPermissions` see a fresh `undefined -> true` edge and rescan the entire blocklist.

  **`/init disable` also persists before it tears down** (same ordering as `runChatToggleCommand`): `teardownChatRuntime` is made entirely of irreversible durable work (the aiChat owner's memory deletion, the translate owner's session removal, the wed owner's member-set removal, the joinLog owner's join-log removal, the qa owner's Q&A removal), so the reverse order means a failed write leaves "the switch still on disk while this chat's data is already gone". That first write still throws on failure — nothing has been written yet, so the replayed round still reads `wasEnabled` as true and the reply never degrades into the "it was already off" ambiguity above.

  **A second write always follows the teardown.** Both the `isProxySendEnabled` field `teardownChatRuntime` clears synchronously and the whole-row `purgeChatStateExceptLockdown` that runs right after it touch memory only; without that second write, a restart would revive the proxy-send session and the entire switch set for a chat nobody manages any more. When the state falls back to its defaults, that write emits a delete tombstone and the `chat_states` row disappears, which is what frees the slot. An unrestored lockdown is the sole exception: dropping it would wedge that group's invite permission forever. The second write shares the teardown's degradation path, reporting the "not everything was torn down" wording instead of withholding the offset — and on that round the row deletion never ran either, so the feature switches survive for the admin to clear with one more `disable`, exactly as the reply says.

  **`disable` never creates a row for a chat that has none.** Its endpoint is deleting that row, so materializing one first is pointless and would make `assertChatStateCapacity` throw whenever `STATE_MANAGED_CHAT_LIMIT` groups are already managed elsewhere — turning the manual retry above into a non-zero-exit process death. `clearChatStateField` is an explicit no-op for a missing entry, and the following write still emits the delete tombstone.

## Worker and State Ownership

### Thread and State Ownership

- The main thread owns the Telegram runner, Worker supervision handles, and the authoritative in-memory `memory/global/state.json` mirror under `cache/main/storage.ts`. `infra/storage/stateStore.ts` is the business facade that hydrates the mirror, builds snapshots, and exposes domain accessors; `StateStore` in `infra/storage/statePersistence.ts` owns only strict decoding, latest-only atomic writes, bounded failure retries, and exit flush. Exhausting bounded retries is a fatal durability failure: the runner must stop and must not continue acknowledging updates.
- The AI Worker exclusively owns group-chat memory, reply admission, the media-description pipeline, the global mood, and runtime state for sticker-catalog generation.
- The Anti-Raid Worker exclusively owns the verification/lockdown state machines and their timers; the main thread holds only recoverable mirrors.
- The Disk I/O Worker exclusively persists logs, AI memory, the sticker catalog, fortunes, and pending-verification data, serializing access to those shared directories within one Worker thread. `memory/global/` is the explicit exception: the main thread invokes `StateStore` in `statePersistence.ts` through the `stateStore.ts` facade. Business Workers must not write shared directories directly.
- Long-lived Maps, Sets, queues, and timers must have capacity, cleanup, and Worker-reconstruction semantics jointly defined by the corresponding `packages/cache/` module and its business lifecycle owner.
- **A cache's owning thread is declared by its directory and verified against the real module graph.** The first level under `packages/cache/` names the owner: `main/` belongs to the main thread, `workers/aiChat|antiRaid|diskIO/` each belong to one Worker thread, and `perThread/` holds state that every thread instantiates separately and independently (the Telegram-capability holder, Worker duplex waiters, deployment-config singletons, self-sent message tracking, and the update cancellation-context storage). Every cache file starts with `/** owner: <main|perThread|workers/<thread>>。`, matching its directory, which `bun run check:conventions` also verifies.

  Threads exchange messages and never share memory, so **importing thread-owned state from another thread is always wrong**: the other isolate gets a second instance of the same module, writes never reach the owner, nothing shows up statically, and at runtime it only looks like "the cache mysteriously never hits". `bun run check:conventions` walks the runtime import closure from all four thread entry points (`index.ts` and the three `*Worker.ts`; `import type` and `new Worker(new URL(...))` are not edges) and prints the full import chain on a violation.

  The single exemption is `packages/cache/main/diskIO.ts` — `infra/logger.ts` statically depends on `relayLogMessage` from `infra/diskIO.ts` and every thread must be able to log; the Worker-side copy stays at its initial value and is never read or written, as documented in that file's module header.
- **When a Worker-reachable module needs main-thread state, the main thread resolves it and sends only the final field.** For example, the AI Worker's super-admin ID arrives in its `init` message; the Worker may not import `config/bot.ts`. Telegram actions send a minimal allowlisted payload to the main thread rather than mirroring the Bot token, client, or outbound queues. This duplex boundary is only for calls that naturally require a remote result; it must not add a request/reply round trip to every group-message hot path.
- Business Workers and the independent Disk I/O host turn synchronous `postMessage` rejection into explicit failure. Request dispatch clears its waiter and timer immediately; critical business rejection is fatal. Accepted error logs use two ACK hops: Worker to main, then main to Disk I/O. Each hop permits one batch of at most 32 messages in flight and retains its original batch until ACK, replaying it after generation replacement; failure boundaries may produce duplicates. The main hop ACKs only after the batch is flushed. Write failures obey the log-file reopen backoff, which new logs cannot bypass.

  Both hops bound queued plus in-flight messages and JSON payload bytes: each business Worker allows 1,024 messages / 2 MiB, and main to Disk I/O allows 4,096 messages / 8 MiB. Overflow retains only dropped-message and byte counters, then enqueues a summary when capacity permits; Worker errors also reach that thread's stderr. Accepted batches survive synchronous rejection and Worker rebuilding. Process exit or isolate termination can still lose logs that are not durable. Before Disk I/O initialization, logs go only to the journal.

  Concurrent batches must not use `Promise.all` directly. Independent fixed tasks use `Promise.allSettled`, wait for every settlement, and aggregate failures per item. Dynamic input goes through the fixed-worker `runBoundedSettledBatch`, which executes each item once and whose results retain `item/index`; when a lower owner such as the Telegram outbound gate already retries, callers must not execute a side effect a second time. A drain that only waits for tasks already registered by an owner may `allSettled` a snapshot directly, but each task must already own its error handling — settlement is never a sink for swallowed failures.

  Disk I/O runtime recovery is one indivisible handshake: after load succeeds, each domain must replay through the current generation's scoped transport in registration order and await all asynchronous work; only then may the host drain the bounded recovery-window business FIFO and expose writable. Mirror replay is bracketed by `storageFlushHold` open/close marks: inside the bracket the Worker only arms timers for full-batch and timed commits, and closing the mark commits once by threshold, so blocklist writes and outbox snapshots replayed at different domain priorities never split across two transactions. Explicit flushes ignore the mark, while AI-context deletions and first snapshots after a purge only queue inside it and commit immediately when the mark closes. A listener returning `false`, throwing, rejecting, timing out, or having a scoped post rejected terminates the current generation and is fatal.

  A stale listener's late settlement may neither write to nor activate a newer generation. Callers that require processing or durability acknowledgement must treat `false` as failure and must not acknowledge the corresponding Telegram update.

  Draining the recovery FIFO is additionally bracketed by a pair of `recoveryReplay` open/close marks (`RecoveryReplayRequest`). When a live shared-SQLite write message is rejected, the Worker records a per-domain rejection mark, the caller's domain barrier that immediately follows collects the failure receipt, and the update stays unacknowledged for redelivery. A message replayed from the recovery FIFO has no following barrier to ask about it, so a rejection inside the bracket also answers with `recoveryReplayFailed`, on which the main thread takes the unified fatal shutdown path and Telegram redelivers from the last acknowledged point.

- **Main-to-Disk-I/O business transport is always bounded.** Queued and in-flight payloads share a 45,000-message and 64 MiB estimated budget, with 16 additional control slots. At most one batch of 128 messages is in flight; the Worker serial operation queue holds at most eight operations, and its sources are bounded: at most one main-thread business batch and one diagnostic batch in flight, one load and one daily-maintenance cron operation, and the Worker's own per-domain timed flushes, which `workers/diskIO/timedFlush.ts` coalesces into a single operation once due (a source that comes due again before running executes only once). No other module enqueues directly. Batch-consumption ACKs release transport capacity, while domain persistence ACKs establish durability. A missing batch ACK after 30 seconds or capacity rejection signals fatal while preserving the final-flush channel. Worker replacement retains the business FIFO and rejects read waiters. Generation-scoped mirror replay precedes FIFO draining and publication of writable state. Recovery-only revision watermarks and object markers for sticker snapshots and member operations suppress only older writes covered by mirrors, preserving later updates.

- **Worker informational group notices share the main-thread send and cleanup boundary.** AI rate-limit/topic errors, lockdown release, verification welcome/terminal notices, and flood-mute receipts are deleted 30 seconds after successful sending. A `notice` request through `sendTemporaryMessageFromMain` uses the shared group-notice lifetime and forwards an optional `replyToMessageId` to preserve the reply target. The main thread registers deletion in the successful send's `onSent` callback before returning the message ID to the Worker; a lost response, cancellation, or Worker replacement leaves that cleanup responsibility with the main thread. Failed sends create no task. Welcome send/transport errors pass through the shared Telegram action boundary, and subsequent verification effects continue in order. Deletion timers use `unref()` and failures use unified Telegram error logging. Verification buttons and `/qa set` forms remain state-machine-owned; inline luck uses the inline API.

- **Incoming messages from other bots are limited at the main-thread ingress.** After tracking the update ID and before receipt confirmation or business dispatch, `app/registerHandlers.ts` calls `shouldPassBotMessage`. It only counts `message.from.is_bot` when `sender_chat` is absent. Channel identities, non-message updates, and this bot's own ID pass without a record. Other bots are counted by ID across chats: the first 15 messages pass and the 16th onward are silently dropped. Every incoming message, including a blocked one, refreshes that bot's separate 90-minute timeout from its last message. The main-thread Map holds at most 512 bot IDs; at capacity, new IDs are rejected without allocating a timer, while existing IDs retain their counters. Each record has at most one `unref()` timer. A process restart clears the counters; a Worker restart does not.

- **The per-update dispatch shape is load-bearing, not merely a performance trade-off.** grammY registers `command`/`on`/`hears` through `filter → branch → lazy`, and `lazy` awaits a factory, allocates an array, and constructs a Composer on every single update. Every slash command must therefore sit in a child Composer behind one shared `:entities:bot_command` gate rather than being registered flat on `bot`: the gate uses grammY's `matchFilter(":entities:bot_command")`, exactly the first step `Context.has.command()` performs itself, so the matched set, the relative order, and claim-and-terminate stay identical, while messages without a `bot_command` entity skip the whole group in one step. The preamble from update_id tracking to the message fallback (including the three ingress boundaries, the command gate, the CJK action-command gate, and the fallback) is collected in order into one array, registered in a batch with `bot.use(...preamble)`; order, claiming, and the next contract are managed by the grammY SDK. The three ingress boundaries on `message` / `channel_post` and the message fallback are not registered through `bot.on`; they apply the same predicate by hand (`allowed_updates` has no `edited_*`, so `ctx.msg` always equals `message ?? channelPost`). The `hears` for CJK action commands sits in a child Composer behind a "raw text starts with `/`" gate, a strict superset of `CJK_ACTION_COMMAND_PATTERN`, so other messages never enter that `lazy` layer. For the same reason, the three ingress boundaries in front of every group message (Anti-Raid, gag, `/qa set` form delivery) and the bot-admin check they share all return `boolean | Promise<boolean>`: steady state returns synchronously and allocates no promise, and only an on-demand permission probe, an actual message deletion, or a durable post returns a promise — all funnelled through `claimOrContinue` in `app/registerHandlers.ts`.

  **Whether a promise is returned is part of the semantics, not a detail free to optimize away**: the paths that must await a durability barrier (join/leave service messages, verification button callbacks) have to return one, because returning synchronously means Telegram acknowledges the update before the write lands. Conversely, marking an always-false synchronous check `async` makes every group message pay one promise allocation and one microtask turn for nothing. Tests pin both directions: steady state asserts a synchronous return, and the durable paths assert `toBeInstanceOf(Promise)`.

- **Every timer handle owned inside `packages/workers/` must be `unref()`ed.** An isolate stays alive through its message port to the main thread, independently of any timer's ref state; ordered shutdown is delivered by each isolate's own drain/flush and then by `terminate()` from the main thread. An owned timer must therefore never hold the isolate's event loop open on its own. Workers also use the short-lived wait timers in the shared libs (`libs/sleep.ts`'s signal branch, `libs/drainWaiter.ts`), which are not `unref`ed: their lifetime is settled by an abort or by `clearTimeout` in `finally`, so the rule is scoped by directory rather than by thread. `check:conventions` verifies this per handle across `packages/workers/`: it takes the assignment target of each `setTimeout`/`setInterval` and requires one `<same target>.unref()` inside the same function body, after that call and before the next write to the same target. A handle that lands on no target at all (a bare `return setTimeout(...)`) is rejected as well. This does not apply to the main thread, which also runs short-lived promise-race timers cleared in `finally` and the shutdown hard deadline.

### State-Machine Contracts

- `packages/types/states/` owns every state-machine `State/Event/Effect/Transition/Decision` contract. `packages/states/` implements only I/O-free pure transitions; interpreters and caches depend directly on those contracts.

  **There are two shapes, chosen by whether the subject has discrete states worth persisting**: `verification` and `lockdown` do (PENDING/ACTIVE and friends live in a Map and are referenced by later events), so they use the `transition(state, event) → {next, effects}` machine shape; `replyAdmission` and `adDetectAdmission` do not (the rules take scalars the caller already computed, while containers and timers stay in the runtime modules), so they are plain pure functions.

  Forcing the latter into the machine shape puts "my one item" and "how many across the whole thread" into the same state object, and those have entirely different lifetimes.
- **Every lockdown read-modify-write of default chat permissions passes `use_independent_chat_permissions: true`.** Applying, expiry restoration, corrective reapplication after a late receipt, and main-thread onGiveUp emergency restoration use `packages/workers/antiRaid/lockdownApi.ts` and `packages/infra/telegram/lockdownPermissions.ts`. Both boundaries reread `getChat().permissions`, change only `can_invite_users`, and pass all other default permissions, including unknown fields, back to Telegram unchanged.
- **A lockdown notice belongs to the round that started it** (`LockdownState.announced` and `announcementMessageId`). After the APPLYING placeholder is installed, the notice enters the per-chat serial chain before permission preparation. Dispatch and receipt application check the `LockdownEntry` object identity. Unsent work for an ended round stops; an already-sent notice is cleaned up by its own ID on the same chain without claiming the new round’s notice. `onSent` records the remote ID before cancellation propagates. The current round persists its notice ID and deletes that message after restoration; deletion errors are logged without changing permission-recovery state.

- **An unlock announcement requires this round to have announced the lockdown** (`announced`). Expiry, manual release, an uncertain permission commit, and persistence failure all use the restoring state. Successful restoration uses the round’s announcement flag to decide whether to send the unlock notice.

  Announcement ownership follows the same lockdown round through APPLYING, ACTIVE, RESTORING, and RECONCILING. A threshold event in RESTORING keeps the restore intent and does not start a new round. `announced` and `announcementMessageId` persist with `{phase,intentId,originalPermissions,announced,announcementMessageId?,expiresAt}`; an ID requires a successful send, and an unannounced record with an ID is invalid. APPLYING may already be announced. In-flight announcement state is memory-only; recovery resends an unannounced lockdown that must continue, except while RESTORING. Completing the round’s restoration emits `reportUnlock` so main can remove the durable record.

- **A lockdown must advance toward restoration when its round expires.** The `LOCKDOWN_MS` deadline is fixed on entering ACTIVE and later joins do not reschedule it. Expiry first persists the restore intent; the durable ACK starts the restore API call. A threshold event in RESTORING only prefetches admins and never returns the round to ACTIVE. Failed restoration retries after `RESTORE_RETRY_MS`; once it has been denied permission (bot removed or demoted) more than `RESTORE_PERMANENT_FAILURE_LOG_LIMIT` times in a row it logs at warn level and the interval doubles from `RESTORE_RETRY_MS` up to `RESTORE_PERMANENT_RETRY_MAX_MS`, the record is kept, and the retry fires immediately when the bot is again confirmed able to restrict members. A restore request cancelled by the Worker shutdown drain is reported back as an ordinary failure, without touching the consecutive-denial count or logging an error. External API completion is not guaranteed to be instantaneous. Success clears the chat's join window. Announcement-deletion failure is logged without blocking a new round, which counts subsequent joins afresh.

- **The persisted permission copy contains only fields declared by the schema** (`normalizeChatPermissions` in `packages/libs/chatPermissions.ts`). Preparation narrows `ChatState.lockdown.originalPermissions` at the input boundary, and the strict decoder validates that copy. Restoration reads only its original `can_invite_users`. Writes to Telegram use freshly queried complete permissions and override only the invite permission; they do not replace other fields with the persisted copy.

- **Persistence failure retains recovery responsibility for a potentially effective restriction** (`persistFailed`). APPLYING drops its placeholder only if the commit has not been dispatched. A dispatched commit is treated as possibly in flight: the round enters RESTORING and compensates through its existing serial API chain. ACTIVE and RECONCILING also publish a restore intent and begin restoration without waiting for another durable receipt. RESTORING starts immediately if it was waiting for persistence and does not duplicate an in-flight restore. Main retains schema-valid recovery records for Worker reconstruction and clears them only on `unlock`; invalid Worker records are rejected before entering the mirror. The relevant transition starts `LOCKDOWN_RETRIGGER_COOLDOWN_MS`, and late or duplicate failures must match the current phase and intent. Failed restoration retains its state-machine retry timer.

- **A lockdown record from a Worker event must pass the persistence self-check before it is attached to the in-memory `ChatState`** (`assertPersistableLockdown`). `ChatState` is written to memory first and persisted after: attaching a record that cannot pass the check makes every later state write for that chat (any toggle command) throw, and that error travels an uncaught path and takes down the whole update. The gate must sit at the entrance, not at `encodeChatStateData`.

- **`commitApply` is dispatched only once per applying intent** (`commitStarted`). Dispatch does not prove that Telegram has committed: the task may still be queued or querying permissions. Before execution, after that query, and before applying the result, the task checks its round entry, phase, and intent. Cancelled work cannot tighten permissions. Duplicate persistence receipts do not dispatch again; adopting a durably confirmed intent sets the flag with dispatch. `lockdownRuntime.ts` interprets states and timers, while `lockdownApi.ts` executes serial API effects.

### AI Chat Runtime

- Weather refresh belongs to the AI Worker and starts only after it receives `init` with the configured time zone set to `Asia/Tokyo` (the same condition that mounts `get_tokyo_weather`); other time zones send no weather requests, and the mood draw has no weather weighting. Stopping clears the interval, cancels in-flight HTTP requests, and revokes permission to update the cache. After a restart, only the current loop may publish results. The HTTP boundary observes caller cancellation, the existing timeout, and the response-body size limit.

- `/mood query` and `/mood switch` share a main-thread request/waiter handshake with AI Worker acknowledgements. Any group member may use the former to read the currently effective mood without forcing a reroll; only the latter checks `isCanSwitchMood` and performs the reroll. The main thread registers the waiter before dispatch and settles it uniformly on timeout, Worker crash, abandoned restart, or shutdown. Each request carries an absolute deadline, and the Worker rejects expired queued requests before reading or rerolling. Only a `moodQueried` / `moodSwitched` acknowledgement whose request ID and expected event type both match proves the result. A later Telegram reply failure must not be rewritten as a query or reroll failure. The AI Worker keeps exactly one mood shared by all groups, and mood requests and acknowledgements carry no chat ID: a reroll from any group applies to every group, and `/clear_context`, `/ai_chat disable`, group teardown, and memory-capacity eviction never touch the mood.
- **AI chat teardown retains finalization responsibility across timeouts.** Main’s `pendingAiMemoryTeardowns` waits for durable deletion and `chatInvalidated` with the matching request ID; AI Worker reconstruction, give-up, or termination also settles old requests. A deletion timeout releases only its waiter, and late receipts continue finalization. If the Worker’s `memoryDeleted` creates another deletion, that tombstone must also be acknowledged. New records or snapshots take ownership and cancel old finalization; ordinary `/ai_chat disable` does not create this teardown identity. Once no new snapshot, first-persist marker, tombstone, or waiter remains, main releases the chat counter and sends `forgetAiMemory` through the FIFO. A single global revision floor prevents a new lifecycle from reusing released numbers. Pending teardowns are capped at `STATE_MANAGED_CHAT_LIMIT` (25); exhaustion signals the existing storage fatal boundary and rejects new responsibility. Main replays pending deletes after DiskIO reconstruction; process restarts do not restore these in-memory identities.

- AI-chat invalidation is an awaitable cancellation boundary. The first generation-sensitive task for a chat receives an epoch that is never reused within that Worker isolate. Invalidation synchronously deletes the current epoch, aborts the old generation, and clears work that has not started, then waits for the registered reply rounds, rate-limit notices, media descriptions, and memory compaction tasks under that epoch to settle before acknowledging `chatInvalidated`.

  **That wait must be bounded** (`AI_CHAT_INVALIDATE_DRAIN_TIMEOUT_MS`, comfortably below the main thread's `AI_CHAT_INVALIDATE_TIMEOUT_MS`). Memory compaction and media description both pass the generation's `AbortSignal` to model requests, and compaction retry waits receive it too; an external request may still take time to settle after cancellation. The unref expiry timer used by `Promise.race` must be cleared in `finally` whether tasks or timeout win. A timeout only ends the wait: old reply rounds continue to consume live capacity until their actual cleanup completes.

  Waiting without a bound means one `/ai_chat disable` landing on a mirror-block rotation makes the main thread reject first, and that rejection escapes into the grammY middleware: the update is marked failed, the final offset is withheld, and Telegram redelivers the same command after a restart. Give up on time, log one error, and move on — correctness does not depend on the wait, because every registered task re-checks its generation and can no longer write anything once invalidated.

  A late task performs only a side-effect-free epoch check; neither reclaiming the entry nor re-enabling the chat can revive an old token. The epoch Map therefore scales with currently active work rather than historical chats. The main thread may report invalidation complete only after both durable memory deletion and that Worker acknowledgement succeed. `/ai_chat disable` and `/clear_context` share that single `invalidateAiChat(chatId)` path: both require this chat's memory to be cleared and `chat_states.ai_context` set to NULL without touching chat state, and only the former also persists a switch.

- `/clear_context` requires the actor's `isCanClearContext` permission and clears only this chat's conversation memory. The super administrator always receives true directly; new allowlist members default to false. Grants and revocations are independent `/permission` changes.
- Transport, network, 429, and 5xx retries for model requests are owned solely by the selected provider's official SDK (Gemini through `@google/genai`'s `retryOptions`, OpenAI and Anthropic through their SDKs' `maxRetries`; all three are aligned at the initial attempt plus at most five retries). All three SDKs apply their timeout **per attempt**, so each of the three aiChat bottom-level wrappers (`aiChat/gemini/client.ts`, `aiChat/openai/client.ts`, `aiChat/anthropic/client.ts`) composes a deadline covering the whole call — every retry and backoff included — via `signalWithTimeout` from `libs/abortSignal.ts` and passes that down: once the signal fires the SDK short-circuits the remaining retries, so the worst-case hang equals the capability's timeout in `GEMINI_REQUEST_TIMEOUTS_MS` / `OPENAI_REQUEST_TIMEOUTS_MS` / `ANTHROPIC_REQUEST_TIMEOUTS_MS` itself rather than that value times the attempt count. Each package builds and caches its SDK clients per capability through `aiChat/capabilityClient.ts`. A caller's invalidate signal is composed with the deadline, never replaced by it. Once one request returns `failureKind: "request"`, callers must not wrap it in another full-request retry loop. Domain resampling is allowed only when the SDK request succeeded but the model response is unusable or ended abnormally (`failureKind: "response"`), or when normalized text is empty, preventing multiplicative request counts, latency, and transient allocations.

  `aiChat/openai/image.ts` also applies `OPENAI_IMAGE_REQUEST_TIMEOUT_MS` to both each attempt and the whole image call. The composed signal governs the SDK and the outer wait, including reference preparation, SDK retries, and backoff. Caller cancellation settles silently; expiry of the whole-call deadline is logged as a request failure.
- AI model calls never enter the Telegram gate, but equal provider, `base_url`, and API-key identities share one quota lane; model name and `headers` do not split a lane. Each lane permits 16 active model requests and 128 not-yet-started tasks, with at most 32 background waiters. After eight consecutive interactive starts, one waiting background task is admitted. SDK retries retain their original slot; a full local queue returns an explicit domain failure instead of retaining prompts or media bytes without bound. Telegram message pressure only pauses random interjections and reduces same-chat direct-trigger concurrency to one; provider and Telegram queues remain independent.
- Reply action tools validate, claim cooldowns and take quotas synchronously during the call (`send_voice` only reserves its daily unit at call time and records it when TTS succeeds); calls failing validation, eligibility, cooldown, or quota return errors immediately. Both round types return `success: true, queued: true, actions_used` by call ID, an admission receipt without a real message ID, and the receipt is what counts against the action budget; `toolset.execute` returns synchronously, so the model round trip never waits for pauses, synthesis, or sends. `send_voice` additionally starts synthesis and encoding in the background at call time, and its receipt does not wait for synthesis. Each round has a single serial action chain (`aiChat/ai/tools/replyToolset/actionChains.ts`): both round types queue accepted actions in tool-call order, and generation, human-like pauses, waiting for voice synthesis, Telegram queueing, and queue-owned retries run inside it; an ordered parallel round's chain waits for its delivery turn, while the direct round's chain has no gate; every step ends by switching back to idle. A voice moved to the background does not hold the chain and is appended to the chain's end once synthesis succeeds. Real results drive dependent sends and self-recording. Whole rounds are delivered in ingress order; later rounds cannot interleave with an earlier round’s text, corrections, or captions. Chains own failure logging and cleanup, and the model must not resubmit an accepted action.

  **Chat actions** (typing, choosing a sticker, recording voice, uploading a photo) are switched only through the round heartbeat handle (`aiChat/ai/chatActionHeartbeat.ts`). Action statuses are switched only by the chain step currently running; executors do not switch them at call time. The direct round additionally shows request statuses through `createDirectPacing` in `replyToolset/pacing.ts`: model requests made before any action has been accepted show "typing", and if the first action returned by such a request is text (`send_message`), it is sent under that status without an extra pause; the request right after a new sticker pack view shows "choosing a sticker"; other requests show nothing. A request status lights only while the serial chain is idle: when the chain goes from idle to having steps, its steps take over, and when it drains, a request that still wants a status lights it again; actions take over the request status at acceptance in call order, while a background voice step does not. Every other action switches to its own status on the chain, pauses, and switches back to idle when it finishes; when the model phase ends (`toolset.afterModel`), a request status not taken over by an action is withdrawn. `view_sticker_pack` itself does not touch the status. Callers switch to idle and settle before a send, and switch to idle again once it lands. Switching to idle ends a status segment, and the chat then stays silent for `CHAT_ACTION_REST_MS` (500 ms) counted from the last idle: no chat action request is sent, a switch made meanwhile lights only when the silence ends, and the human-like pause is extended by the remaining silence so the visible duration is kept. An idle from a round that does not hold the current status neither withdraws it nor starts the silence. After a typo message lands, the correction waits `TYPO_QUICK_CORRECTION_MIN_MS`–`TYPO_QUICK_CORRECTION_MAX_MS` (1–2 seconds) in silence, then shows "typing" for `TYPO_QUICK_CORRECTION_TYPING_MS` (1 second) before it is sent.

  `view_sticker_pack` synchronously returns the current round's actual menu indices, names, and descriptions and records the viewing intent, without waiting for pauses or sends. A round may view five distinct packs, each once; sending must use that same previously viewed menu. Weather and group-QA tools read existing data, with query quotas separate from action reservations.

  `activeReplyCounts` counts unfinished model rounds, including the direct round. The limit comes from `replyRoundConcurrencyLimit` in `states/replyAdmission.ts`: at most `REPLY_ROUND_MAX_CONCURRENT` (5) ordered parallel rounds per chat; the direct round (started when the chat has no round in flight, i.e. no delivery window) is independent of them and takes one extra slot while its model runs, tracked by the window's `directModelActive`; under Telegram pressure a chat runs 1 round in total. Admission and queue draining use the same limit. `pendingReplyTriggers` holds at most `REPLY_TRIGGER_QUEUE_MAX` (15) unstarted direct triggers per chat, independently bounded by 25 managed chats (375 entries total); teardown clears that chat's waiting entries. In the AI Worker, `replyDelivery.ts` reserves ingress-ordered positions in one FIFO per chat window. All live generations share `REPLY_DELIVERY_MAX_PER_CHAT` (32) and `REPLY_DELIVERY_MAX_TOTAL` (128). Full capacity drops random triggers and queues direct triggers; queue overflow records a temporary notice. Failed reservation consumes no rate quota and builds no prompt or model task. Only successful startup removes the queue head; media recognition follows reservation. When the model phase ends (including early returns and cancellation), the round commits and releases its model slot: an ordered parallel round marks its full chain ready, and the direct round returns its extra slot. Only the ready head sends, and completed empty or failed rounds are skipped in order; the direct round heads a new window and is ready as soon as it reserves, so its chain runs each action right after acceptance and sends while it generates, its model phase does not wait for sends, and later ordered parallel rounds are released in order only after it finishes. Actual sends and heartbeat cleanup precede live-capacity reclamation. `onFinished` settles overflow notices and drains waiting chats; a served chat with remaining work moves to the tail. Invalidation, reset, and invalidation-wait timeout detach current windows without releasing old tasks' capacity. Late old-generation cleanup cannot delete a new window; destroying the Worker releases its counters. The five-minute rate limit, trigger FIFO, provider lanes, Telegram per-chat send scheduler, and categorized 429 queues retain their respective controls. Each round stays in its generation task set until its serial action chain (including any voice moved to the background) and its heartbeat settle and its delivery position is reclaimed. Exceptions from either completion callback must not skip cleanup. Invalidation and shutdown signals reach actual requests and queued retries. Memory eviction first skips chats with an active model or current-generation task, falling back to LRU when all candidates are active. Only actually sent messages and Telegram-confirmed reply relationships enter self-recorded memory; admission receipts do not.
- AI replies synchronously reserve text, sticker, reaction, image, and voice actions against one unified action budget at admission: the model-visible prompt limit is 8 and the execution hard cap is 11. Sticker, reaction, generated-image, and voice actions may each be accepted at most once; other action tools have no per-tool call cap. Sticker-pack viewing retains an independent lookup cap; the per-reply server-side web-search count is a soft limit written into the prompt, and the execution side only accounts for it and names it once it is crossed. All custom function calls also share a whole-round loop guard, and every call beyond it receives only a "budget exhausted, stop calling tools" tool result. All of these caps, together with the action hard cap, are enforced solely on the execution side: none of them may change the round's tool declarations midway.

  The final body falls back through `send_message` only if no action was accepted. Every intentionally displayed piece of text must be produced by an explicit model tool call and must never be left in the final response body alone.

  **Visible text has exactly two outlets**: a standalone message goes through `send_message`, and the line accompanying the image this round's `generate_image` produced goes through that tool's `caption`. A captioned generation is **one** Telegram message with one `message_id`, so it counts as one action and its self-record must be merged into a single entry. When a caption exceeds `TELEGRAM_CAPTION_MAX_CHARS` the Bot API rejects the whole send rather than truncating, so the execution side degrades to "photo without caption + one standalone text message" and reserves `actions_used: 2` at admission. With fewer than two slots remaining, only the image is accepted and the receipt reports `caption_delivery: "no_action_budget"`. A typo message with a follow-up correction likewise reserves two slots; the correction runs only after the original message actually sends.

  **Duplicate text within a reply round is silently skipped before sending.** `send_message` bodies and model-authored `generate_image` captions share `modelAuthoredTextPolicyResult`. After normal reply cleaning, comparison alone collapses whitespace and applies Unicode NFC, then matches the complete string against accepted model text, captions, and the execution-reserved correction character. Words, case, and punctuation remain distinct; semantic similarity is not a hard rejection criterion. A match returns `{"success":true,"skipped":"duplicate","actions_used":0}` without typing state, generation requests, cooldown claims, Telegram sends, or memory self-recording. Failure or cancellation after admission neither refunds the reserved budget nor permits model resubmission. Rejected calls reserve nothing, and deduplication state is never shared across rounds.

  The system prompt requires each idea to be expressed once, without paraphrased repetitions or extra actions to fill a quota. A trigger already answered with nothing new to add ends the round; queued replay follows the same rule. Skipped results still return to the SDK session paired with their call IDs. Model output and tool results remain append-only: history, encrypted reasoning, thought signatures, and the round's tool declarations are preserved.

  **The tool list is constant; per-round eligibility lives only in the round's tool status and is enforced by executors.** `createReplyToolset` assembles tools from deployment capability and the startup time zone: `get_tokyo_weather` is mounted only when `bot.json.time_zone` is `Asia/Tokyo`, including the omitted default; `generate_image` is mounted when an image provider is configured, `send_voice` when `agent.tts` is configured and the selected implementation has `synthesizeSpeech`, `group_qa_query` / `group_qa_answer` always, and `send_message` always declares `typo_original_char` / `typo_replacement_char` as optional fields (their descriptions only say "fill when the reply task asks"; the typo rules are appended to the reply task through `TYPO_REQUIRED_INSTRUCTION` only in drawn rounds). Within one deployment and persona, declarations are byte-identical regardless of trigger type, the chat's Q&A entries, or the typo draw. The `send_message` and `send_voice` declarations (including the `text` / `tone` parameter descriptions) and the system prompt's "行动与停止" (action and stop) section take the same copy from `VOICE_LANGUAGE_PROMPTS` (`consts/aiChat/prompts/tools.ts`, one copy each for `en` / `zh` / `ja`) according to `agent.tts.bot_language`; when the `tts` section is omitted, `TTS_DEFAULT_BOT_LANGUAGE` applies. When `prompt/voice_tool.md` has been adopted, the `send_voice` tool instruction uses its text instead (`buildSendVoiceToolDefinition` reads `voiceToolPromptCache`), while the parameter descriptions, the other two places and the speaking-language requirement of synthesis requests (`speechLanguageStyle`, carried into every AI synthesis request by `createSendVoiceExecutor`) still take that copy. `createReplyToolset` selects it once and hands the action section to `workers/aiChat/replyModel.ts` through `ReplyToolset.replyActionInstruction`, so all three agree on the language within a reply. Per-round availability is snapshotted once by `aiChat/ai/tools/replyToolset/toolStatus.ts` at assembly time and rendered as 【本轮工具状态】 in the runtime-state block: the image line reads available (with the reference-material note), unavailable (not a direct mention/reply), or cooling down (with remaining seconds; `superAdmin` triggers bypass the cooldown); the voice line reads remaining or used up; the Q&A line reads the registered count or none; a configured standalone-search line states the round's function-call limit. The section states facts only; "do not call tools marked unavailable, cooling down, or used up" lives in the action-and-stop section. Because the snapshot can go stale during a reply, executors check again at call time: `generate_image` with `mediaToolsRequested` false (`replyRound.ts` sets it only when a member directly mentions/replies to the bot or invokes it through media with a `directTriggerReason`) is rejected as not authorized, the chat cooldown is claimed atomically at call time and a cooling-down call is rejected with the remaining seconds, a chat without Q&A gets an empty list, and typo fields are ignored outside drawn rounds. Eligibility does not imply creative intent; the model still decides whether the message requests creation.

  **Tool receipt semantics are declared once, in the action-and-stop section (`VOICE_LANGUAGE_PROMPTS[*].replyActionInstruction`)**: an `error` means the action did not happen, so the model must not treat it as done, quote it, or retry it verbatim, and must not react to the failure itself (no apology, no explanation, no mention of tools, quotas, cooldowns, or failures). The only exception: when a member explicitly asked for a picture this round and `generate_image` is unavailable or rejected, the model tells them in one sentence that it cannot draw this time.

  **`send_voice` has no per-round eligibility.** Under one `bot_language` its declaration is byte-identical every round, and whether to send a voice message is left entirely to the model under the tool instructions. At call time the executor checks, in order, that the reply is still active, the one-per-reply cap, provider capability, and the arguments, then reserves one daily unit in the `ai` scope (`reserveAiTtsUsage`); when `agentCount` in the window plus in-flight reservations reaches the limit it refuses immediately with `SEND_VOICE_DAILY_LIMIT_TOOL_ERROR`. On admission it returns an acceptance receipt right away and reserves a slot in the unified action budget, starts synthesis and encoding in the background, and queues the delivery step on the serial chain in call order, the same in both round types; the model does not wait for synthesis. When the chain reaches the delivery step while synthesis is still running and `VOICE_FOREGROUND_WAIT_MS` (25 seconds from the call) has not elapsed, it shows "recording voice" and waits; when the window closes, it withdraws "recording voice", moves delivery to the background (`chains.defer`), and lets the chain continue; a background synthesis that succeeds is appended to the chain's end. A failed synthesis (including a timeout or unusable audio) sends nothing and only logs `AI reply voice was not sent` in English; the model never learns about it, and nothing is logged once the reply has been invalidated. Before every voice message is sent, including a background re-send, "recording voice" is simulated for the audio's duration, regardless of how long it was already shown while waiting for synthesis. The synthesis result is awaited outside the tool call by the window timer, the serial chain, and background delivery, so `synthesizeVoiceMessage` never throws: an unexpected exception from the synthesis entry point or encoding is logged and settled as a synthesis failure. The reservation lives only in AI Worker memory (`pendingAiTtsReservations` in `cache/workers/aiChat/ttsUsage.ts`) and is never persisted; `agentCount` is recorded only when the TTS call succeeds (`settleAiTtsReservation`), a failed TTS call, a cancellation before success, or a thrown error only releases the reservation, and once the TTS call has succeeded an encoding failure, send failure, or cancellation is not refunded; the tts facade does not record `ai`-scope requests; only the `/send` and cron operator scope is claimed by the facade before the request. The line (`text`) is limited to `VOICE_TEXT_MAX_CHARS` and the optional tone (`tone`) to `VOICE_TONE_MAX_CHARS`; over-length or wrongly typed values are returned as argument errors, never truncated. The line is spoken audio rather than a visible-text outlet, so it does not go through `modelAuthoredTextPolicyResult` deduplication. "Never resend what the voice already said via `send_message`" is enforced only by the prompt, judged by meaning (the line is in the `bot_language` language, so translating it, rephrasing it, or annotating it all count as repetition); the execution side does no semantic comparison. The prompt also forbids text that mentions, announces, or points at the voice, or explains why no voice was used, because text issued in parallel in the same response is written before the synthesis result exists. After the voice message actually sends, the execution side writes the `（发送了一条语音：…）` self-record marker for that message. Voice has a daily quota: at the start of each reply the model-visible remaining count (`daily_limit - daily_reserve_quota` of this isolate's current `agent.tts`, minus `agentCount` in the current window and in-flight reservations, never below 0) is read once and rendered as the voice line of the round's tool status (`voiceToolStatus`, present only when `send_voice` is mounted); the block count stays at 4, the stable prefix and tool declarations are unaffected, and tool round-trips within one reply reuse the same status. The acceptance receipt carries `voice_remaining_today` (the remainder after this reservation). The quota-exhausted error text and the tool instructions tell the model not to retry and not to mention the voice, the quota, or the failure in the group.

  **"Text + tone → voice" has exactly one implementation** (`packages/aiChat/ai/voiceSynthesis.ts`, AI Worker): `resolveSpeechSynthesizer` decides whether the entry point exists, `synthesizeVoiceMessage` synthesizes through the tts facade (the interactive-priority quota gate), skips encoding once the signal is aborted, and then `aiChat/ai/voiceEncoding.ts` turns it into a Telegram voice by MIME: WAV is resampled to 48 kHz and encoded to OGG/Opus in `VOICE_OPUS_ENCODE_CHUNK_SECONDS` chunks, yielding the AI Worker event loop between chunks; OGG/Opus and MP3 are only container-checked by `aiChat/ai/utils/voiceContainer.ts` (Ogg page layout and OpusHead, MPEG Layer III frame sequence), timed, copied into an exclusive buffer and used as is. The result carries an upload file name matching its container (`voice.ogg` / `voice.mp3`), which all three send boundaries use. The tone is always appended after the base reading style (the xai protocol has no style field and does not send the tone). The tool declaration, argument rules, per-round cap, and reply attachment belong only to the AI voice tool. `/send` relay TTS requests and `send_voice` in `cron.json` post `synthesizeVoice` from the main thread through `packages/aiChat/voiceSynthesis.ts`; the Worker returns the result in a `voiceSynthesized` receipt with the same requestId, transferring the voice bytes' buffer on success. A waiter is registered before posting and settles on exactly five paths: the receipt, the `VOICE_SYNTHESIS_REQUEST_TIMEOUT_MS` timeout, caller cancellation, a rejected post, and Worker crash respawn / abandonment / termination; timeout and cancellation also post `cancelVoiceSynthesis` to abort the Worker-side synthesis, and a late receipt is dropped as an unknown requestId. Settlement always returns a result union and never rejects. On the Worker side each synthesis signal is combined with the Worker lifecycle signal, and a request arriving after draining starts is answered with "worker unavailable" directly. The operator line limit is `VOICE_OPERATOR_TEXT_MAX_CHARS`, which bounds how long a single encode occupies the AI Worker thread. **The operator entry points' daily count is recorded in the tts facade** (`packages/aiChat/provider.ts`): every request queues through the quota gate, and when a `quota: "operator"` request runs it calls `claimOperatorTtsUsage` in `aiChat/ai/ttsUsage.ts` right before the provider request; requests cancelled while queued or rejected by a full queue are not counted, and a request over its caller's limit is not sent and settles as `daily limit reached`. A registration returns a claim (the start of its window); when the provider yields no audio (returns null or throws), the facade passes that claim to `refundOperatorTtsUsage` to give the use back, unless the window has rolled over since. The AI voice tool reserves and records on its own as described above and passes `quota: "ai"`, which the facade synthesizes directly without recording. Limits come from `ttsQuotaLimit`: the `ai` scope is `daily_limit - daily_reserve_quota` (the AI voice tool reads this isolate's current `agent.tts` at admission); `/send` and cron requests forwarded to the Worker pass `operator`, with limit `daily_reserve_quota` (from the `agent.tts` captured when the facade was built). AI checks and increments only `agentCount`; `/send` and cron check and increment only `reserveCount`. Neither quota borrows from the other. A zero reserve disables synthesis through both operator entry points. When hot reload changes either field the facade cache is discarded as a whole, new requests are judged against the new values, and the used count is not reset. One recorded use corresponds to one synthesis call; retries inside the provider request (`GEMINI_SPEECH_REQUEST_ATTEMPTS`, `OPENAI_SPEECH_REQUEST_ATTEMPTS`) are not counted separately. The window starts at its first request; when a use is recorded `TTS_USAGE_WINDOW_MS` or more after the window start, that request starts a new window, clears both counts, and increments only its own count.

  A direct trigger queued after the concurrency gate filled must stay at the head of the queue when the rate-limit gate refuses it during drain, and draining must stop there: the limiter only looks at the chat's window count and is independent of which trigger it is, so the first refusal means every following one is refused too — and a refusal does not increment the concurrency count, so continuing would discard the entire queue of @-mentions and replies within one synchronous tick, leaving all of those people with no reply at all.
- **Speech configuration snapshots**: `packages/config/agentCapability.ts` strictly parses `agent.tts`: `provider: "openai"` must declare `speech_protocol` (`openai` / `xai`) and `google` rejects it; the `xai` protocol rejects `model` and `style` and defaults `language` to `auto`; `style` defaults to `TTS_DEFAULT_STYLE` and invalid values are rejected. All three protocols accept an optional `bot_language`: after trimming it must be one of `TTS_BOT_LANGUAGES` (`en` / `zh` / `ja`), it defaults to `TTS_DEFAULT_BOT_LANGUAGE` (`ja`), and any other value refuses startup; it selects which voice-related copy AI replies use: the prompts visible to the reply model and the speaking-language requirement appended to AI speech synthesis requests (`speechLanguageStyle`); the field value itself is never sent with synthesis requests and is independent of the xai `language`. `packages/aiChat/gemini/speech.ts` and `packages/aiChat/openai/speech.ts` read the protocol, model, voice and style (or language) from the same tts snapshot when issuing a request; the google and openai protocols compose `<style>[; <speaking language>][; 细节: <tone>]` through `aiChat/ai/utils/speechStyle.ts`: only the AI reply send_voice executor adds the speaking-language requirement for the round's `bot_language`, `/send` and cron (`workers/aiChat/voiceSynthesis.ts`) do not, and the xai protocol sends neither. Hot reload affects subsequent requests; removing style restores the default. The openai protocol requests `response_format: "opus"` through the official SDK; the xai protocol requests `mp3` with fetch in `packages/aiChat/openai/xaiSpeech.ts`, retrying network errors and 408/429/5xx up to `OPENAI_SPEECH_REQUEST_ATTEMPTS` attempts within `OPENAI_SPEECH_REQUEST_TIMEOUT_MS`, failing other non-2xx responses directly and never following redirects. Both read the body within `VOICE_SPEECH_MAX_BYTES` and label the MIME from the requested format rather than the response header.

- **Anthropic responses are classified by stop reasons and tool results**: bodies ending with `max_tokens`, `refusal`, or `model_context_window_exceeded` are unusable. Ad detection resamples at most `AD_DETECT_EMPTY_BODY_MAX_ATTEMPTS` times; request exceptions do not add business retries. Reply sessions and standalone search continue `pause_turn` with the unchanged assistant content, at most `ANTHROPIC_PAUSE_TURN_MAX_CONTINUATIONS` times, combining text and search counts across segments. Standalone search fails on `web_search_tool_result_error` even with HTTP success and does not return explanatory text as a search conclusion. Structured JSON schemas pass directly to the SDK, while callers still strictly decode the result.

- **Model tokens come from valid SDK usage responses**: `packages/infra/aiCacheUsage.ts` owns validation and per-thread reporting; `packages/infra/aiCacheUsageRelay.ts` owns the main-thread diagnostic envelope sent to Disk I/O. Reporting covers text, summary, media, image, tts, web_search and ad_detect. TTS Interactions, image generation/editing and audio transcription adapt their own protocols. Reporting precedes body validation and media decoding; valid usage returned after outer cancellation is still counted once, while requests without SDK usage are not estimated. Gemini response and thought tokens are validated separately before addition; OpenAI output does not add reasoning tokens again. Duration-only transcription responses are not converted to tokens. When token counts are present only tokens are recorded; responses that report only a cost (xAI image generation's `cost_in_usd_ticks`, via `reportXAiUsage`) are recorded as cost usage, never both for the same response. Provider clients report search counts together with valid token usage from the same response, counting one request in the daily summary. Without valid tokens, `reportAiSearchUsage` records only the search count and does not add a request. Counts must be non-negative safe integers; 0 is omitted, and searches already run inside a failed response still count. Anthropic uses `usage.server_tool_use.web_search_requests`; when absent, only successful `web_search_tool_result` blocks count, excluding unexecuted calls and tool errors. OpenAI counts only `web_search_call` actions with `action.type: search` and `status: completed`, excluding page opens, in-page finds, and unfinished calls; see [OpenAI web search](https://developers.openai.com/api/docs/guides/tools-web-search). OpenAI audio/speech and xAI `/tts` speech responses carry no usage; each response is diagnosed as `missing` and not recorded. Reporting failures do not change model results; see [07 operations](07-operations.md) for diagnostics and persistence.

- AI reply admission is two independent gates separated by an open-ended "queued, waiting to be drained" middle state: the concurrency gate (`admitTrigger`) decides when a trigger arrives, the rate-limit gate (`isReplyRoundRateLimited`) decides against the 5-minute sliding window just before a round actually starts. When the rate-limit gate rejects, only a direct trigger (`directInvokerId` set) gets a rate-limit notice; random interjections and random media comments return silently.

  **While the queue is non-empty every trigger is enqueued, even if a concurrency slot is free**: the queue is FIFO, and letting a new trigger cut in front of people who already waited a round inverts that semantics entirely — the moment the window opens, the first to run would be the one that just arrived while the queued ones have been waiting for minutes.

  The waiting queue has four drivers: model-processing completion (`onModelFinished`), actual delivery completion (`onFinished`), an immediate attempt after enqueueing, and the AI Worker's maintenance tick (`drainPendingReplyQueues`). Model completion can start more work without waiting for delivery.

  The post-enqueue attempt and maintenance tick also wake a chat with no active model and a non-empty queue. Rate-limit rejection creates no round task, so maintenance resumes the queue head when the window has room again.

  All four drivers check the five-minute window through `drainReplyQueueIfWindowAllows` and skip saturated chats; each actual round start still passes `isReplyRoundRateLimited`. The model-completion callback only drains waiting triggers. Overflow notices remain pending until ordered delivery completes and are settled there; if the chat has no live round when the notice is registered (`hasLiveReplyRounds` in `replyDelivery.ts` is false, so no completion driver will follow), it is sent immediately.

  **Flushing the overflow notice must be a separate path from draining the queue** (`flushOverflowNotice` vs `drainReplyQueueIfWindowAllows`): the notice `enqueueOverflow` owes the chat has to go out whether or not the window has room, so folding the two into one function means either gating swallows the notice forever or leaving it ungated brings the spam back. One wasted attempt sends a rate-limit notice (itself on a 60-second cooldown), i.e. one line into the chat every minute.

  Enqueue first, then push, so the order stays first-come-first-served.
- The main-thread AI activity-probability layer is the admission gate for random proactive replies, not the reply-round rate limiter. Every visible group message first enters that chat's sliding window; more recent messages raise the random-trigger probability until the hot-chat ceiling is reached. Chats never borrow activity from each other, a process restart begins from cold state, and direct triggers bypass this probability gate. Tunable values live in `packages/consts/aiChat/rateLimit.ts`; documentation fixes these semantics, not the current numbers.

  This activity table is also a JIT-hot path hit by every group message. A hit for an existing chat updates the stable-shaped `AiReplyActivityEntry` (`timestamps`, `lastAccessSequence`, `lastObservedAt`) in place; it must not reorder the Map through `Map.delete` plus `Map.set`, or allocate a temporary compound key or projection object. Only the cold path that inserts a new chat into the bounded full table scans it to choose the LRU. Window timestamps, capacity, eviction order, and wall-clock-rollback protection are semantic and must survive performance changes.

  The main thread owns the per-chat, per-speaker random-reply cooldown map, `userReplyTriggerTimes`, as two nested Maps keyed by numeric chat and identity IDs, without compound strings. `userReplyTriggerSweepState.size` tracks the global entry count during claims, renewals, sweeps, and clearing; capacity is shared across chats. Sweeps remove empty chat buckets, with one unref'ed sweep timer. A full-table sweep records only the interval `[validFrom, validUntil)` in which all entries are known to remain valid. New keys are rejected directly within that interval; expiry or clock rollback before the interval requires another sweep. Replacing an old key in a full table or clearing the table invalidates the interval. Production constants define capacity and cooldown duration, and valid entries are never evicted.

  Telegram reply backpressure reads the main-thread outbound gate's current active and retry-pending counts for the message lane and carries the final boolean in the existing message. Other lanes do not affect reply admission. Diagnostic commands continue to use the `telegramOutboundStats` snapshot.

  **One wall-clock read per group message.** `handleIncomingMessageMiddleware` takes `Date.now()` once at the entry point, and the activity-window insert, the quiet-period check, and the random-reply cooldown claim all use that single value (threaded downstream through `MessageTriggerContext.now`). The Anti-Raid side works the same way: the `now` handed to `enqueueAdCandidate` reaches the admin-cache TTL check unchanged. Functions that consume a `now` always accept it explicitly; every call site on the per-message path must pass one, and default arguments are reserved for low-frequency command paths. Both halves of the rationale are load-bearing. Semantically, all checks for one message must land on one instant — reading the clock separately lets them straddle a millisecond boundary and reach contradictory conclusions. Practically, the cost of reading the wall clock depends entirely on the host clocksource: when a VM falls back to a source without a vDSO fast path, a single read can reach microseconds — two orders of magnitude more than the checks themselves — and the syscall's cache pollution slows the rest of the surrounding function as well.
- **All four media kinds (image / sticker / GIF / voice note) share one "placeholder → async parse → in-place backfill" pipeline**; the dedup cache, bounded executor, and backfill ordering exist exactly once, and the per-kind difference lands on a single dispatch — "vision description or voice transcription" (`resolveMedia` in `packages/aiChat/ai/imageDescription.ts`). A parallel pipeline for voice would mean writing concurrent-request merging, capacity eviction, and executor-slot contention a second time, and those are precisely the parts hardest to cover in tests.

  Non-catalog media descriptions share the AI Worker's `transientDescriptionCache`, keyed by `file_unique_id` and capped at 4,096 Promise entries (`MEDIA_DESCRIPTION_CACHE_MAX`). Hits refresh LRU order, overflow evicts only the least recently used entry, failed results are removed, and there is no TTL. Concurrent requests for the same media share a Promise; Worker reconstruction starts with an empty cache. Allowlisted sticker catalogs restore independently, consume no entries in this LRU, and are not deleted by its eviction.

  **Media recognition checks new-task capacity only after an LRU miss.** Each call performs one LRU lookup. Completed results return directly and in-flight results add a shared subscription; neither consumes another execution or waiting slot. A miss without capacity returns a null description without inserting a failed entry or evicting useful cached data. Closed-modality, backoff, and already-aborted checks still precede the cache lookup.

  Chat recognition, sticker-catalog descriptions, and image-generation reference downloads share the executor in `cache/workers/aiChat/mediaTasks.ts`. At most `MEDIA_DESCRIPTION_MAX_CONCURRENCY` (32) tasks execute, while executor-queued tasks and cold-probe waiters across both modalities total at most `MEDIA_DESCRIPTION_MAX_PENDING` (256). Each unknown modality runs one probe. Before entering execution or probing again, a waiter releases its waiting slot and admits the next step in the same synchronous segment. A task that needs no cold-probe wait may start immediately when an execution slot is free. Image-generation reference downloads pass the same cancellation signal to the executor and downloader. Cancellation while queued immediately removes the waiter; if the model request has not started, the action's cooldown reservation is released, and the action chain's finally settles its resources.

  `libs/sharedResult.ts` owns removable subscriptions for shared tasks. Cancellation immediately removes the waiting record and abort listener; normal settlement clears all subscriptions. Cancelling one consumer leaves other consumers active. When the last cancellable consumer leaves and no consumer without a signal remains, the underlying task is aborted and its LRU entry is removed only if the Promise identity matches. Settlement of a cancelled cold wait releases its waiting capacity. LRU eviction does not cancel tasks with surviving consumers, and cleanup of an old task must not delete a newer task under the same key. Worker reconstruction clears the executor, waiting count, and subscriptions.

- **Images the bot sent itself have a placeholder state and a content state in rolling memory** (`packages/workers/aiChat/botImages.ts`). A verbatim entry's optional `pendingImage` field (`origin` + `caption`) marks the placeholder state: the body holds only the self-record marker (the prompt, for generated images) and the caption. Its absence marks the content state: the marker carries the image description. The only transition between them is "description succeeded → rewrite in place and clear `pendingImage`".

  - Images sent by commands and scheduled tasks (the `/wed` result, the `/h_image` result, `cron.json` `send_image`, one entry per album photo) are written by `recordBotImage` as `（发送了一张图片）<caption>` placeholders and are not described up front. A `/wed` re-roll only resets the original entry, if still in the hot zone, to a placeholder with the new caption; it never adds an entry. The gate matches the inline-result self-record: AI chat is active in the chat and there is no copy target. The main thread calls this after the send has succeeded and it never throws: when the AI Worker is unavailable it logs one error line and the send result is unaffected. `/info` avatar receipts are deleted after 30 seconds and are not written to memory.
  - After `generate_image` lands it first writes a `（…生成并发送了一张图片：<prompt>）` placeholder, then immediately describes the photo Telegram returned and, on success, rewrites it to `（…生成并发送了一张图片：<picture description>）`. A failed description keeps the prompt and the placeholder state.
  - When a member replies to a bot image, the main thread attaches `botImage` to the reply reference (the file_id, dedup key and original caption needed for description; it only crosses the thread with this record and never enters the verbatim buffer or disk). If the original entry is in the hot zone and already in the content state, its body is copied synchronously without describing again. If it is still a placeholder or has left the hot zone, the image is described and both the original entry (if still in the hot zone) and this reply reference are back-filled; for an entry that has left, the reply text uses the command-image marker with the description and original caption. In-flight back-fills are registered in `repliedBotImageBackfills`, and the reply round waits for them before building its prompt so the round sees the picture content. On failure the reply reference keeps `[图片] <caption>` and the original entry stays a placeholder, retried on the next reply.
  - Concurrent descriptions of the same image join the in-flight Promise and LRU above by `file_unique_id`, so a generated image's description and a later reply never issue a second request. A back-fill only applies while the entry still holds the same `pendingImage` object it had when description started: a `/wed` re-roll installs a new placeholder object, so a late description of the old picture never lands on the new picture's entry. Description is cancelled with the current reply generation, and nothing is back-filled after the generation is invalidated.

  **Voice's two limits (duration, declared size) must be checked before the download.** Telegram's update already carries `duration` and `file_size`, whereas the byte gate on the download side only learns about an overflow after pulling the whole file — an hour-long voice note would waste a media executor slot and the full download for nothing but a fallback placeholder. Rejected notes fall back to a plain `[语音 N 秒]` line; **what is rejected is the transcription, not the reply** — a direct trigger must still get an answer, since silence is worse than saying "that one was too long to listen to". Audio bytes are not transcoded (voice notes are always OGG/Opus and the multimodal endpoint accepts `audio/ogg`), but the byte limit is bound by the same inline-request budget: audio and images are both inlined as base64, which inflates by 4/3, and a Gemini inline request must stay within 20 MB in total (`MEDIA_INLINE_REQUEST_MAX_BYTES`). The vision limit `MEDIA_MAX_DOWNLOAD_BYTES` is derived so that the encoded bytes plus a 1 MB prompt reserve fit exactly (14,250,000 bytes); voice uses a smaller 8 MiB. The transcript truncation limit is likewise more generous than for media descriptions — that text is a member's **actual words**, not the model's summary, and cutting it in half makes the model answer the wrong question.

- Allowlisted sticker packs reconcile during AI Worker initialization and maintenance. During maintenance, complete packs without failure records make no requests.

Existing requests for the same pack still share their Promise; settlement caches results only for currently allowlisted packs. Catalogs, summaries, and per-sticker failure records retain active packs and packs with generation or reporting work pending. Generation settlement and dirty-snapshot reporting both retry cleanup. ### AI Prompts and Transcript

- The bot's own speech is identified by account ID and uses `SELF_SPEAKER_NAME` (`自己（也就是你）`, meaning “yourself—that is, you”) in self-records, speaker rosters, reply references, and summary input. These identity sections omit its Telegram `first_name`, `last_name`, and `username`. A separate self-identity sentence in the reply prompt's read-only reference memory supplies the current deployment's `@username`: the main thread fetches the account identity once per process startup through `bot.init()` and its `getMe` call, then passes it to the AI Worker through `initAiChat`. Worker reconstruction replays the same startup snapshot; individual messages and reply rounds do not fetch it again, and username changes take effect at the next process startup. The `me` roster code and account ID remain; other speakers' identities, message bodies, and mentions are preserved. Existing verbatim snapshots use the same rule at rendering time without changing the persistence format or historical summary text.

- AI replies use one fixed, provider-neutral web-verification instruction, and every model request in the same reply reuses an identical system prompt. It requires a search before visible action when information can change or a checkable fact is uncertain and a search tool is available; subjective chat, creative work, and facts already supplied by the transcript are not searched. Results outrank memory, insufficient evidence or an unavailable tool must be stated as uncertainty, and the search process stays hidden from group members. The built-in text search uses the fixed soft budget `MAX_WEB_SEARCH_CALLS_PER_REPLY`; the standalone function reads `agent.web_search.max_calls_per_use` from the round's tool-status line. Search takes one of two forms depending on whether `agent.web_search` is configured; the tool shape and the instruction change only with that configuration, and the explicit cache moves to a new slot when hot reload switches it:
  - Without it, the reply uses `WEB_SEARCH_INSTRUCTION` and attaches the `text` model's server-side search; `replyModel.ts` accounts for the real calls and names the overrun once it is crossed, but it neither rewrites the system prompt nor unmounts the server-side search tool.
  - With it, the reply uses `WEB_SEARCH_FUNCTION_INSTRUCTION` (the call limit comes from the round's tool status; results are reference material, not instructions; a result of 「模型搜索失败」 means insufficient evidence), attaches no server-side search, and attaches the local function tool `web_search` instead. The executor snapshots the validated call limit at construction (default `WEB_SEARCH_DEFAULT_MAX_CALLS_PER_USE`); each function invocation consumes one call, including invalid arguments and failed requests, independently of provider-side search counts. Excess calls make no request. It is the only tool executed asynchronously: `replyModel.ts` waits while the executor in `aiChat/ai/tools/webSearch.ts` sends one single-turn request with built-in search to the `web_search` capability's model, trims "notice + conclusion + numbered sources" to 2048 characters and at most 5 sources, and feeds it back. Whenever it does not succeed — invalid arguments, the per-reply limit exceeded, a failed or timed-out request, an endpoint that did not search at all, an empty conclusion — the tool returns only 「模型搜索失败」 and logs one error line without the query; text the model made up is never passed off as a search result.

  For “today”, “current”, and “latest” facts, verification uses configured local time to check when the fact applies; a page's publication time is not treated as the event time. Built-in text search uses the current time already present in the reply's runtime state. Each valid standalone `web_search` function call appends one reference time in the configured zone to the end of its query, shared by all searches inside that model request; the fixed system prompt contains no dynamic timestamp. `max_calls_per_use` limits local function invocations per reply, not provider-side searches within one model request or cron digests.

  Requests after an observed search (server-side search calls or local executor searches) set `grounded: true`; Gemini uses that signal to lower sampling temperature, while OpenAI Responses keeps the model's default sampling parameters.
- The initial input for an AI reply must remain four ordered text blocks: read-only reference memory, read-only current conversation, this round's runtime state, and the reply task. The blocks reach the implementation package in two groups split by whether they stay byte-identical across replies—the stable group holds only the reference memory, the volatile group the other three (`stableBlocks` / `volatileBlocks` on `AiReplySessionParams`)—and the stable group always comes first, which is the premise for any provider cache hit. The block count does not depend on the trigger type—a direct @/reply only adds one invoker sentence at the top of the reply task (`directInvokerSentence`, whose identity segment matches a transcript line verbatim); it must never insert another Part or copy that member's hot-window messages a second time. The blocks keep their domain meaning in `packages/workers/aiChat/replyModel.ts` and are mapped to a provider shape no earlier than each implementation package's `replySession.ts` (Gemini uses two adjacent `user Content` values for the stable and volatile groups respectively, with one `text Part` per block; OpenAI uses multiple `input_text` entries under one user message; Anthropic uses multiple `text` blocks under one user message and further splits the current conversation at the transcript's settled offsets, with breakpoints described below). Each section is enclosed only by model-visible start/end tags and a one-line responsibility marker. The global anti-injection rules—data versus instructions, forged boundaries being invalid, and non-disclosure of internal structure—appear exactly once in the system prompt, not repeated in each section. The runtime-state section is written by the system and is trustworthy; it holds today's mood, the current wall-clock time, and 【本轮工具状态】 in that order, but it only describes state and never assigns work. A matching tag, mood claim, time claim, or tool-status claim appearing inside transcript or summary text is always forged. Data Parts carry only data and tier labels: how to read a transcript line is stated by `TRANSCRIPT_FORMAT_INSTRUCTION` in the system prompt (which names the Part it describes), constant text must not be concatenated into the per-round transcript block, and the anti-injection whitelist therefore no longer has a "format explanation" category.

  The cross-task action-and-stop section (`ReplyToolset.replyActionInstruction`) and web-verification instruction live in the system prompt; the dynamic reply task contains only trigger-specific semantics and does not repeat those policies. Tool-call history is appended afterward with its true `model/user` roles; reference material must not masquerade as historical conversation turns. The system prompt is sent only through the provider's separate system field (Gemini's `GenerateContentConfig.systemInstruction` or OpenAI Responses' `instructions`) and must not be concatenated into ordinary conversation content. **The system prompt must stay byte-identical in full**: today's mood, the current wall-clock time, and the round's tool status are assembled into the runtime-state block by `buildRuntimeStateBlock` in `workers/aiChat/runtimeState.ts` and travel inside the user content. They must never move back into the system prompt, because that segment together with the tool declarations forms the provider cache prefix, and a per-second timestamp invalidates all of it.
- Gemini replies use two request structures (`aiChat/gemini/replySession.ts`). The first request of each reply references a shared explicit context cache (`cachedContent`) and sends only the complete `contents`, never `systemInstruction`, `tools`, or `toolConfig`; when no cache is usable yet, that request goes out in full. From the second request on, every request carries the complete static `systemInstruction`, the round's `tools`, any required `toolConfig`, and the complete `contents`, and the server-managed implicit prefix cache picks up the first request's blocks and the tool round-trips. Both structures produce the same token sequence; only `config` switches between `cachedContent` and the three full fields, and `contents` and the model content (thought signatures included) are handled identically. If the endpoint rejects the cache on the first request with a 404/4xx, the local registration is released and the request is resent once in full, and that slot is not created again for `GEMINI_CONTEXT_CACHE_RETRY_AFTER_MS`; endpoint failures are not resent.

  The shared explicit cache (the text scope in `aiChat/gemini/contextCache.ts`, registry in `cache/workers/aiChat/geminiContextCache.ts`) holds only "system prompt + tool declarations + toolConfig"; reference memory, transcript, and runtime state are never cached. Entries are slotted by the system-prompt fingerprint (the persona is a process-wide snapshot, so every chat shares one slot; slots adopted by the startup scan beyond `GEMINI_TEXT_CACHE_MAX_SLOTS` (1) are evicted least recently used first), and each slot records a content fingerprint (model, system prompt, tool declarations, toolConfig); the `displayName` is `copy-ninjia:text:<slot fingerprint>:<content fingerprint>`. Scanning, creation, renewal, release, and eviction are done by the capability-neutral shared core `infra/geminiContextCache.ts`, which the ad-detection Gemini cache uses as well (see [Ad-detection admission, classification, and disposal](#ad-detection-admission-classification-and-disposal)). Server entries live for `GEMINI_CONTEXT_CACHE_TTL_SECONDS` (24 hours). Acquisition never waits: a usable entry is referenced, otherwise the request goes out in full while scanning, creation, and renewal happen in the background—the first acquisition of a registry adopts existing entries carrying this scope's prefix through `caches.list` and leaves entries with other prefixes alone; a miss creates at most one entry per slot at a time; when the endpoint rejects a creation with 400 (content below the model's explicit-cache minimum, or invalid parameters) the content fingerprint and a rejection count are recorded and only a warning is logged: below `GEMINI_CONTEXT_CACHE_MAX_REJECTIONS` (3) rejections the same content is retried after `GEMINI_CONTEXT_CACHE_REJECTION_RETRY_AFTER_MS` (5 minutes), after that it is never created again, and a content change starts the count over; any other creation failure, and a release after a rejected reference, backs off for `GEMINI_CONTEXT_CACHE_RETRY_AFTER_MS`; a hit with less than `GEMINI_CONTEXT_CACHE_RENEW_BEFORE_MS` (30 minutes) left is renewed, a failed renewal backs off for `GEMINI_CONTEXT_CACHE_RETRY_AFTER_MS` as well, and a delete or renewal answered with 404 or 403 (the entry is no longer reachable with this credential; Gemini returns 403 for both missing and inaccessible entries) is not logged as an error, the renewal also silently dropping the local registration; these back-offs are judged from the failure time, and a wall-clock rollback to before that time ends the back-off; failure and rejection records are removed when the slot is created successfully or evicted; less than `GEMINI_CONTEXT_CACHE_MIN_REMAINING_MS` left counts as a miss. A content change within a slot creates a new entry and deletes the old one, and a new entry also deletes adopted entries never used since startup. A registry binds the text client current at its creation; when a hot reload changes `agent.text`, the registry is discarded and the next reply rescans with the new client, in-flight requests of the old registry only write to that registry, and entries under the old credentials expire through their TTL. Background requests follow the AI Worker's abort signal. Creation input tokens are billed at the full rate and recorded in `usage.json` as `text` usage with 0 cached.

  Stable reference memory must precede the volatile current conversation, runtime state, and reply task; later model turns and `functionResponse` values are appended only at the end of `contents`. Dynamic values such as the wall-clock time, mood, reference-media dimensions, the image cooldown's remaining seconds, the remaining voice quota, and the chat's Q&A count must stay out of the system prompt and tool declarations and may live only in the runtime-state block. Within one deployment and persona, tool declaration content and ordering must remain byte-identical regardless of trigger type, the chat's Q&A, or the typo draw, and **within a single reply both `tools` and the server-side search tool stay mounted unchanged**—the action hard cap, the function-call budget, and the search count may never mount or unmount a tool. The sole exception is the one downgraded retry after the provider reports its server-side tool-call limit, whose response was already unusable (it does not reference the explicit cache either). Across replies, only real semantic changes—persona updates, bot-identity changes, changes to deployment capability or the sticker menu, or cold-memory compaction—may change the prefix. Gemini alone decides whether an implicit-cache request hits and how long the implicit entry remains available. All OpenAI-protocol requests likewise keep stable content before volatile content and carry a per-chat `prompt_cache_key` derived from the stable prefix. Only the GPT-5.6 family on the SDK's default official endpoint adds an explicit `prompt_cache_breakpoint` after the last stable block while retaining `prompt_cache_options.mode: "implicit"` with a 30-minute TTL, so the cross-reply stable-prefix breakpoint and the growing in-reply breakpoint coexist. Earlier models and custom compatible endpoints must not receive those GPT-5.6-specific fields. Anthropic Messages only hits at block boundaries and allows at most four breakpoints per request; the reply session (`aiChat/anthropic/replySession.ts`) places them at the end of the system-prompt block (tools + system prompt), the end of the last stable block, the end of the current conversation's last settled segment, and a top-level automatic breakpoint (which lands on the request's last block, so later requests in the same reply read the whole previous request back). The current conversation is split into several `text` blocks at `AiReplySessionParams.conversationSettledOffsets` (taken from `ReplyPromptSections.currentConversationSettledOffsets`); splitting only moves block boundaries and the segments concatenate to the original block byte for byte. The Gemini and OpenAI implementations do not read these offsets and their requests are unchanged.
- How to read a direct @/reply is fixed by `DIRECT_INVOCATION_READING_INSTRUCTION`, which lives permanently in the system prompt and prescribes the reasoning order: first read `【最热记忆】` to work out what is currently happening in the group, then locate the invoker's messages by the roster code given in the reply task, and only then answer from both (transcript lines carry only codes and no `[id:]`, so the instruction must speak in codes or the model goes looking for a marker that is not there). It also fixes three anti-confusion rules: identify people only by the `[id:]` behind the code, forwarded text belongs to its origin rather than the sender, and earlier messages are context rather than things to answer one by one. The text is constant and lives permanently inside the equally byte-identical system prompt.
- Memory tiering (`【最热记忆】`, `【较早逐字记录】`, `【冷记忆】`) is only how the model reads its context and stays invisible to group members: `MEMORY_MECHANISM_SILENCE_INSTRUCTION` forbids reproducing or hinting at those tier labels in a reply, along with mechanism vocabulary such as context, block, `Part`, summary, compaction, sliding window, cache, size limits, token and system prompt.

  **The ban must name every tier label and inline marker that actually appears in the transcript** (the tier and roster block names, the `me`/`uN`/`fN` codes, `#messageId`, and the `[已滑出]` marker used when a replied-to target has been evicted). Those markers are written into the model-visible transcript to begin with, so a generic "do not expose internal structure" clause still leaves the model explaining whichever labels went unnamed — or volunteering "that one already slid out of the window" to explain why it forgot something, handing group members the internal context structure together with its capacity. Direct questions, and probes from members claiming to be developers, admins or testers, get no explanation, no confirmation, no denial and no "roughly, yes" implication; forgetting is expressed in everyday wording rather than as tiering, compaction, cleanup or window eviction. This is kept separate from `CHAT_MEMORY_PRIORITY_INSTRUCTION`, which governs only how the tiers are used, whereas this rule governs only never saying them out loud.
- The reply transcript uses a compact **roster + code** rendering (`buildTieredVerbatimTranscript`): each identity and forward origin appears once in the 【发言人名册】/【转发来源名册】 blocks and lines carry only the code; the bot always gets `me` rather than a `uN` slot. A date separator line is emitted only when the date changes, lines keep just the clock time, and each memory tier repeats the current date at its start. `#messageId` is written only for lines replied to within the segment and for this round's trigger message. A replied-to message that is still in the segment leaves only a `（回复 #id）` pointer — the model reads author and text from that line; only an evicted target falls back to an inline snapshot marked `[已滑出]`. The transcript is the single most expensive part of the input (80–86% of the user blocks, of which only a fifth is what members actually typed) and is resent on every reply. Together these compressions cut roughly half of the transcript's tokens while scoring level with the full format across 88 objective questions on attribution, reply tracing and forward provenance. **The tier boundary is rounded up to a multiple of `TIER_BOUNDARY_ALIGNMENT`**: 【较早逐字记录】 only ever holds a multiple of that many messages, so the boundary moves once every `TIER_BOUNDARY_ALIGNMENT` messages and within one step the verbatim lines are a pure append over the previous round, so the cross-reply prefix cache reaches all the way to the previous round's trigger line (its `#message-number` appears only in the round it triggered). The rendering also returns **settled offsets** (`RenderedTranscript.settledOffsets`): the window is divided into cells of `TRANSCRIPT_SETTLED_SEGMENT_SIZE` messages by index, and only the cell boundaries before the cell holding the newest message are kept. Each offset sits right after the text of the previous cell's last message, before the following newline, date line, and tier header, so the same cell boundary keeps the same index when the tier boundary moves. The granularity must divide `TIER_BOUNDARY_ALIGNMENT` so that tier boundaries always fall on cell boundaries. The offsets do not change the transcript text; they only let a provider that hits at block boundaries split its blocks. **The roster comes after every verbatim line**: a new speaker or forward origin in the window only changes the end of the block and never breaks the prefix of the lines before it. Every prompt that describes the roster position (`TRANSCRIPT_FORMAT_INSTRUCTION`, the anti-injection rule, and `CHAT_INTERACTION_INSTRUCTION`) says "at the end of the transcript"; moving the roster requires updating them together. Rounding up also keeps 【最热记忆】 at or below `COMPACT_BATCH_SIZE` entries, matching the count written into that block's own title; the granularity must divide `COMPACT_BATCH_SIZE`, or the boundary misses the even split when the window fills. When one `message_id` has two entries in the hot window (one recorded by snapshot hydration, one by Telegram redelivering the same update) only the last is rendered—backfills such as a media description land only on the later entry, and two lines sharing a number make a `#messageId` pointer resolve to both. Detecting duplicates costs no extra pass: the context build already fills a presence set over every message, so the duplicate count comes free from `messages.length - present.size` and the input array is rendered as-is when there are none.
- References to people or messages outside the transcript must use its notation and **must not point to absent message numbers**. Invoker sentences use roster codes, and reference memory identifies the bot's own lines by `me`. Queued replay renders its single-hop reply reference through `RenderedTranscript.replyReference`: a target still in the window uses `#messageId`, while an evicted target uses an inline snapshot marked `[已滑出]`. `RenderedTranscript` exposes only transcript text, `codeOf`, and the single-hop reference renderer.

  Reply context retains only the single-hop reply relationship, forward origin, and Telegram exact quote from message records. The reply task does not recursively append a separate multi-level chain. Queued and slow-media triggers use their captured text and single-hop references without inventing source text or absent message numbers.
- Cold-history compaction (`summarizeBatch`) keeps the **self-contained** line format (`formatBufferedMessageLine`): it is a separate model call with no roster to consult and runs only once per `COMPACT_BATCH_SIZE` messages, so compressing it buys nothing. The two formats have separate description constants (`TRANSCRIPT_FORMAT_INSTRUCTION` for the compact one, `SUMMARY_SYSTEM_PROMPT` for the self-contained one); changing one must not incidentally change the other. On this path `systemPrompt` carries only the verbatim-constant `SUMMARY_SYSTEM_PROMPT` and the current time is appended at the **end** of `userContent`, after the whole batch of transcript lines — that constant is the only prefix of the request an implicit cache can hold, and a second-precision timestamp in `systemPrompt` or at the head of `userContent` would make it differ from the first byte on every call; the transcript lines already carry each message's own send time, so the trailing sentence only supplies "what time is it now".
- Inline transcript markers for group messages — reply quotes and pointers, the exact-quote fragment appended after a pointer, forward origins, roster entries, block names (`【最热记忆】`, `【较早逐字记录】`, `【冷记忆】` and both rosters) and tier block headers, date separators and message numbers — are generated from shared templates in `packages/consts/aiChat/prompts/transcript.ts`. Those templates produce both assembled text and the placeholder shapes used by the prompt's format description; the same format must not be hand-written independently on both sides. A placeholder shape must be produced by passing the placeholder through the template, never by running the template with a magic number and then substituting that digit out: once the template contains a second copy of the same digit, the substitution rewrites only the first and the description teaches the model a shape the renderer never emits. Forward attribution follows marker nesting: an outer marker belongs to the current message and an inner marker to the replied-to original.

  The bot's own action markers (`（发了一枚贴纸：…）`, `（…生成并发送了一张图片：…）`, `（发送了一张图片…）`, `（发送了一条语音：…）`) come from the same template file and are **written by the execution side only after the action actually landed**: they are the sole evidence that the action happened, so the model may read them but must never produce them.

  When image generation hits the chat cooldown, the model sometimes will not say "I can't" but instead types out, through `send_message`, the shape it has seen in the transcript — the chat gets a message claiming an image was attached when nothing was, and memory keeps a fabricated action record that the model itself will believe next round.

  A prompt prohibition is only probabilistic, so the `send_message` execution side hard-rejects once and tells the model to state plainly, in its own words, that it could not do it.

  **`generate_image`'s `caption` goes through the same rejection.** On the caption side the image really was sent, so the sentence is not literally a lie — but the whole value of the marker is that only the execution side can write it. Once the model can legitimately produce that shape from a caption, the `send_message` rejection is effectively dead and the model can copy it back into plain text next round. The caption check runs before `claimImageGeneration`: rewriting the caption is enough to pass, so it must not burn a chat cooldown.

  **The rejection must anchor on the full template shape, not the bare phrase** (`SELF_ACTION_TAG_PATTERNS`: the marker inside a fullwidth parenthesis pair, immediately followed by `：` or the closing `）`, allowing only a short prefix that does not cross `）` — enough to cover the model rewriting "参考素材" as "参考上传的素材"). **That RegExp set is a module-level singleton now shared by two executors, so it must never carry the `g`/`y` flag** — a flagged `.test()` maintains `lastIndex`, the two call sites would poison each other, and the symptom is a caption intermittently slipping a forged marker through, reproducible only when the previous call happened to match. A bare substring will not do: "发了一枚贴纸" and "生成并发送了一张图片" are ordinary Chinese, so a member asking "你刚刚生成并发送了一张图片吗？"

  gets the model's normal answer rejected, the round's final-text fallback runs through the same executor and is rejected again, and the bot ends up completely silent on a direct @-mention. All three consumers (execution-side writing, prompt placeholders, rejection test) share one literal; hand-copying it anywhere invalidates the evidence.


### Join Verification and Terminal Disposal

- Verification terminal work has at most 15 attempts per process. A completed terminal action waits for the final revision's durable receipt before removing its record. If the revision changes while waiting, the new revision is confirmed even when the attempt budget has been reached. Main-thread emergency lockdown recovery dispatches deletion of the recorded announcement before clearing the record; deletion failures use the shared Telegram logger, and recovery does not wait for deletion.

- Timeout verification rechecks the inviter through `isChatAdmin` in `checkingInviter`: a confirmed admin is exempt, and a confirmed non-admin advances to `expelling`. An unknown identity keeps the same terminal and disk snapshot, clears the local execution flag, and rechecks after the existing exponential backoff. Each execution still consumes a terminal attempt approved by the main thread.
- A terminal permit result applies only to the same state object, generation, and revision while the business lifecycle is active. A rejected current request, a current `stale` result, or an exhausted budget unloads runtime state and publishes the exact deferred index without advancing the revision or writing a tombstone. The main thread retains the disk snapshot and process-level deferral latch. Worker reconstruction does not reset that latch, and new events for the same key do not recreate verification; a full process restart restores it from disk. Results for old tokens, generations, revisions, or cancelled lifecycles are ignored.
- Duplicate durable ACKs cannot bypass a terminal's pending backoff timer. A timer callback must match the entry, state object, and current handle, and clears the handle before dispatching its retry. Old callbacks after rescheduling, replacement, or teardown do nothing. An exact durable ACK for `expelling.successNoticeSent` still completes the record immediately, even with a retry timer present.

- The Anti-Raid Worker's verification runtime shares a `VERIFICATION_RUNTIME_CAPACITY` (15,000) hard limit across persistent phases and `exempt`/`kicked` deduplication. At capacity, new keys are rejected before join counting, transitions, or effects. A fatal event is reported once per generation, and new joins remain blocked until a new-generation adopt or stop; existing keys, verification release, and terminal settlement continue. A new generation clears the old runtime before restoring the durable mirror. Same-generation incremental recovery at capacity may release only a nonpersistent deduplication slot for an existing durable responsibility; persistent phases are never evicted and the admission latch stays closed.
- The Anti-Raid Worker's revision map shares a `VERIFICATION_REVISION_CAPACITY` (15,000) limit across active keys and terminal keys still within their retention period. Existing keys remain updatable. For a new key at capacity, the Worker first clears expired tombstones; if still full, it rejects the key and asks the main thread to stop through the business Worker fatal boundary. Worker reconstruction replays active and deferred records from the main thread; generation isolation handles old tombstones.

- **Join verification and the anti-raid private mode share one per-chat switch, disabled by default**: verification windows and join counting exist only while `ChatState.isAntiRaidEnabled === true`. Identities holding `isCanControllAntiRaidPermission` (the super admin always does) toggle and persist it with `/antiraid enable|disable`. Both chains consume the same join events, so splitting them into two switches would only produce the combination nobody expects — verification off while the private mode still kicks people. Everything else running on the Anti-Raid Worker is **unaffected**: `/ad_detect`, `/flood_control`, the permanent blocklist's instant kick, and the join log that `/batch_kick` reads all keep their own boundaries.

  The gate sits on the **main-thread delivery side** (`packages/antiRaid/updateIngress.ts`): a disabled chat posts no `join`/`left`/verification `message`/`callback`. **Inviter-exemption changes (`adminsChanged`) are deliberately outside the gate**: they are low-frequency cache maintenance, `applyAdminChange` only touches the Worker-side admin cache and never the state machine, so delivering one while the guard is off has no effect at all. Dropping one does have a cost — cache entries expire by `fetchedAt` and `applyAdminChange` does not refresh it, so when "disable → someone is demoted → re-enable" all land inside one `ADMIN_CACHE_TTL_MS` window, everyone the demoted admin invites during the remainder of that window still skips verification. The Worker therefore needs no mirror of this switch — per the decision order in [Thread and State Ownership](#thread-and-state-ownership), the writer (the main thread owns `ChatState`) is the owner, and no cross-thread message is added. Blocklist instant kicks are still delivered, but **without `joinedAt`**: that field feeds the anti-raid sliding window, and a chat with the guard off must not have its threshold reached by blocklisted joins.

- **`/antiraid disable` means "stop triggering from now on" and also closes interactions that have become invalid**: `deactivateJoinGuard` makes the Worker feed every verification record of that chat through the state machine's `guardDisabled` transition (`packages/states/verification/disable.ts`). Every record returns to ABSENT, and the two kinds of verification reminder already sent by the bot are deleted because their buttons are invalid once the switch is off and must not remain indefinitely. Join announcements and members' own messages stay, and nobody is kicked (pending timeout expulsion and both terminal dispositions are voided together). Persisted `checkingInviter`/`expelling` records get a tombstone from the dispatcher, so a restart cannot adopt them back and resume kicking. An already-issued kick cannot be recalled, but its late settlement finds no state and creates no follow-up effect. Only an administrator's explicit `/antiraid disable` or `/init disable` uses this Telegram cleanup path; loss of administrator authority or departure performs local emergency teardown without calling a delete API that the bot can no longer use.

  The same message also sends `deactivate` to that chat's private mode: `APPLYING(preparing)` simply drops its placeholder (Telegram was never touched), every other stage moves to RESTORING and gives `can_invite_users` back through the existing persist→restore chain — with the switch off, nobody would ever unlock it again. The lockdown notice in the chat is removed as well. The join sliding window and the abandon cooldown are discarded too: re-enabling starts counting from zero and must not carry the previous cooldown's blind spot.

  When the Worker is unavailable this teardown fails: the switch is still persisted as off (the exception must not escape the handler, or the offset is withheld and Telegram redelivers the same command) and the reply must say plainly that the runtime was not fully torn down. Leftovers are collected by `purgeDisabledJoinGuards` (`packages/antiRaid/workerBridge/replay.ts`) on every process start and Worker respawn; it runs **after both adopt messages** — tearing down before adopting would send the teardown at empty state, leaving that chat's invite permission with nobody to restore it.

- Anti-Raid applies the same exemption semantics to direct comments and nested replies in linked-channel discussion groups. The recent-comment cache stores only message IDs and observation times; it does not leak source markers with no behavioral difference into the state machine.

  Only comment threads in linked-channel discussion groups are candidates: `message_thread_id` is also present on every message in a forum (topics) group, so forum topics must be excluded via `is_topic_message !== true` and always follow ordinary pending-verification semantics without triggering an extra barrier post or linked-channel lookup. A comment clue is delivered through `postAntiRaidDurably` only while the sender is pending verification; when the sender is not pending, the Worker only records the clue in memory and the main thread sends it with a plain `post`, relying on the same port's FIFO to deliver it ahead of any later join.

  A cold-cache `message_thread_id` is only an asynchronous confirmation candidate: treat it as an ordinary pending-verification message until lookup completes, and revoke that treatment only when `linked_chat_id` is confirmed and the state object/generation still matches. Lookup failure is fail-closed and permits later retries.
- **The Worker-side admin exemption cache must release its in-flight slot by identity and decide write-back by generation.** In-flight fetches are deduplicated through `getOrCreateKeyedTask` in `libs/keyedTask.ts` (shared with the linked-channel lookup), and its `.finally()` may delete only while `adminFetches.get(chatId)` is still its own promise (same as the main thread's `botPermissionFetches`): `resetAdminCache()` clears the whole table while a fetch is in flight, a new fetch for the same chat then registers, and an unconditional delete from the stale fetch removes the **new** fetch's slot — deduplication breaks and the next caller starts yet another full fetch through the query-category Telegram lane. `resetAdminCache()` also bumps a table-wide generation counter, which an in-flight fetch checks in its `.then` before writing back: on a mismatch it only hands the result to its waiters and never calls `cacheAdminIds`, and the `.catch` likewise skips discarding `pendingAdminChangesDuringFetch`. Otherwise a pre-reset snapshot is poured into the freshly cleared table while that reset discarded the demotions that arrived during the window — the demoted admin stays in the inviter-exemption set for a full `ADMIN_CACHE_TTL_MS`, and everyone they invite skips join verification.
- Join verification has exactly two buttons with independent eligibility. "我是良民" (self-verify) accepts only the pending human's own click: the Worker must derive self-ownership from the trusted `callback_query.from.id === callback_data` target ID rather than a caller-supplied claim. "通过" (approve) accepts only a **non-anonymous administrator of that chat** clicking on someone else's behalf (humans and bots alike); eligibility comes from the Worker-side admin cache (`isChatAdmin`, one `getChatAdministrators` fetch on a cold cache), and when it cannot be determined the click is answered with "try again later" and the record is left untouched. The allowlist boundary (a row in SQLite `permission_list`, or `SUPER_ADMIN_USER_ID`, which is always inside it) plays **no part** in either check: allowlisted members cannot approve anyone, the super administrator can only press "通过" when they are themselves an administrator of that chat, and the target pressing "通过" is always rejected. Inviter exemption likewise recognises only non-anonymous administrators (synchronous cache hit, with `startAdminCheck` re-checking asynchronously on a cold cache); an allowlisted inviter exempts nobody. A click with no record, a terminal record, or a mismatched target can only be answered as failed and must not change the verification record.

  A missing, terminal, or mismatched target may only receive a failure answer and must not mutate verification state.
- Before a terminal timeout/flood removal calls `kickChatMember`, it must query `probeChatMembership`: kick only after confirmed presence, settle silently after confirmed absence, and perform no destructive member action after an inconclusive lookup while retaining the terminal for its existing retry backoff. **The first attempt pays for that lookup too; there is no exemption.** "Kick without banning" in a supergroup maps to `unbanChatMember` without `only_if_banned`, and that call **lifts an existing ban**. A 429 sends that request into the independent kick lane, and a human admin may ban the user while it waits. Before every replay of this form of `unbanChatMember`, the main thread must therefore issue a fresh query-category `getChatMember`: replay only while the target is still present, and cancel with the business outcome `absent` for `left` / `kicked`. An explicit unban carrying `only_if_banned: true` does not use this precondition. Without it, the delayed replay lifts the admin's ban while still reporting `kicked`, allowing the user to rejoin through an invite link.

  "Kick without banning" also requires an exact chat kind: a basic group uses `banChatMember` (which only removes there), while a supergroup uses `unbanChatMember`. The main thread observes `group` / `supergroup` from updates only for chats with `/init enable`, and the first `/init enable` records one observation after it is persisted; unmanaged chats (including an `/init` rejected by the `STATE_MANAGED_CHAT_LIMIT` capacity gate) never enter the mirror, so its size is bounded by the managed-chat count. The whole mirror is replayed before terminal adopt on both initial startup and Worker respawn. When a full process cold start has no mirror entry, the Worker deduplicates `getChat` by chat and bounds in-flight lookups with `VERIFICATION_CHAT_KIND_FETCH_MAX`; a request superseded by a mirror update or chat deactivation still counts against that bound until it settles. A failed lookup, a non-group result, or capacity backpressure must never guess either destructive API: retain the terminal and use its existing backoff. If a mirror update arrives during the lookup, it wins over the stale response.

  A failed terminal removal retries with exponential backoff up to a cap, and the record is never deleted just because retries ran long — deleting it would treat an unprocessed member as done.

  `VERIFICATION_TERMINAL_RETRY_MS` and `VERIFICATION_TERMINAL_RETRY_MAX_MS` bound the backoff interval. After permission is restored, a terminal with process-level attempts remaining retries at its next backoff deadline. An exhausted record keeps its disk snapshot and waits for a full process restart.
- A lockdown fast-kick first enters the `kickPending` state (its snapshot is written ahead to disk so a restart resumes the membership probe and kick; the state object itself and `executionStarted` exist only in Worker memory), whose object identity is the execution token for that batch of irreversible work. After any preliminary `await` such as announcement deletion and immediately before `kickChatMember`, the interpreter must confirm that the entry still holds that exact object; no `await` may separate the check from the API call.

  An authoritative admin exemption, departure, new physical-join record, or chat teardown replaces or deletes the token and must stop the old batch at that check. Set `executionStarted` only when the API request is synchronously issued: an exemption arriving earlier transitions to `exempt`, while one arriving later can only leave a diagnostic. Only a settled request whose token still matches may transition to `kicked` and start its dedupe window at settlement time.

  A dispatcher writing `kicked` must never stand in for a Telegram action that has not happened.

  **Retracting a join count may only target a join that was actually counted**: `kickPending` carries its own `countedJoinAt`, set only for the join where `joinCreatesNewRecord` was true and the caller really did `recordJoin`.

  Someone who genuinely re-applies after being kicked gets a fresh `kickPending`, but that path already has a state and is never counted again; retracting with its `requestedAt` removes the first queue entry equal to that value — and members from one `new_chat_members` batch are processed in the same tick with identical timestamps, so the entry removed would be another, legitimately counted joiner.

  The sliding window then sits one short of the threshold and lockdown never fires, which is exactly what the counter exists to prevent.
- That diagnostic (`logUncancelableKickExemption`) must go through `logger.error`: a Worker only relays error-level log envelopes to the main thread, so `warn` stays in the Worker's ephemeral stdout and never reaches `logs/<day>.json`. It is the only trace that an admin was wrongly removed and needs a manual re-invite; if a post-raid log review cannot see it, that person simply stays out of the chat.
- Each member has exactly one verification-reminder delivery owner with bounded backoff after send failures. At least one of `reminderMessageId` or `replyReminderMessageId` must be populated before timeout may kick the member. If no reminder has landed, timeout only extends the window and retries delivery.

  **That extension must have an end**: once more than `VERIFICATION_REMINDER_UNDELIVERED_MAX_MS` has passed since the join and still nothing has landed, settle it as an ordinary timeout (the removal only kicks, never bans, so the member can rejoin at any time).

  Extending forever leaves one immortal record per joiner — when a chat's `sendMessage` keeps failing (forum General topic closed, bot muted but still able to restrict members) those records sit in the pending table and the main-thread mirror indefinitely and rewrite the day file every 90 seconds. An individual record is bounded (`trackedMessageTimes` keeps only the last minute of timestamps per `JOIN_WINDOW_MS`, and reaching `ANTI_RAID_PER_MINUTE_LIMIT` moves the record to a terminal state); the cost is in their number — one per person who ever joined, never retired.

  **A member's own messages never enter any cleanup set.** A verification record stores `trackedMessageTimes`, a series of timestamps forming **that pending member's own** 60-second window (`JOIN_WINDOW_MS`) whose 46th entry past `ANTI_RAID_PER_MINUTE_LIMIT` moves the record synchronously into `expelling{reason:"flood"}` and kicks — a mechanism independent of the `/flood_control` "15 messages, 3-minute mute" path — and never a member's message id; expulsion deletes only the three traces the bot or Telegram produced itself — `announcementMessageId`, `reminderMessageId`, and `replyReminderMessageId`. That boundary must match what the reminder says: the text promises only that the member will be kicked, never that their messages will be wiped, so deleting them performs a destructive action that was never announced to them, and contradicts the "kick, never ban, leave as little behind as possible" stance of automatic disposal (wiping messages belongs to `/block` and the blocklist fast-kick, which carry `revoke_messages`; see below).

  A current-format snapshot restored without a reminder ID reuses the same owner; state replacement, departure, teardown, and Worker termination all cancel it. This is legitimate business state for an unsent reminder, not a legacy compatibility branch.

- **Asynchronous verification approval checks bind both the verification instance and Worker generation**: `packages/workers/antiRaid/verificationCallbacks.ts` rechecks both before dispatch. Leave/rejoin, adopt, chat deactivation and stop invalidate old results; they only receive an expired callback answer and cannot alter a replacement verification. In-place pending-field updates retain the current check. `VERIFICATION_CALLBACK_CHECK_MAX` and `VERIFICATION_CALLBACK_REPLY_MAX` each allow 10,000 in-flight operations, owned by `packages/cache/workers/antiRaid/verificationCallbacks.ts`. A full check budget only attempts the existing retry-later answer; a full answer budget creates no request or waiter. Stop/adopt do not release unsettled slots early. Duplex cancellation drains them, and an isolate restart reconstructs zero counters. All verification answers use `answerVerificationCallback`.

- **Comment correlation window**: `packages/workers/antiRaid/recentComments.ts` accepts only observations at least as recent as the existing same-key entry. Reads and wall-clock sweeps retain only `0 <= now - observedAt < COMMENT_JOIN_CORRELATE_MS`. Capacity sweeps use the observation time and allow asynchronous confirmation to reorder different keys; newer observations are not discarded as clock rollback. Capacity eviction follows insertion order, without sorting by observedAt.

- A cold linked-discussion confirmation has exactly one mutable owner per `chatId:userId`, with global backpressure at `THREAD_COMMENT_CONFIRMATION_MAX` and bounded settlement at `LINKED_CHANNEL_FETCH_TIMEOUT_MS`; saturation keeps the ordinary fail-closed verification semantics. Once chat teardown, adopt, or stop removes an owner, a late callback must fail its object-identity check before writing a recent comment.

  If a message covered by that owner synchronously moved the same pending state into a flood terminal, confirmed linkage may retract that terminal and publish its tombstone only while `executionStarted !== true`; irreversible disposal is never presented as cancellable after it starts.
- Settlement of a `kickPending` Telegram request is not proof that the member was kicked. `kickSettled` is allowed only after `kickChatMemberWithOutcome === "kicked"` or an authoritative follow-up membership probe confirms absence. `forbidden` and `failed` clear that attempt's `executionStarted`, retain the exact token, and enter bounded terminal backoff. If exemption, teardown, or a newer physical join replaces the state, late results and timers must stop.

### Flood Muting and the Bot's Own Permission Cache

This section covers [counting and enforcement boundaries](#counting-and-enforcement-boundaries), [verdict-time suppression and concurrency safety](#verdict-time-suppression-and-concurrency-safety), [permission gates before enforcement](#permission-gates-before-enforcement), and [the bot's own permission mirror](#the-bots-own-permission-mirror).

#### Counting and enforcement boundaries

- **Flood counting and enforcement both live in the Anti-Raid Worker; the main thread only applies synchronous gates and makes one best-effort `post`.** The feature defaults off per chat and enters counting only when `ChatState.isFloodControlEnabled === true`. Any identity holding `isCanControllFloodControlPermission` (the super administrator always does) may persistently change it through `/flood_control enable|disable`; disabling also clears that chat's live windows. When one member posts `FLOOD_MESSAGE_LIMIT` messages (currently 15) within one minute in one **supergroup**, they are muted for `FLOOD_MUTE_DURATION_MS` (currently 3 minutes).

  Supergroups only, because `restrictChatMember` is defined to work only there; counting in a basic group merely wastes memory — filling a whole window buys one request that is guaranteed to fail plus one misleading error line.

  Before allocating a candidate, the main-thread half (`packages/antiRaid/floodControl.ts`) checks the per-chat switch, supergroup type, whether the speaker is a real user, and whether that sender has the flood-control bypass. Channel identities and anonymous administrators have no member identity to mute — `restrictChatMember` only accepts real users, and Telegram does not reveal who is behind the disguise. The bypass depends on one permission only: `isCanBypassFloodControl`. It defaults to `true` on an allowlist entry, and the identity participates in counting only when that permission is explicitly `false`; `SUPER_ADMIN_USER_ID` always holds it and therefore always bypasses, so the decision point no longer compares the identity separately.

  It then posts a `floodCandidate`. Like ad detection, delivery uses a plain `post` rather than `postAntiRaidDurably`: the window lives and dies with the isolate, and a cross-thread barrier per group message buys no recovery. Join/leave service messages are nobody's "utterance", so the entry point sits after those two branches.

  The window is keyed by "chat + member" in `packages/cache/workers/antiRaid/flood.ts`; entry count is bounded by `FLOOD_WINDOW_MAX_MEMBERS` with LRU eviction, and entries idle for a full window are dropped by the Worker's shared sweep tick — with LRU alone, a chat that was once busy and has long gone quiet would hold its slot and crowd out genuinely active ones.

  Unmuting is Telegram's own `until_date` expiry, so the Worker arms no restore timer; this disposal writes no persisted state and needs no adopt on Worker respawn.

#### Verdict-time suppression and concurrency safety

- **The suppression window is claimed at the moment of the verdict, not after the mute lands.** The mailbox handler is synchronous, so a burst can fill the next window before the first round trip returns; waiting for the result would mute the same person twice and post two notices.

  Deterministic outcomes (mute succeeded, target is an administrator, the bot lacks the restrict right) **keep** the suppression — re-judging buys no new answer, only a repeated request or the same line pushed into `logs/` once per filled window. Transient failures (admin identity could not be confirmed, the mute request failed or threw) **roll it back** to 0 so the next filled window retries.

  Both the rollback and the alignment to the real mute deadline must first re-check, by state-object identity, that the entry is still the one that started this verdict: across the `await` it may have been evicted by LRU or cleared by `deactivateChat`.

  **When that re-check fails, the whole disposal must abort, not merely the write-back**: `/init disable` and losing management both run `deactivateChat → clearChatFloodWindows`, dropping every window of that chat, while the bot most likely remains a Telegram administrator there — it can still mute and still speak.

  Acting anyway means silencing a member for three minutes in a chat this process no longer manages and then calling them out publicly, with no unmute timer and nobody left accountable for it (same shape as the ad verdict's `pendingAdBundle(chatId, senderId) !== bundle` and the verification disposal's `stillCurrent`). The cost is one missed flood verdict when an LRU eviction happens to land inside that round trip, exactly the trade-off `FLOOD_WINDOW_MAX_MEMBERS` already spells out.

  Clearing the whole window on a hit complements this: even if suppression is rolled back, stale timestamps cannot immediately produce another hit.

#### Permission gates before enforcement

- **Two gates before acting, neither optional.** Read the bot's own permission bits first (next bullet), then confirm through the admin cache the join guard already keeps warm (`freshAdminIds`, falling back to `fetchAdminIds` when cold) that the target is not a chat administrator, and **never act when that cannot be confirmed**. That tri-state verdict (`true` = is an administrator / `false` = confirmed not / `undefined` = could not tell) is a permission boundary and may have only one implementation, living beside the two fetchers as `isChatAdmin` in `workers/antiRaid/adminCache.ts`; with a copy each in flood muting and ad disposal, a later change to the fallback semantics (treating a 403 as "not an administrator", say) reaches only one of them and the two pipelines start disagreeing about who is exempt. The ad side's "a channel alias is immediately `false`" is its own precondition and stays at the call site, out of the shared verdict.

  The permission gate is three-valued, and **"not observed" is not "observed to be absent"**: only a confirmed absence gives up on the spot (keeping the suppression); an unobserved chat proceeds and lets Telegram's answer decide — the mirror may simply not have arrived yet (one 429 on the main thread's on-demand probe backs it off for minutes), and letting a flood through for those minutes while logging a groundless "no permission" is far worse than one request that may fail.

  The mute request therefore reports three outcomes too (`muteChatMemberWithOutcome`, shaped like `banChatMemberWithOutcome`): `forbidden` is Telegram's explicit refusal (missing `can_restrict_members`, or a target that really is an administrator the cache happened to miss) — keep the suppression, do not retry, and let the shared error boundary record Telegram's own wording; `failed` is throttling or a network hiccup — roll the suppression back and wait for the next filled window.

  Those two buckets are what closes the "mirror has not arrived" fallback: without them, a chat where the bot genuinely lacks the right would buy one doomed request per filled window.

  They cannot be collapsed into "just try it": Telegram answers both "the bot lacks the right" and "the target is an administrator" with the same 400 `not enough rights`, so acting blind only pushes a misleading line into `logs/` that sends operators after a permission problem that does not exist — and muting the owner for three minutes costs far more than letting one flood through (the next message re-enters counting).

  The mute request hands `FLOOD_MUTE_DISPATCH_TIMEOUT_MS` to the shared wrapper as its `dispatchTimeoutMs`, which composes it with the shutdown signal (same boundary as `/mute`; see the dispatch-deadline entry above): `until_date` is computed before the request is queued, and a request that hits 429 may still wait in the independent `restrict` retry lane; if it reaches Telegram less than 30 seconds before that deadline, the Bot API treats it as a **permanent** restriction — and this module schedules no unmute timer and persists no state, so the member is silenced forever until a human intervenes.

  Timing out abandons the mute instead (suppression rolls back, the next filled window retries), which costs far less.

  Send the group notice only after a successful mute. The main thread registers its 30-second deletion in the successful-send `onSent` boundary. Timer expiry and shutdown `flushPendingMessageDeletions` share the deletion owner and in-flight set, so drain waits for started deletions. When shutdown cashes deletions in early, `flushPendingMessageDeletions` groups all pending entries by client and chat and calls `deleteMessages` with at most `TELEGRAM_DELETE_MESSAGES_BATCH_MAX` (100) IDs per batch; normal expiry still deletes messages one at a time.

  The timer remains `unref()` and never keeps the process alive by itself; orderly shutdown cashes it in through that flush. A hard crash still loses this in-memory responsibility table and may leave a notice behind, an explicit trade-off of not adding a durable deletion queue.

  The notice carries a dispatch deadline of its own (`FLOOD_NOTICE_DISPATCH_TIMEOUT_MS`). Notices queue in this chat's lane of the send scheduler while verification kicks use the independent `kick` 429 category, so neither freezes the other; an expired notice is nevertheless no longer useful and must not prolong shutdown drain.

  The bot's own chatter must not push functional messages past their window; dropping an overdue notice also frees its place in this chat's send lane, which bounds how long it can hold up a verification reminder.

  The whole disposal is registered in the Worker's in-flight task set and awaited by the shutdown drain, **but every request of this kind must subscribe to the shutdown cancellation signal** (`antiRaidDispatchSignal`; the authoritative contract lives in `packages/cache/workers/antiRaid/tasks.ts`): the drain budget is the seconds-scale `ANTI_RAID_BARRIER_TIMEOUT_MS`, while a mute may wait in the `restrict` retry lane for `FLOOD_MUTE_DISPATCH_TIMEOUT_MS` (minutes) after a 429.

  When shutdown lands inside that queueing window the drain never settles, so the lifecycle refuses to confirm the Telegram offset and exits non-zero — after the restart that update is replayed (verification kicks and notices already emitted by it may repeat) and systemd reports a failed unit.

  The drain therefore aborts those queued requests in place and starts no new disposal; muting is best-effort anyway (Telegram lifts it by `until_date`), so losing one is not a breach of a safety boundary — the same reasoning that keeps ad verdict batches out of this set entirely.

  **This cancellation signal does not cover the requests the drain itself must send**: the notice flush has to go out during shutdown, so queued work is aborted first to settle the cancelled lifecycle before the drain assumes the remaining cleanup responsibility.

#### The bot's own permission mirror

- **The bot's own permission bits are owned by the main thread and mirrored to the Worker on change; "not observed" must never be folded into "observed to be absent".** The snapshot lives in `ChatState.botPermissions` (every permission bit of the pinned Bot API version, persisted along with the rest of the chat state); the owner is `packages/infra/botAdmin.ts`, and only chats that have been `/init enable`d get an entry (otherwise merely being added to a pile of groups grows a table out of nothing).

  Observation can only happen on the main thread — the `my_chat_member` update (Telegram delivers it both when the bot is promoted/demoted **and when an administrator merely toggles one of its rights**) and the on-demand `getChatMember` probe — while kicking, muting and deleting all execute in the Worker.

  Every confirmation or invalidation is therefore broadcast as one `botPermissionsChanged` through the reverse-registered single slot in `packages/cache/main/botAdmin.ts` (infra must not statically depend on Anti-Raid business modules), and the Worker keeps a read-only snapshot (`packages/cache/workers/antiRaid/botPermissions.ts`).

  **Persistence and broadcast dedupe on different keys**: persistence compares every permission bit (the snapshot itself must be stored accurately), while the broadcast compares only the two bits the downstream actually reads, `canRestrictMembers` and `canDeleteMessages` (the field set lives in `BOT_ACTION_PERMISSION_KEYS`, `packages/consts/botAdmin.ts`). Telegram delivers `my_chat_member` for *any* change to the bot's own membership record, so deduping the broadcast on the full table would push a byte-for-byte identical message into the Worker mailbox every time somebody toggles a right this repository never reads.

  Receiving somebody else's `chat_member` update proves "I am an administrator" but says nothing about the individual rights, so **it must never write a partial "is an administrator" on that basis alone** — doing so would permanently mark a fully privileged chat as unable to act. When the snapshot is missing, or contradicts that fact (it says "not an administrator"), this path probes one complete `ChatMember` and writes it as a whole; that probe must pass the backoff gate and must not be awaited (see below).

  Demotion, removal from the chat and an `/init` toggle all clear the entry immediately, broadcast "unknown", and invalidate any in-flight probe. **Clearing must reach disk as well**: the snapshot is a persisted field, so clearing memory alone lets a restart read back the very snapshot that was just ruled stale — and the fact that it is "not undefined" is enough to make every later check bail out early, leaving that chat treated as unprivileged until the next membership change heals it. Invalidation works by generation, and **the presence of the generation entry is itself the only signal for "a probe is in flight", so it must be claimed synchronously before the request goes out** — otherwise an invalidation arriving in that narrow window is lost and the stale identity is written back.

  A failed probe, a result voided by invalidation, and a result that is not an administrator at all all yield `undefined`. The main thread treats that as "this action cannot be done right now"; the Worker only reports the three states faithfully and lets each disposal decide what the unknown bucket means (flood muting's choice is in the previous bullet).

  **The mirror must stay three-valued and must never be collapsed into a boolean**: collapsed, "confirmed to lack the right" and "not yet known" become indistinguishable, and those two call for opposite handling.

  **Worker respawn and process startup must replay the whole table** (`replayBotPermissions`, ordered before adopt): the new isolate's table is empty, and an empty table means, by contract, that nothing can be done.

  **Every entry point that probes because the snapshot is missing must pass the same backoff gate** (`BOT_PERMISSION_PROBE_RETRY_MS`; today the only one is the identity observation on the join flood, `markBotAdminObserved`): when the snapshot says administrator but reality disagrees, or `getChatMember` keeps failing, `botChatPermissionsIn` by contract records nothing, and without the backoff every new member in such a chat would buy another probe that is guaranteed to fail.

  **This probe must not be awaited**: it costs one Telegram round trip plus one durable write, and the update runner is strictly serial (no further `getUpdates` until the current update finishes), so awaiting it lets the first `chat_member` of a raid on a cold process stall the whole ingress. Getting the snapshot one update later is the same situation as not getting it this round — a backoff hit yields nothing either — and reading "unknown" downstream drops no disposal: every Worker-side consumer short-circuits only on a **confirmed `false`**.

  This cache backs the check-before-acting rule for every destructive action: flood muting reads `canRestrictMembers`, while ad-disposal bulk deletes, channel-alias stragglers and the trace cleanup of a verification-timeout expel read `canDeleteMessages`. Deletes and kicks now use separate 429 categories, but requests known to fail still waste network, logging, and shutdown budget. Only a confirmed `false` blocks; `undefined` still sends the request (same three-valued rule as above).

  **When a confirmed absence skips the deletes, the notice must no longer assert that the traces were cleaned up** — those messages are still sitting in the chat for everyone to see.

  Conversely, **"the message was already gone" is not a failed delete**: an administrator (or the member) hand-deleting it before the timeout, someone else clearing the join announcement, or a message older than 48 hours all come back as a 400 from `deleteMessage`, and folding those into failures makes a fully privileged bot send an administrator off to audit a perfectly correct `can_delete_messages`.

  Deletion therefore reports an outcome rather than a boolean (`deleteMessageWithOutcome`: `deleted` / `gone` / `forbidden` / `failed`, where `gone` counts as cleaned up just like `deleted`); only a genuine permission refusal from Telegram may call out the administrator, and any other failure must state how many of how many were missed — an all-or-nothing boolean flips on the first failure, which makes "not a single message could be deleted" a lie of its own.

  The ad notice drops the deletion claim entirely: the deletes run on the judging thread, after the event is published back, so the main thread never learns whether they succeeded. the Anti-Raid Worker separately keeps a **chat-administrator** cache (`workers/antiRaid/adminCache.ts`). The two describe different subjects, are not shared, and do not substitute for each other.

### Identity Resolution and Runtime Teardown

- The sender-username cache maintains both normalized username → identity and sender ID → current username. Rename, username removal, reassignment, and capacity eviction atomically update both directions under one owner; the resolver rejects inconsistent aliases.
- An anonymous administrator remains exempt as an administrator, but cannot grant inherited administrator-inviter exemption because the inviter is not attributable to a specific account.

  When an anonymous administrator speaks as the current group, visible-sender resolution must retain that group identity for copy and avatar crawling; destructive member operations must reject the current group identity as a user target. **`/block … enable` and `/block … disable` additionally accept a bare user id** (`USER_ID_ARG_PATTERN`, and it must also pass `Number.isSafeInteger`): what they act on is an id in the first place, whereas a released username can be re-registered by somebody else - the same concern as the live-lookup rule for `/icon steal`, only these two commands are irreversible, so the cost is higher.

  A cache miss on the id path is **not a failure** (`resolveIdTarget` degrades to a minimal id-only identity) and affects only the label in the reply. Bare ids are opt-in per command (`acceptUserId`) rather than global: `/copy` and the CJK action commands need an identity with a name and an avatar, and an unseen bare id would only reproduce an empty shell.

  **When a reply target and an argument are both present and point at different people, the command must fail loudly and must never silently pick one**: the scenario the id path exists for is precisely "act on an id somebody else posted" — an administrator sees "please ban 123456789" in the chat, replies to that message and sends `/block 123456789`.

  Silently preferring the reply target permanently blocklists and `revoke_messages`-bans the colleague who posted the id, in every managed chat, while the receipt shows that colleague's name and reads like a successful confirmation. An argument that resolves to no target is reported as the same conflict rather than "that is not a valid username": the latter reads as "the argument was ignored and the reply target won". Both pointing at the same id is a harmless duplicate and passes through.
- A bare **chat** id (the negative id of a channel or group, `CHAT_ID_ARG_PATTERN`) is a separate switch opened only by `/gag`, `/ungag`, `/block disable`, `/permission`, and `/white` (`acceptChatId`). The first two create or release a reversible temporary message-deletion state, the third is a recovery operation, and the last two manage allowlist configuration that admits channel identities; no other command may treat a negative chat id as an ordinary user target.

  Channel-vest ids reach the blocklist on their own - through `/block` on a reply to a channel message, and through ad detection hitting a `sender_chat` - yet removing one previously required either replying to its message or naming its `@username`: the former is gone once ad detection deletes the message, and the latter needs a public username still present in the cache under `USER_CACHE_MAX`.

  An entry with both paths cut off would stay on the list forever. `/block` must keep refusing negative ids: a mispasted chat id there turns the disposal into a ban of a whole chat identity, and that command is irreversible, whereas `/block disable` is the recovery direction and a wrong target costs at most one no-op unban.

  **Every negative id carries `isChannel`** (stamped onto the minimal identity by `resolveIdTarget`, the same sign-based dispatch as `workers/antiRaid/blocklistEffects.ts`): `/block disable` uses it to choose `unbanChatSenderChat` over `unbanChatMemberIfBanned`, and missing it makes the unban fail into `failedCount`, turning the reply into a false report about a target that was never touched.
- The authoritative gag table belongs to the main thread and stores a small target list per chat, with a hard global cap of five. One identity in one chat occupies exactly one slot throughout `starting`, `active`, and `ending`. Every target first gets a public status in the group. A regular user's public status has no button and is followed by a button-bearing temporary entry restricted by `ephemeral_message_parameters.receiver_user_id` and visible only to that target; a channel target has no receiving user and therefore keeps only its button-bearing public status. A session becomes `active` and installs its `unref` timer only after every required message succeeds and both the public `message_id` and, for a regular user, the validated `ephemeral_message_id` have been synchronously recorded. If the second send fails, the already-landed public status must be deleted before the reservation is released. Timeout, targeted `/ungag`, and chat teardown synchronously claim `ending` and clear the timer before invoking the matching delete APIs in sequence. The slot may be released by object identity only after every deletion returns `deleted/gone` and any required release receipt has settled. `failed/forbidden` retains the ending owner and uses finite, `unref` backoff retries; after they are exhausted, `/ungag`, chat teardown, or process drain can retry again. Stale cleanup therefore cannot delete or interleave with a new session for the same target, and cleanup debt remains bounded by the same five-slot ceiling. Every start-state message belongs to the gag session and never enters the fixed 30-second command-text cleanup; the release receipt still uses that unified command boundary. The gag owner must quiesce and drain before the Telegram outbound gate; unfinished cleanup withholds the final offset and instance-lock release.

  **The session owner controls all gag entry refreshes.** `commands/gag/counter.ts` updates message counts in place with a threshold of seven. It allocates no due array below the threshold or while that session already has a `speakNoticeRefreshTask`. `commands/gag/refresh.ts` claims one task synchronously for each ready session and registers it in `gagBackgroundTasks`. Sessions start independently; the common Telegram boundary controls outbound concurrency and backpressure. Message thresholds, topic moves, timed resends, and speech after inactivity must not attach more waiters to an existing task. At most five sessions each own one refresh task, regardless of incoming message backlog.

  A regular user's session arms one `speakNoticeRefreshTimer` for 30 seconds after activation and after each refresh settles, always with `unref`. Public channel entries have no such timer. Scheduling requires the current unexpired `active` owner, an accepting runtime, and more than 30 seconds remaining. Starting a refresh, ending, quiescing, and test reset cancel it. The exclusive task first cleans the `retired` slot, then sends a new entry. `onSent` records `pending` synchronously; commit switches the current entry and topic, resets the count, and then deletes the old entry. Failed sends or retired-entry cleanup retain all owned ids and retry on a later threshold or timer. Before sending and after send settlement, the task checks ownership, expiry, and quiescing again. Ending waits for the task before taking over every id. Refresh never extends expiry or makes the update loop wait for network maintenance. `test/commands/gag.refresh.test.ts`, included in `test:fault-injection`, covers quiet groups for the full duration, thresholds, failures, expiry races, shutdown, and blocked refreshes at full capacity.

  **Speech after inactivity:** activation initializes `lastTargetMessageAt`, and only the target's messages in that chat update it. `refreshGagSpeakNoticeOnSpeech` compares the previous timestamp before storing the current time. When a user speaks after at least 45 seconds of silence, it immediately requests the same refresh task. Other senders, 30-second resends, and seven-message refreshes never change this timestamp. This refresh cancels the old 30-second timer and rearms it after settlement; if a task is already pending, that task handles the reset when it settles. Speech in the same topic below the idle threshold only updates the timestamp and does not reset the timer. Channels keep message-count refreshes and topic moves only. `test/commands/gag.speech.test.ts`, included in `test:fault-injection`, verifies timing boundaries, independent counts, message ownership, failures, blocked tasks, and expiry cleanup.

  Gag and fortune use a strictly exclusive inline-routing protocol. An ordinary `@bot` query without the `gag:` prefix must skip gag and go only to fortune, even when the querying user is currently gagged. User and channel buttons both prefill only `gag:<target Telegram id> ` (a positive user id or negative channel id). The scope before the first space is exactly that canonical safe integer: MD5 or any other digest, random tokens, chat ids, and all other metadata are forbidden. `ParsedGagInlineQuery` may not grow such scope fields; `GagSession.chatId` stores only the authoritative session chat established at command entry and must not derive digest/token side-channel authentication state. Every query carrying `gag:` terminates dispatch in the gag entry; invalid, stale, or user-identity-mismatched input receives an empty answer and must never fall back to fortune. The source text registered per speaking identity after answering (`recordInlineResultSources`, shared by every inline feature) is **only a source of text for ad classification**, never a credential for identity, chat binding, or validity: landing checks still rely solely on the marker, `from.id`/`sender_chat.id`, and `message.chat.id`, and no path may use that registration to admit or reject a message.

  Telegram's `InlineQuery` exposes the clicking user and query, but about the containing chat it provides only the chat type, not the current concrete `chat.id`; there is also no bot-cancellable hook between choosing and sending a result. A token, digest, or claimed chat id therefore cannot prove which chat owns the input field and must not be reintroduced as “stronger validation.” The normal button only uses `switch_inline_query_current_chat` to stay in the session chat. User queries additionally match `inline_query.from.id`; channel queries can only select candidates by the negative target id and use a generic title that does not reveal the group name.

  The generated result's exact `text_link` marker is fixed as `<target profile>#<session chat id>`: the profile binds the user/channel identity and the fragment binds the session chat. Result URLs are public to end users, so the fragment is validation payload, not a secret or authorization token. After landing, the current bot, tool prefix, full marker, active session, actual `from.id`/`sender_chat.id`, and `message.chat.id` must all match; every mismatch and every expired or cross-chat result is deleted and terminates downstream processing.
- The `/icon steal` t.me profile-scrape fallback **only accepts the username returned by a live `getChat(targetId)`**; the one carried in the caller's context must never short-circuit that lookup. That username comes from a `reply_to_message` (possibly months old) or from the identity cache, while a released Telegram username can be re-registered by anyone; the page identity check during scraping can only prove "this page belongs to @name", never "@name still points at targetId".

  Short-circuiting therefore installs the **current handle holder's** avatar as the bot's avatar while the success notice still names the original target. The provided value is a diagnostic hint for the log only.
- The eight fixed callbacks for chat-runtime teardown (`copy`, `translate`, `gag`, `qa`, `wed`, `aiChat`, `antiRaid`, `joinLog`) live in `packages/cache/main/chatTeardown.ts`. Higher-level domains register them in reverse through the business-independent leaf `packages/infra/chatTeardownRegistry.ts`. `packages/infra/chatTeardown.ts` only orchestrates cleanup; `packages/infra/botAdmin.ts` depends on that orchestration boundary and must not statically depend on `commands/`, AI, or Anti-Raid business modules.

  **The reason decides whether data is deleted, and exactly one place decides it.** `ChatTeardownReason` has three values: `explicitDisable` (`/init disable`), `departed` (the bot was removed from the group), and `lostAuthority` (still in the group, merely demoted from admin). The first two mean "this chat is no longer managed", so its `/wed` member set, join logs, Q&A rows, and `chat_states` row are all deleted; `lostAuthority` only stops the runtime and leaves every one of those in place, ready to work again the moment the rights come back. Owners must call `purgesChatData` in `packages/libs/chatTeardown.ts` rather than each writing its own `reason === "..."`: when a new data-deleting reason arrives, missing one owner silently leaves behind a copy of chat data that should have been erased. Two carve-outs have their own reasons — AI memory is deleted by the aiChat owner on every teardown (same semantics as `/ai_chat disable`), while leftover messages such as verification buttons are deleted only under `explicitDisable`, because under `departed` the bot is already out of the group and cannot issue a single outbound call.

  **Dispatch lists must not be duplicated at call sites.** `teardownChatRuntime` iterates `CHAT_TEARDOWN_ORDER` in `packages/consts/chatTeardown.ts`, a constant whose type forces it to cover every `ChatRuntimeOwner`; omitting any owner fails to compile. Each teardown synchronously starts every owner in that order before it waits for their asynchronous settlement together.
- The membership probe is itself a new asynchronous boundary: after `probeChatMembership` reports presence and before `kickChatMember` is called, the terminal state must still be the exact object that initiated the lookup, with no further `await` between that check and the API invocation. Otherwise a stale lookup can let an old removal cancelled by teardown, management disablement, or state replacement kick a member who no longer belongs to that terminal action.
- `/block` must not substitute a cached “previously confirmed kick” for a live membership lookup. `/block disable`, external administrator actions, and rejoining can all invalidate historical outcomes, while commands from different chat lanes may interleave. Every invocation must call `isChatMember` again and must always resend `banChatMember` so Telegram applies `revoke_messages`; `/block disable` therefore maintains no command-side membership-outcome cache.

### `/wed` Member Persistence and Interaction

- The daily review is triggered only by the Disk I/O Worker's single native Bun `cron` at 00:00 in the time zone configured in `bot.json`, through a `midnightMaintenance` notification; the main thread creates no separate cron. `commands/wed/memberReview.ts` traverses all restored authoritative member sets, including groups without interaction-cache entries. It holds one group snapshot of at most 150,000 IDs; IDs added to that set after its snapshot wait for the next round. All groups share serial queries with at least 200 milliseconds between starts and a 30-second timeout per query; slow requests do not cause catch-up bursts. Only confirmed absence calls `removeWedMember` to mutate the original Set and mark it dirty; a 400 `PARTICIPANT_ID_INVALID` from Telegram also counts as absence and is not logged as an API error. Other failed or canceled queries retain members, and speech, present `chat_member` updates, or join service messages observed during the query can veto a late absence result. Startup retains only the latest pending midnight date and admits it after Bot handshake and recovery succeed. Dates are deduplicated; a round that crosses midnight continues without overlapping another round. Worker reconstruction does not replay midnight notifications; process restart clears progress and waits for the next notification. Reviews join `wedRuntime.tasks`: quiesce cancels waits and queries, and drain waits for settlement before delivering final member sets through the existing path. Replies for an old set must not mutate a newly adopted set.

  If a group is disabled or its member set is replaced during review, only that group's inner loop ends; subsequent groups are still reviewed. Only cancellation of the whole round ends the traversal. When Telegram rejects member queries for the group itself (403, or 400 `CHAT_ADMIN_REQUIRED`; see `isChatMemberQueryDenied` in `infra/telegram/actions/core.ts`), every other query in that group would fail the same way: the group's round issues only that one query, logs one API error, and ends, keeping all members.

  **Departures are only reliably detected when the bot is a group administrator, and drawing a member who already left is the defined behavior otherwise.** The Bot API guarantees `getChatMember` for other users only when the bot is an administrator, and `chat_member` updates are delivered only to administrator bots. `left_chat_member` service messages reach every bot regardless of privacy mode, but Telegram may not generate them in larger supergroups or when the member list is hidden, and a deleted account produces no signal at all. The `getChat(userId)` used by the draw returns only the user's private-chat profile and says nothing about group membership. So in a group where the bot is not an administrator, the daily review ends the group on its first query because of the group-level rejection and removes nobody; `left_chat_member` is the only cleanup path, departed members whose message never arrived can stay in the set and be drawn while `getChat` remains accessible. The draw path performs no presence check and never calls `getChatMember`, and the set has no speech-based expiry. For groups that need reliable cleanup, the deployer grants the bot administrator rights, after which `chat_member` updates and the daily review take effect.
- Commands and callbacks sit behind the shared `/init` gate. Adding members also requires `isInitEnabled === true`; the first `/init` exception cannot populate candidates early. A rejected update may still remove a departed ID from an existing set, without creating group state or admitting business handlers.
- `packages/cache/main/wedMembers.ts` owns authoritative membership. Each group reuses one long-lived `Set<number>` capped at 150,000 IDs; full sets retain existing members and reject new IDs until departures free space. `packages/cache/main/wed.ts` owns interaction state, in-flight avatar probes, and the executor, with one session per user per group and at most 512 sessions per group. The interaction table is a plain `Map` and can only hold groups that already have a member set. The authoritative member table and startup file validation are limited by `STATE_MANAGED_CHAT_LIMIT` (25) and reject new groups at capacity, and chat teardown removes the interaction before clearing the member set, so interactions are also bounded by 25 groups. Neither table evicts. Channel senders, reply targets, forwarded origins, automatic forwards, and anonymous group identities do not add candidates. Ordinary speech performs synchronous set lookups, actual additions, and dirty marking; only an in-flight avatar probe also records the group where that ID spoke, without temporary sets, candidate snapshots, or cross-thread messages. Draw candidate arrays are created only for commands and change-button operations.
- Only an actual addition or deletion increments the revision and change count and marks the group dirty. Repeated speech, rejected additions at capacity, and absent deletions are silent. The member owner uses the shared DiskIO thresholds of `FLUSH_MAX_ENTRIES` (256) changes or `FLUSH_INTERVAL_MS` (30 seconds) from the first unsubmitted change; reaching the count schedules an earlier asynchronous batch. Only dirty groups produce final arrays. DiskIO reuses the shared dirty flush and temporary-file, fsync, and rename boundary to replace `memory/wed/<chatId>.json` atomically. Successful writes release pending arrays; failed writes retain each group's latest snapshot for retry. On Worker reconstruction, main replays pending deletes and final member sets. Recovery filters only older operations already in the bounded FIFO for that chat at replay time; it does not compare revision numbers across lifecycles, and later operations continue in order.

  **Whole-group deletion keeps a separate pending responsibility.** After removing `wedMemberStates`, `purgeWedMembers` registers a process-unique deletion number in `pendingWedMemberDeletes`, then dispatches and waits for the domain flush. Rejected delivery, failed flush, and Worker reconstruction retain that responsibility for repeated purge, the existing retry timer, or recovery replay. Only a matching `wedMembersDeletedPersisted` receipt or that purge’s successful domain flush releases it; late old receipts and flushes cannot settle a newer deletion. DiskIO deletion cancels the old snapshot and immediately attempts durable unlink, retrying failures with the existing timer. A new snapshot cancels the old pending delete, so only the latest operation per chat owns retry responsibility. Re-enabling while deletion is pending takes ownership with an empty member set and a pending empty snapshot, without restoring old candidates. Active pools and pending deletes together are capped at `STATE_MANAGED_CHAT_LIMIT` (25); capacity rejects new chats while reopening the same chat uses no extra slot.
- The read-only startup gate checks canonical negative-integer group filenames, unique positive safe-integer user IDs, the 150,000-member limit, and the group-count limit. Any invalid input refuses startup and leaves files unchanged. Missing directories or files mean no records and are created as needed. Sets built during validation are copied through the Worker message and adopted directly by the main thread before Telegram client initialization; reads and draws never reconstruct them.
- The only candidate source is the `memory/wed` member ID set: a drawn ID goes straight to `readCurrentAvatar`, and the identity that the caption and the public-avatar fallback both need comes from the private-chat profile returned by the `getChat` call that avatar read makes anyway. No `getChatMember` is issued, so drawing needs neither administrator rights nor an extra request; a candidate that `getChat` does not resolve to a private user counts as having no usable avatar. Presence is not judged, bots are not filtered, and only an explicitly inaccessible bare user ID is removed during a draw — bots are kept out on the ingestion side, departed members are cleaned up by departure updates and the daily review, and the whole set is deleted by teardown when the chat stops being managed. `readCurrentAvatar` returns four states: confirmed unusable avatars and inaccessible private chats consume the eight-candidate budget per draw, while unfinished avatar queries do not count and abandon the draw once three of them accumulate. Changing excludes the current target. Both names in the caption use user-mention entities. Candidate queries, avatar downloads, and photo sends/edits share a 30-second request budget plus update and session cancellation. Image bytes never enter sessions, files, or the database. Downloads reuse the Telegram download gate, bounded reads, and public-asset domain validation, without invoking avatar-setting APIs.
- When `getChat` for a positive bare user ID explicitly returns 400 `Bad Request: chat not found`, drawing removes that ID from every managed group's candidate set. This only marks the main-thread sets dirty; the existing 30-second / 256-change batch submits the snapshots asynchronously, and normal shutdown flushes them. A group that observes actual speech from the ID during the query keeps that candidate; later speech can add the ID back to its group. Missing avatars, other errors, cancellation, and results arriving after chat teardown do not trigger this cleanup.
- `commands/wed/dispatch.ts` releases the update after admission. `runtime.ts` reuses `createPrioritizedBoundedTaskRunner`: commands and buttons share 32 global active slots and 512 FIFO waiting slots. Active slots cover the entire interaction, including outbound waits; waiting operations do not prefetch images. Each operation restores its admission-time update cancellation context and adds the runtime stop signal, without inheriting the preceding task's context. Telegram sends, queries, edits, and deletions use the existing outbound gate and category-specific 429 queue.
- `sendWedResult` in `commands/wed/messages.ts` is the only photo-send boundary, exempt from fixed-delay deletion. The avatar source lives only for the current operation. Match the current `ChatPhoto.big_file_unique_id` against sizes in the first 100 user photos and reuse the matching `PhotoSize.file_id`; never send a download-only ChatPhoto ID or assume the first historical photo is current. Missing matches retain current-photo downloads and the web fallback, and photo-list queries follow the shared outbound and cancellation boundaries. The successful response synchronously records message ID, target ID, and self-sent identity before propagating update cancellation. Target and confirmation state change only after a successful edit. Buttons bind the chat, message, caller, and current target; queued clicks for an earlier target must be rejected.
- Commands accept only personal accounts; channel and anonymous group senders are rejected before entering the interaction executor. Buttons require positive user IDs for both caller and target, and only the original caller may operate them. Message and target validity are checked again after leaving the queue.
- `commands/wed/chats.ts` centralizes interaction creation and session cleanup. Chat teardown synchronously detaches interaction state and cancels queued operations and sessions, then deletes the results that were idle when cleanup began in `deleteMessages`-sized batches, forgetting a batch's message ids only when the whole batch succeeds; when the bot has left the chat (`departed`) it sends no deletions and just forgets every result's message id. Whether the long-lived member set survives depends only on the teardown reason: `lostAuthority` keeps it, while `explicitDisable` and `departed` delete it through `purgeWedMembers` together with `memory/wed/<chatId>.json`. **That deletion is not conditional on the group still being in the interaction table** — a group with no interaction in this process must have its pool erased just the same. Busy operations clean up late results in their own `finally` and are not deleted again if they become idle while cleanup waits; once the bot has left the chat, a redraw in progress likewise stops deleting the old result it replaces. Buttons expire after teardown, and a newly created interaction for the same group reuses its member set. Ordinary removal failures retain sessions for retry, and Telegram deletion failures use the shared error boundary. Shutdown closes admission, drains accepted tasks, submits dirty member snapshots, and finally confirms writes through DiskIO flush. Task timeouts or delivery failures block final-offset acknowledgement and instance-lock release. This owner drains before unified delayed deletion and Telegram outbound. Worker crashes preserve the main-thread sets; process restarts restore members but not sessions, and old buttons ask the caller to reopen.

- `commands/info.ts` resolves the target with `acceptUserId`, `acceptChatId`, and `allowSelfTarget` (a read-only lookup may target the bot itself; every other command keeps the default refusal). It then hands the lookup to the deferred command executor's interactive lane, bounded by `INFO_TASK_BUDGET_MS`; a shutdown cancellation ends silently, and a budget timeout replies with whatever was fetched.

A failed lookup falls back to the `CachedUser` from target resolution, and with neither a name nor a username the reply is "not found". The avatar reuses `readCurrentAvatar` (group identities have no avatar to read). - Replies with an avatar go only through `sendCommandPhoto` in `infra/telegram/commandPhotos.ts`, which registers the self-sent message and, in groups, the 30-second deletion at the moment the message id arrives; private chats are not deleted and a failed send creates no deletion task. ### `/h_image` Random Pictures

- The random image directory comes from `onlyPath.random_h_image_dir` in the validated `config/dynamic/assets.json` (default `./h_image`; only an absolute path or an explicit relative path starting with `./` or `../` is accepted, and a relative path resolves against the runtime data root, see `getAssetConfig().randomHImageDirectory` in `config/assets.ts`). At startup, after the deployment-input gate and before any Worker or external connection, `ensureRandomImageDirectory` in `infra/randomImage.ts` prepares it: a directory (including a symbolic link to one) is left alone, a missing one is created, and a path that exists but is not a directory or cannot be created refuses startup with a diagnostic naming only the `assets.json` path, the field path (`$.onlyPath.random_h_image_dir`), and the resolved directory. When hot reload switches `random_h_image_dir` to a new directory, that directory is prepared and checked under the same rules first; a failure rejects the edit and the old directory stays in use. A directory deleted at runtime is not recreated.

- Before any Worker or external connection, `ensureRandomImageDirectory` checks read/write/traversal access and requires regular files with supported extensions and 64-character lowercase SHA-256 basenames. The directory root may be a symlink; subdirectories, file symlinks, hidden files and leftover temporary files refuse startup. Validation checks names and entry types, without rehashing, repairing or cleaning inputs. Separate random directories explicitly configured for cron are not subject to this naming rule.

- Drawing (`pickRandomImage`) lists the directory afresh every time and caches nothing: candidates are only non-hidden regular files (`Dirent.isFile()`; symbolic links and subdirectories do not count) whose extension is in `RANDOM_IMAGE_EXTENSIONS`, drawn uniformly. Size is checked through `Bun.file().stat()` first, so a file over `RANDOM_IMAGE_MAX_BYTES` (10 MB, Telegram's photo upload limit) is never read into memory. A drawn file that is oversized, or that vanished before it could be read, is dropped from the remaining candidates and another is drawn uniformly, with at most as many attempts as there are candidates, so a few oversized files do not stop the rest of the library from being drawn. Once the candidates are exhausted with nothing sendable, the round reports `tooLarge` naming the last oversized file if it drew one, and `empty` otherwise.
- `/h_image` and `/h_image add` share one global sliding-window quota (`tryConsumeHImageRateLimit` in `commands/hImage.ts`, window and limit in `consts/hImage.ts`, queue in `cache/main/hImage.ts`): at most `H_IMAGE_RATE_LIMIT_MAX_CALLS_PER_WINDOW` (5) accepted calls per `H_IMAGE_RATE_LIMIT_WINDOW_MS` (1 second), counted across all groups and users. The check runs before the argument is parsed, and a call beyond the quota returns immediately, submitting no task and sending nothing back — answering a throttled call with a message would defeat the throttle. The quota is process-local and starts empty after a restart.
- The update runner is strictly serial, so `/h_image` never awaits directory listing, downloads, or uploads in its handler: after argument validation it synchronously hands the task to the deferred command executor (`commands/deferredCommands.ts`, state in `cache/main/deferredCommands.ts`; 2 in flight, 16 waiting, at most 4 of them in the background lane) and returns, answering with a busy hint when full. Drawing uses the interactive lane; collection, the whole `/batch_kick` batch, and the `/block enable` cross-chat ban fan-out use the background lane (`/batch_kick` runs one batch per chat at a time, tracked in `cache/main/batchKick.ts`); with both lanes waiting they alternate by `interactiveBurst`. Each task restores the update cancellation context it was admitted under, merged with the runtime stop signal, through `submitCommandExecutorTask` in `infra/commandExecutor.ts`, which `/wed` shares. The shutdown maintenance quiesce stops admission first (owner `deferred-commands`); the "deferred commands drain" entry sits before the Telegram gate in the drain table, waits within its budget, and on timeout cancels queued and in-flight tasks. It takes no part in the shared persistence gate.
- `sendHImageResult` in `commands/hImage/draw.ts` is the only send boundary for result pictures (`check:conventions` forbids calling `sendPhotoWithResult` anywhere else under `commands/`). Result pictures are a user-authorized long-lived exception: no fixed-delay deletion, and in forum groups they carry the triggering message's topic and reply to it. Usage, busy, and failure hints all go through `sendCommandMessage` and are deleted after 30 seconds.

- `/h_image add` (`commands/hImage/add.ts`) requires `isCanAddHImage`. Candidates are the picture in the replied message (the pure `messageImageCandidate` in `libs/telegramImage.ts`: the largest photo size, or a document whose MIME type is in `RANDOM_IMAGE_DOCUMENT_MIME_TYPES`) plus the other pictures of the same `media_group_id` and chat from the album cache, deduplicated by `file_unique_id`.
- The album cache `cache/main/mediaGroups.ts` is written by the main-thread message pipeline: `handleAcceptedIncomingMessage` calls `observeMediaGroupImage` in `infra/mediaGroups.ts` only when a message carries `media_group_id` (an ordinary group message costs one field read and no allocation). Private chats are not recorded, ownership is checked by chat id, each album keeps at most `MEDIA_GROUP_ITEMS_MAX` (10) pictures, and the cache holds `MEDIA_GROUP_CACHE_MAX` (256) albums with LRU eviction. It is not cleared by chat teardown, not persisted, and empty after a restart.
- Before collection, `readRandomImageLibrary` in `infra/randomImage.ts` lists the directory once only to count existing candidates for the receipt. Candidates within the batch deduplicate by `file_unique_id`; deduplication against the library uses the downloaded content's SHA-256 filename and target existence, without reading existing image contents.
- Collection handles one picture at a time within the `H_IMAGE_ADD_TASK_BUDGET_MS` budget, holding at most one in memory: a known size over `RANDOM_IMAGE_MAX_BYTES` is not downloaded; downloads go through the shared `infra/telegram/fileDownload.ts` (separate getFile and download timeouts, the download outbound gate, a bounded read); `storeRandomImage` in `infra/randomImage.ts` detects the format from the bytes and names the file after the hex SHA-256 of its content plus the saved extension: if that target already exists the picture counts as already collected and is skipped; otherwise it writes a temporary file starting with `RANDOM_IMAGE_TEMP_PREFIX` plus a `Bun.randomUUIDv7()` (hidden files are never drawing candidates) and renames it within the same directory to the final name, deleting the temporary file on failure. The name is the content digest, so a name clash means identical content: the same picture lands on the same file name no matter who forwards it or whether its `file_unique_id` differs, which is why deduplication happens after the download; manually added pictures must also use content-digest names. When the budget runs out the rest count as failed and the summary is still sent; a shutdown cancellation ends silently.

### `cron.json` Scheduled Tasks

- Parsing lives in `packages/config/cron.ts`: `parseCronConfig` checks shape, values, and paths lexically with no I/O; after reading the file, `loadCronConfig` confirms that what each `payload.path` points to exists and has the right type (symbolic links are followed). `payload.path` accepts an absolute path or a path relative to the runtime data root (`RUNTIME_DATA_ROOT`, the same base as local paths in `assets.json`; no `./` prefix required), is normalized to an absolute path when parsed, and may point anywhere on the host; any file the service account can read can be sent into a chat, and where it points is the deployer's responsibility. Task count, action count, and task-name length are capped (`CRON_MAX_TASKS`, `CRON_MAX_ACTIONS_PER_TASK`, `CRON_TASK_NAME_MAX_CHARS`) and exceeding them rejects rather than truncates; `cron` and `time_zone` are checked with `Bun.cron.parse`, and an expression with no future occurrence is rejected too; `just_once` and `rand_cron` are mutually exclusive; exactly one source is allowed. For `send_voice`, `content` is required and at most `VOICE_OPERATOR_TEXT_MAX_CHARS`, and `tone` is optional and at most `VOICE_TONE_MAX_CHARS`; both are stored after being cleaned into a single line, and a task list that uses it requires `agent.tts` (see the agent configuration entry above). For `send_web_digest`, `topic` is required, cleaned into a single line and at most `WEB_DIGEST_TOPIC_MAX_CHARS`; `language` is optional (`zh`/`ja`/`en`, default `zh`); `max_items` is optional (`WEB_DIGEST_MIN_ITEMS`–`WEB_DIGEST_MAX_ITEMS`, default `WEB_DIGEST_DEFAULT_MAX_ITEMS`); `instructions` is optional and at most `WEB_DIGEST_INSTRUCTIONS_MAX_CHARS`; a task list that uses it requires the chat core capabilities. `assertCronAgentSupported` checks both dependencies against the agent configuration in effect at the startup gate and on hot reload, and the diagnostic names the first action whose dependency is missing. `chat_id` must be a non-empty array: `["all"]` (`CRON_ALL_CHATS`, which may only appear alone), `["except", <id>, ...]` (`CRON_EXCEPT_CHATS`, only as the first element and followed by at least one id), or explicitly listed chat ids; ids are non-zero safe integers, must not repeat, and are capped at `CRON_MAX_CHAT_IDS_PER_TASK`. The scalar form is rejected outright and the diagnostic names the offending index. Parsed tasks have a fixed, fully initialized shape, and hot reload reconciles them by name and deep equality.
- Scheduling runs on the main thread in `packages/cron/scheduler.ts`, with state in `cache/main/cron.ts`. Each task gets one Bun-native in-process cron (task time zone, unref'd); the handler returns the run's Promise, so Bun schedules the next fire only after it settles and a task never overlaps itself. Handlers swallow every error so no `unhandledRejection` can trigger an emergency exit. `just_once` stops on its first fire and records the run; `rand_cron` stops its cron after the first fire; afterwards, after each run it picks a uniformly random instant in its range, rounds it up to the whole minute, and registers a new Bun-native cron that matches only that minute (written as UTC fields "minute hour day month *", independent of the task time zone, unref'd), which is likewise stopped when it fires. The range is capped at 24 days, so the one-shot expression, which has no year field, never lands on the same instant a year later.
- Reconciliation: deep-equal tasks keep their handles (including a `rand_cron` random instant); changed or removed tasks stop and are marked cancelled — a run in flight finishes its current request and stops before the next action or retry; new tasks are registered. `just_once` records live in a bounded LRU (`CRON_JUST_ONCE_RECORD_MAX`); a record is kept while the task stays `just_once`, cleared when it becomes recurring, and refreshed each round for names in the current table. Neither records nor random instants are persisted, and triggers missed while the bot is down are not made up.
- Explicitly listed chats are delivered by `packages/cron/run.ts` in the written order without any permission lookup and without going through `cron/targets.ts`, with the same one-second gap between chats; a final failure in one chat only skips the rest of that chat's actions before moving on. When more than one chat is listed, the failure log names the chat.
- Execution (`packages/cron/run.ts`): actions run in order one second apart; network errors, 5xx, 429 responses remaining after outbound-gate retries, and a full outbound queue are retried up to 3 times with 2/4/8-second back-off, and so are a failed `send_voice` synthesis, a timed-out wait, and a temporarily unavailable AI Worker, as well as a failed `send_web_digest` search or composition request, a timed-out wait, and a temporarily unavailable AI Worker; a missing `tts`, an exhausted daily quota (`daily limit reached`), and an encoding or container-check failure are not retried, nor are a searched digest without sources or a digest still invalid or too long after recomposition, nor other failures; digest retry classification depends on the failure reason, independently of the search count. Each run creates a fresh `CronRoundVoices`, so one `send_voice` action is synthesized only once per run, retries and later chats reuse the same audio, the `file_id` Telegram returns for the first successful send is recorded and referenced afterwards instead of uploading again, and it is discarded when the run ends; each run also creates a fresh `CronRoundDigests`, so a successful `send_web_digest` result is cached as complete MarkdownV2 text, including any unsearched warning, and reused by send retries and later chats; failed generation is not cached; a final failure logs one English error line and skips the rest of the run. A retry can duplicate a message when a timeout hid a successful send.
- `chat_id: ["all"]` and `["except", <id>, ...]`: at the start of each run `packages/cron/targets.ts` walks every `isInitEnabled` group in the main-thread `chat_states` cache that is not on the exclusion list, in ascending chat id order and checks the bot's membership live (`getChatMember`; a plain member also reads the group's default permissions with `getChat`). The actions the task uses require `can_send_messages`, `can_send_photos`, `can_send_documents`, and `can_send_voice_notes`; a group missing any of them, or whose lookup fails, is skipped entirely. That module only reads; sending stays in `cron/delivery.ts`. Groups that can receive run the whole action list one by one with the same one-second gap between groups; retries and "skip the remaining actions" apply to the current group only before moving on, and revocation or shutdown stops before the next group. The skipped count is logged once at the end of the run with `logger.log`; groups removed by `except` are never queried and never counted as skipped, and the empty exclusion list is passed as `CRON_NO_EXCLUDED_CHAT_IDS` rather than allocated per run.

- Fixed images require 1–10 URL or file-path entries and forbid `rand_image: true`. One item uses `sendPhoto`; multiple items use one `sendMediaGroup` call, only the first caption, spoilers on every item when enabled, and registration of every returned message ID. Random mode still draws one image and accepts an optional directory string.
- `packages/cron/delivery.ts` is the only send boundary (`check:conventions` forbids sending from any other file under `packages/cron/`). It goes through the main-thread grammY client, and therefore the outbound gate (sends enter their chat's lane in the send scheduler), sets `parse_mode: "MarkdownV2"` only for `send_web_digest` and none for the other actions, carries no forum topic (so it lands in General in groups with topics), and registers self-sent messages on success. Cron messages are a user-authorized long-lived exception with no fixed-delay deletion. A `url` is handed to Telegram as-is and never downloaded; a local file is first checked against Telegram's upload limits (10 MB pictures, 50 MB files) and uploaded from a `Bun.file().stream()` reopened on every serialization, so a 429 replay never gets an exhausted stream; `rand_image` reuses `infra/randomImage.ts` and draws again on every attempt; when `send_image` has `is_blurred: true` the request carries `has_spoiler: true`, and otherwise the field is absent; `send_voice` takes the run's voice (synthesizing it through `synthesizeVoice` and registering it when absent), calls `sendVoice` with the duration in whole seconds, uploading under the synthesized voice's own file name (`voice.ogg` or `voice.mp3`) until the run has a `file_id` and referencing that `file_id` afterwards, and writes nothing to AI memory; `send_web_digest` takes the run's digest (generating it through `composeWebDigest` in the AI Worker and registering it when absent), sends it as one MarkdownV2 message without `link_preview_options` (Telegram previews the first link), treats a Telegram rejection, including a parse failure, as a non-retryable failure without falling back to plain text, and writes nothing to AI memory.
- Digest generation (`aiChat/ai/webDigest.ts`, inside the AI Worker; the main-thread waiter is `aiChat/webDigest.ts`): research uses the `agent.web_search` model when configured, otherwise the `text` model's built-in search. Request failure returns `search failed`. When `searchCalls === 0` and the body is non-empty, prepend the fixed warning 「注意，以下可能为模型侧缓存内容，请仔细甄别」 and escape the whole message as MarkdownV2. Beyond 4096 visible UTF-16 code units, preserve the warning and truncate the body at a character boundary with an ellipsis. This branch skips JSON composition and requires no sources. Its `sending with warning` log includes at most 2000 characters of model text, the full length, source count, and truncation flags; an empty body returns `search failed`. After a search, source metadata and complete HTTPS links in the research text form the URL allowlist; absence of URLs in both returns `no sources`. Composition uses `text` without tools or Gemini explicit caching and returns digest/v1 JSON (`json_object` on OpenAI-compatible endpoints, `responseJsonSchema` on Gemini, `output_config.format` on Anthropic). `libs/webDigest.ts` decodes strictly: `body` may contain non-empty lines, and other text fields are single-line. Each item URL must appear verbatim in source metadata or research text and be HTTPS without credentials or whitespace. These checks only parse local strings and URLs; they make no request to the links. `libs/webDigestMarkdown.ts` renders MarkdownV2 and checks the visible 4096 limit. Invalid output triggers one recomposition with a diagnostic (`WEB_DIGEST_COMPOSE_ATTEMPTS`); persistent failure fails the run, with no truncation or splitting in this branch.
- Each `send_web_digest` generation captures one reference time in the configured zone, used once at the end of the research query and once in each composition request's user content; composition retries reuse it. `topic` is a short research description, while `instructions` supplies task rules shared by research and composition in their user messages. System prompts contain fixed responsibilities and format rules. Cron and interactive `web_search` prompts are separate and share only the trusted-clock instruction. Topics specifying today include only facts or plans applicable to that configured local calendar day, never substituting page publication time for event time. `payload.max_items` accepts 1–15. The source metadata list shown to the composer contains at most 20 distinct URLs; local matching uses all metadata and research links regardless of this display limit. All three providers use an independent 180-second `web_search` timeout for each SDK attempt and for the entire provider call, including SDK retries; interactive search and cron share it. Quota queueing precedes the provider deadline. The main-thread generation wait remains 480 seconds (`WEB_DIGEST_REQUEST_TIMEOUT_MS`), including queueing, research, and up to two composition calls; expiry cancels the Worker request.
- Lifecycle: the startup gate strictly loads the file when it exists; the scheduler starts before `startConfigReload`; the maintenance quiesce stops admission and every cron handle first, and the "cron drain" entry sits before the Telegram gate in the drain table, cancels in-flight requests on timeout, and takes no part in the shared persistence gate.

### Reply and Response-Body Resource Boundaries

- **Bounded reads control both bytes and retained chunk references.** `libs/boundedResponse.ts` checks accumulated bytes before accepting each chunk, skips empty chunks, and aggregates with `Bun.ArrayBufferSink` when the reference budget is exceeded. Successful output owns its bytes. This limit does not control producer allocations made before delivery. One reader boundary handles oversize cancellation, read errors, and lock release; unsuccessful avatar HTTP responses cancel their unconsumed bodies.
- **Model concurrency and live delivery capacity settle separately.** Tool context stays alive until real sends and resource cleanup finish. The 32-per-chat and 128-per-Worker bounds include every still-live generation. Regression tests cover blocked windows, capacity rejection, cross-chat draining, cancellation/reopening, and cleanup after timeout in `test/workers/aiChat/replyOrder.test.ts`, `replyDelivery.test.ts`, and `replyState.test.ts`.

## Persistence

- **Optional persisted input accepts only genuine absence.** `inspectOptionalDirectory` and `inspectOptionalFile` in `libs/fileAccess.ts` check ancestors when an entry is missing. Dangling or cyclic links, a directory at a file path, ENOTDIR, and EACCES are rejected. Domain directories allow valid directory links; ordinary persisted files reject links, while `memory/global/state.json` retains its own file-link policy. Synchronous append adoption remains synchronous, and contents are read through Bun. Verification, logs, luck/secrets, AI/stickers, join logs, and member files all finish inspection before adoption or maintenance. Failure in any domain prevents publishing recovery, generating a secret, compaction, or old-day/temporary-file cleanup; existing bytes remain intact.

### Durability and Snapshot Contracts

- Persisted copy and translation target identities (`username`, `first_name`, `last_name`, `title`) are saved and read exactly as Telegram supplied them: they are not trimmed, empty and whitespace-only strings remain valid, and absent fields stay absent. A present field that is not a string is rejected by strict decoding. Unknown keys in global state, asset configuration, AI usage, and log records are located by a fixed field placeholder or entry index; diagnostics do not echo key contents.

- `memory/global/state.json` uses latest-value coalescing, a temporary file, fsync and atomic rename. Its top level holds only `copy` (required) and `ttsUsage` (optional), with no backup copy; asset settings (the random image directory, the default avatar source and the thumbnail URLs) live in `config/dynamic/assets.json`, and feature switches and translation sessions live in SQLite `chat_states`. Startup recovery and the installer share the read-only state gate `loadCurrentGlobalState` ([`packages/infra/storage/statePersistence.ts`](../../packages/infra/storage/statePersistence.ts)): while a 14.x `state.json` or `state.json.bak` remains in the data root, it refuses (`assertLegacyStateFilesAbsent`), and the current format never reads them; it then strictly decodes `memory/global/state.json` against the current schema and likewise refuses invalid content such as an unmigrated total-count `ttsUsage`, so the installer stops before registering or starting the service. Authoritative copy changes must wait for their revision to reach `memory/global/state.json` before success feedback or middleware completion.
- **The authoritative `ttsUsage` in `memory/global/state.json` (daily speech-synthesis count) lives in the AI Worker** (`cache/workers/aiChat/ttsUsage.ts`); `globalTtsUsageState` in the main thread's `cache/main/storage.ts` is only a persistence mirror. Each time the Worker records or refunds a use it sends the full count (`{ windowStartedAt, agentCount, reserveCount }`, a fresh object each time; `null`, meaning never used, when a refund brings both counts to zero) in a `ttsUsage` event; the main thread replaces the mirror and hands it to `StateStore`'s background write: latest-value coalescing writes it `STATE_BACKGROUND_SAVE_DELAY_MS` (5 seconds) after the first unsaved change, and in the meantime any write that awaits persistence (such as an authoritative copy change) or the shutdown flush writes the latest count out immediately along with it. There is no durability barrier; uses not yet on disk are lost if the process crashes. The AI Worker receives `hydrateTtsUsage` right after `init` at startup and after the replayed `init` on respawn, ahead of any trigger or `synthesizeVoice`; a null mirror means never used. The AI voice tool's in-flight admission reservations (`pendingAiTtsReservations`) live only in AI Worker memory, are neither sent back nor persisted, and start from 0 on respawn, since the old isolate's in-flight syntheses end with it. The counting window runs `TTS_USAGE_WINDOW_MS` from `windowStartedAt`; a window start later than the current time (a wall-clock rollback) counts as an ended window (the `libs/clockWindow.ts` rule), and the next claim starts a new window from zero. A missing block means never used; when present, `windowStartedAt`, `agentCount`, and `reserveCount` must all be non-negative safe integers, with at least one positive count, otherwise startup is refused. Counts are not checked against configuration limits; lowering a limit below its used count blocks only that quota's new requests. The old `count` field refuses startup and requires a cold migration. The AI Worker terminates before the state flush, so the last use recorded before shutdown reaches the final write.
- **Translation sessions are independent of copy**. Sessions are the `ChatState.translate` field, persisted with the `chat_states` row and held by the main-thread hot read copy, so they share the 25-group capacity with other chat state; each group holds a nonempty readonly array of 1–5 distinct identities and their `ja|cn|en|uk|ru` directions, or `undefined` when there is none. A group without a chat-state row cannot start translation once capacity is full. Invalid values, duplicate identities, empty arrays and capacity overflow refuse startup, as does a `translate` block in `memory/global/state.json`. Recovery seeds the existing identity cache without a Worker mirror. The message path reads the group Map and searches at most five entries by identity, without projection objects. Translation sends only the translation of the text or caption as a text message; same-language text, neutral text and API failures send nothing, and media are never copied. An identity that is also the copy target is only translated, with no echo and no reaction mirroring. Adding or removing targets replaces the array while retaining other session objects; results send only while their own session remains valid. `queueTranslateMessage` in `translate/message.ts` hands each translation to a per-group serial background chain that generates and sends it; the update waits for neither the Google RPC nor the send, and a group's translations go out in arrival order but may land after later output in that group, such as command receipts. Tasks are registered in `translateRuntime.tasks`, and shutdown waits for them through `drainTranslate`. Each group's backlog (including the one running) is capped at `TRANSLATE_CHAT_BACKLOG_MAX`; at the cap new messages are not translated, and one stretch of backlog is logged only once. Translations are sent only after the update is acknowledged: a translation whose turn comes after the shutdown quiesce is not sent at all, queued translations are lost if the process crashes, and Telegram redelivers neither. Start, targeted/group stop and teardown change the group state synchronously and then await the exact durable ACK of `persistChatState`. `/translate disable` persists session deletion before persisting `isTranslationEnabled`; either failure blocks success feedback. Its permission is `isCanControllTranslatePermission`; `/bot_status` reads this group's array length. Translation never changes avatars or consumes the copy cooldown.
- **The global state file passes a read boundary before decoding** (`infra/storage/statePersistence.ts`): `memory/global/state.json` must be a regular file or a valid symbolic link to one. Directories, links to directories, dangling links, and access failures such as `EACCES`/`ELOOP`/`ENOTDIR` refuse startup. Only when `lstat` also reports `ENOENT` is the file treated as absent. A fatal `TextDecoder` strictly decodes UTF-8 and strips a BOM. Read, decode, or schema validation failures preserve the original file. Errors contain only the file path, field path, and expected shape.
- **`config/dynamic/assets.json` has exactly three top-level groups: `onlyPath` (the random image directory `random_h_image_dir`), `pathOrUrl` (the bot's default avatar `bot_default_avatar`), and `onlyUrl` (the two inline fortune thumbnails and the gag inline thumbnail). A missing file, group or field means "never configured" and falls back to the built-in constant** (`consts/ui/assets.ts`), never "keep whatever was there last". The main-thread snapshot lives in `cache/main/assets.ts`: the startup gate adopts the whole file when it exists, each hot-reload round replaces it wholesale from what it read, and deleting the file switches back to the built-in defaults. The bot never writes this file back; it only reads it and never seeds it, so a change to a code constant shows up directly on deployments that do not set that field. An unknown group, a field outside its group (including an old field left flat at the top level), or a group that is not an object rejects the whole file; the previous format is not accepted.
- Asset URLs are validated at decode time: non-empty, trimmed, and a parsable absolute URL, and what is read back is the WHATWG-normalized `href` rather than the raw string (`trim` only touches the ends, while the URL constructor also swallows interior tab/LF/CR and percent-encodes spaces — keeping the raw string lets an address the constructor accepts but Telegram rejects pass validation). **No image host is privileged**, but the scheme is: the three thumbnails are fetched by Telegram clients and must be `https`; only `pathOrUrl.bot_default_avatar`, which this process downloads itself, may be plain `http` — whether that hop uses TLS is the deployment's call. A local path is accepted only as an absolute path or an explicit relative path starting with `./` or `../` (without NUL) and resolves against the runtime data root; a `bot_default_avatar` value of that shape becomes a local-file source (`path` in `DefaultAvatarSource`), and any other value is judged as a URL. `parseAssetConfig` is lexical and performs no I/O; `loadAssetConfig`, shared by the startup gate and hot reload, verifies a local avatar file as an existing regular file (following symlinks), at most `AVATAR_MAX_DOWNLOAD_BYTES`, with a JPEG or PNG signature, reading at most one byte past the limit. A malformed value rejects the whole file instead of silently falling back — a missing scheme merely makes Telegram skip the picture, which is indistinguishable in the group from the image being down.
- The default-avatar download **does follow redirects** (`redirect: "follow"`): the address is part of the deployment's configuration, where it lands is decided by the image host the operator chose, and "a direct link 302s to the actual storage domain first" is precisely the norm for image hosts and object stores (the built-in Google Drive default included). Forcing the operator to resolve the final hop themselves only turns an inevitable trip-up into a documentation caveat. The redirect ban on the three downloads behind `/copy` and `/icon steal` belongs to a different constraint — see [Outbound Requests and Message Safety](#outbound-requests-and-message-safety) — because those addresses come from the Bot API's `file_path` and from HTML scraped off a t.me page and are governed by the Telegram-owned asset-domain allowlist; this entry is not a weakened version of it. The `AVATAR_MAX_DOWNLOAD_BYTES` bounded read and the pre-upload image-signature sniff guard against "what came back is not an image at all" (Drive's quota / virus-scan HTML interstitial being the classic case), which has nothing to do with redirects. A local-file source is re-read with the same bound and signature check on every attempt; an unreadable, oversized or non-JPEG/PNG file is a permanent failure and is not retried.
- Failure logs for a local-file source name the resolved absolute path. All four failure logs for a URL source name the effective address, which is what distinguishes "the `assets.json` entry is wrong" from "the shipped fallback constant rotted" — but they print **only `origin + pathname`** (`redactUrlForLog` in `libs/redaction.ts`), dropping the query string, fragment and userinfo. This entry is deployment-configured and may be an S3/OSS presigned URL, while `logs/<day>.json` is mode `0644` and part of the backup set, and `redactSecretsInText` in the same file only redacts credentials from loaded configuration and never looks at the query. The download itself still uses the full address — strip the signature and the image cannot be fetched at all.
- Before anything reaches the journal, Worker envelope, or `logs/`, the shared logger first replaces raw credentials from loaded configuration, including each google-provider `headers` value, then reduces HTTP(S) URLs in strings to origin and pathname, removing userinfo, query strings, and fragments. An apostrophe inside a path belongs to the URL. Credential fields in SDK/HTTP errors — `authorization`, `cookie`, `set-cookie`, API keys, tokens, secrets, and passwords — are replaced by key, including raw header tuples. JSON-escaped credential fragments also match object keys in the serialized result. The traversal callback is cached with the configuration snapshot and reuses the existing JSON serialization and expansion budget, without allocating a callback or deep-cloning objects per emit. Non-secret diagnostics such as request IDs, rate-limit counters, and token counts remain available.

- Before output, logger expands and recursively redacts `cause`, `AggregateError.errors`, and Error-valued enumerable own fields. One emit shares a budget of 64 Errors and 256 arguments/properties/array elements, with nesting depth at most 5 and parameter JSON at most 64 KiB. Cycles, depth limits, and exhausted budgets produce static placeholders.
- **`normalizeChatState` reclaims only fields that have genuinely expired; a reading that merely looks implausible is clamped, never deleted.** The upper-bound check on `quietUntil` (`isQuietUntilActive`) exists for wall-clock rollback, yet `/quiet <max minutes>` writes a `quietUntil - now` exactly equal to `QUIET_MAX_DURATION_MS`: with zero tolerance, a 1-millisecond backward step voids a maxed-out quiet period outright. The check therefore carries a `QUIET_CLOCK_SKEW_TOLERANCE_MS` tolerance to absorb ordinary NTP steps, and a larger rollback is clamped by this normalizer to `now + QUIET_MAX_DURATION_MS` — the quiet period stays in effect and is still guaranteed to end within the cap, which is exactly what that cap was for. Deleting the field is not an option: this normalizer runs over every chat on every `saveState()`, so one deletion wipes the quiet period from memory and SQLite `chat_states` together, unrecoverable even after the clock corrects itself (same trade-off as `libs/slidingWindowRateLimit.ts`, which drops only the out-of-range entries and never clears the whole window).
- **`ChatState` has a canonical shape: every field is created once, and from then on it is only assigned, never `delete`d** (`createChatState` in `libs/chatState.ts`). "Never set" is expressed by `undefined`, not by an absent key, and the `DEFAULT_CHAT_STATE` that `getChatState` hands out for chats with no entry must share that shape, or the hidden class flips back and forth between "has an entry" and "has none". This is the hot-call-site shape contract (AGENTS.md: fields must not be added or removed after the fact) — every group message reads `getChatState(chatId).isXEnabled` 4-6 times (`antiRaid/updateIngress.ts`, `antiRaid/floodControl.ts`, `antiRaid/adCandidate.ts`, `auto/message/index.ts`, `aiChat/availability.ts`).

  **State encodes only nondefault fields.** `encodeChatStateData` writes only nondefault state fields to `chat_states.status`, and an empty object is not valid state. A confirmed `botPermissions` snapshot remains even when all fields are false, unlike the `undefined` of an unchecked identity. Canonical `ChatState` initializes all 12 fields at once. Emptiness is checked by field value; context alone cannot keep a chat-state row alive. Decoded state passes through `adoptChatState` into the same shape, with unset fields represented by `undefined`. Hot-path objects must not gain or lose keys.
- The AI Worker reports dirty AI-memory snapshots every `AI_SNAPSHOT_INTERVAL_MS` (30 seconds). The Disk I/O Worker strictly validates each one and queues the chat's final value in the shared SQLite transaction buffer, which updates `chat_states.ai_context` by primary key in the same transaction as the other tables and commits on the shared timer, full batch, domain barrier, or shutdown flush; an invalid snapshot is rejected in place with an `aiMemory` rejection mark and does not advance the revision watermark. Deletions and the first snapshot after a purge commit immediately; inside the mirror-replay window and during the retry backoff after a failed transaction they only queue, committing when the window closes or on the retry. The sticker catalog uses atomic snapshots per entity. Fortunes, pending-verification state, logs, AI cache usage, and ad samples are all append-only JSON files; only logs and AI cache usage repair tail truncation, through `inspectRepairableAppendOnlyFile` during the read-only startup inspect, and ad samples also allow tail trimming when the file is first opened for writing, while fortune and pending-verification day files are parsed strictly: a torn tail or non-canonical formatting refuses recovery and leaves the original bytes untouched. Fortunes, AI cache usage, and ad samples append in batches at `FLUSH_MAX_ENTRIES` (256) entries or `FLUSH_INTERVAL_MS` (30 seconds) after the first one; ordinary pending-verification field changes coalesce by key and append at 256 keys or after 30 seconds, while creation, terminal states, and finalization append immediately. Every append batch is fsynced before success is acknowledged. Verification completion appends a tombstone.

  On startup across configured local midnight, recovery strictly decodes the latest prior-day file, overlays the current day's newer active values and tombstones, and atomically compacts the result into today; old days are removed only after publication succeeds, while corrupt prior data leaves both sides untouched and fails recovery. Steady state retains only the current local-day file, and entry/byte thresholds compact it into an active snapshot.

  Truncation repair must recognize top-level member boundaries from JSON strings, escapes, and bracket depth rather than relying on indentation at the end of object values; `null` tombstones and other primitive values must count as complete final values.
- Disk I/O startup recovery has three strict phases: every persistence domain is inspected and decoded read-only (SQLite first, so its version and data-root time-zone gates report before day files validated against "today"); only after all inspections succeed are the in-memory owners and writable SQLite connection adopted; temporary/orphan/expired-file cleanup and compaction run after the success reply, followed by the single local-midnight maintenance cron. The cron isolates failures by domain, first notifies the main thread to admit the daily `/wed` membership review, then triggers fortune, log, join-log, ad-sample, pending-verification, and temporary-ad-bypass maintenance; existing startup and event paths remain fallbacks. An inspection failure must not change any domain's files or permissions or leave a maintenance cron behind. AI memory and sticker protocol hydration in the AI Worker reuses the same strict decoders, so a malformed payload fails initialization or reconstruction instead of silently dropping one item.
- AI-memory upserts and deletes use runtime-monotonic revisions per chat. The main thread retains unacknowledged deletion tombstones. The Disk I/O Worker acknowledges only when the SQLite clearing transaction reaches a durable boundary, when the deletion is older than an already accepted revision, or when a newer revision superseded the uncommitted deletion and the superseding write has committed. Worker reconstruction replays tombstones and the latest mirror, so replay order does not determine the final result.

  The context capacity shown by `/bot_status` reads nothing but counts derived from that same mirror: the AI Worker carries the hot-buffer size and the cold-summary round count on every memory snapshot report and seeds them in full once hydration completes, and both counts live and die with the snapshot mirror. The main thread must not parse snapshot JSON on the command path, and a missing entry must never be read as "keep the previous value" — it always means there is no context to show right now, which displays as zero.

  The first new snapshot after an acknowledged deletion or LRU eviction must be persisted immediately; until the matching durable-upsert acknowledgement arrives, the main thread retains its revision marker and replays the latest mirror after Disk I/O Worker reconstruction. Startup recovery treats SQLite `chat_states` as authoritative: only explicitly AI-enabled groups are hydrated, while stale snapshots for disabled groups are scheduled for deletion.

  Every hot-memory message in the current snapshot must have a positive `messageId`; the message index is reconstructed from those messages and is not persisted separately.

- A `chat_member` join fact is accepted once it enters a batch: `recordJoinLog` posts the fact with a monotonic sequence number, registers it in the main-thread unacknowledged mirror (`cache/main/joinLog.ts`), and returns immediately without waiting for disk. The Disk I/O Worker accumulates `FLUSH_MAX_ENTRIES` (256) facts, or waits `FLUSH_INTERVAL_MS` (30 seconds) after the first one, then appends them grouped by `chatId:day` and fsyncs; the unified shutdown flush writes out the remaining batch. As disposition advances, the Worker emits a `joinLogPersisted` receipt carrying the highest sequence number it has received (`through`) and the sequence numbers among them still in its buffer (`pending`): every other fact up to `through` has been written or discarded as outside the window, so the main thread releases them and the mirror keeps only facts not yet on disk. When the Worker crashes and is rebuilt, the mirror replays in original order through the respawn listener, and `DiskIORecoveryRevisions` skips facts in the recovery FIFO whose sequence number does not exceed the last replayed one; the disk index skips an exact redelivery that was already written before append. When facts not yet on disk reach `JOIN_LOG_MAX_BUFFERED_ENTRIES` (1,024 entries, four batches) or Disk I/O rejects the post, `recordJoinLog` returns false and `updateIngress` throws, leaving the update unacknowledged for Telegram to redeliver, so a persistent disk failure never turns into unbounded memory. If the process is killed or loses power, join facts from the most recent window that have not reached disk are lost.

- After a join-log append is fsynced, a compaction failure before rename is a maintenance error and does not negate the append receipt. After rename, parent-directory fsync must complete; otherwise the write is not acknowledged, its cache is discarded, and retry is deferred. Re-adopting an existing file also syncs its parent before rebuilding the append cursor and index.

  On a write failure the Worker must restore the original group to its buffer and retry with backoff, never clear and discard it; those facts are listed in the receipt's `pending`, so the mirror keeps holding them; a chat whose file keeps failing to write retains only its own facts, and other chats' written facts are released as usual. The Worker's pending set is always a subset of the main-thread mirror, so the mirror's hard cap also bounds Worker memory. `handleJoinLogMessage` never throws for a single fact: a day-rollover cleanup failure is only recorded with `console.error` and the fact is buffered as usual (the new fact lies inside the retention window, so the cleanup never deletes its file), and the next fact and daily maintenance retry the cleanup.

  **Whole-chat deletion at teardown occupies its own domain** (`joinLogPurge`). The barrier in `purgeChatJoinLog` flushes only that domain, so an undeletable file from one unmanaged chat makes only that teardown report failure and never drags down other chats' join batches. The deletion side synchronously drops that chat's facts still pending in the Worker buffer while the main thread removes that chat's entries from the unacknowledged mirror (otherwise the next flush or a Worker rebuild would write them back into a file just deleted), unlinks each file with a directory fsync, and keeps the pending-deletion mark for later flushes to retry on failure.

  At most 64 chat/day latest-by-user indexes remain resident under LRU eviction, while the failure-backoff table tracks at most 128 files. Both can be rebuilt safely from authoritative files or a later retry and must never serve as evidence of persistence. Before append, the disk-reconstructed index skips an exact Telegram redelivery. `/batch_kick` reads the rolling `[since, now]` interval and merges every chat/day file covered by the window, including three dates across a short daylight-saving day.

  **Both ends of the window must come from the same clock as `joinedAt`.** Every stored `joinedAt` originates from Telegram's `update.date` (`antiRaid/updateIngress.ts`), so `/batch_kick` takes its "now" from the command message's own `ctx.msg.date`, not the host's `Date.now()` — subtracting one clock from the other shifts the window boundary by whatever skew lies between them, and `readJoinLog` uses `since`/`now` both to compare each `joinedAt` and to decide which day files the window covers (those file names are themselves derived from `joinedAt`'s configured local date). The retention side still judges by the host clock (`today` inside `readJoinLog`): that asks "which days are still on disk", which the Worker's own day-rollover cleanup decides, and has nothing to do with event time.

  **The two sides of "outside the window" end differently and must be judged apart.** **Too old** (a join from days ago that Telegram redelivered after downtime) is a deliberate silent discard — the rolling 24-hour window has no use for it; when the buffer is empty the Worker sends a disposition receipt immediately so such facts do not occupy the main-thread mirror. **Ahead of the Worker's own today** means event time disagrees with the host clock (typically Telegram crossing configured local midnight first). Such facts enter the buffer as usual, and the flush holds them until the Worker's configured local date catches up before writing: startup recovery refuses future-dated files, so the file must not be created early. While they wait they are listed in the receipt's `pending`; if they are still unwritten at the unified shutdown flush, the joinLog domain reports failure truthfully.

  **The "handed back to the blocklist" line in a `/batch_kick` report must actually hand them back.** For records that short-circuit on a blocklist hit, the command does nothing at all — no probe, no removal — and only counts them in the reply. Without one sweep request at the end of the batch (`requestBlocklistResweep` + `sweepBlockedMembers`) that line is empty: the admin concludes the blocklist pipeline took over while no batch, sweep, or retry exists anywhere, and the typical cause is precisely an earlier ban batch that rate limiting made report `complete` without taking effect, leaving the person still in the chat. Dispatch keys off the short-circuit count rather than the total `blocked`: the concurrent-block repair path that re-banned successfully already has the person pinned and needs no sweep. One dispatch per batch is enough — `prepareBlocklistSweep` has its own claim and `nextRetryAt` gates, so per-record calls only spin inside the command's fixed small concurrency pool.

- **The AI persona is a process-wide startup snapshot.** The main-thread startup gate (`ensurePromptFiles` in `packages/config/readiness.ts`) adopts it: the text of `prompt/persona.md` when present, otherwise the built-in `DEFAULT_AI_PERSONA` (`packages/consts/aiChat/prompts/persona.ts`). The snapshot lives in `personaCache` of `cache/perThread/config.ts`; the AI Worker adopts it only through `init`, and the main thread replays the same snapshot when the Worker is rebuilt. It is not hot-reloaded, not stored per group, and has no command that changes it. Each reply round starts its system prompt with the persona, and tool turns within a round keep the same prefix.

- **The `send_voice` instruction override is a process-wide startup snapshot.** The same startup gate (`ensurePromptFiles`) reads `prompt/voice_tool.md`: its trimmed text when present, otherwise `null`; a present file that is blank, unreadable or not valid UTF-8 refuses startup, whether or not `agent.tts` is configured. The snapshot lives in `voiceToolPromptCache` of `cache/perThread/config.ts`; the AI Worker adopts it only through `init`, and the main thread replays the same snapshot when the Worker is rebuilt. It is not hot-reloaded. When not `null`, it replaces the whole `send_voice` tool instruction regardless of `bot_language`; the `text` / `tone` parameter descriptions and the voice de-duplication rules in `send_message` and the action-and-stop section still take `VOICE_LANGUAGE_PROMPTS` by `bot_language`.

- **The group notice style is a process-wide startup snapshot, with explicit configuration taking priority.** Readonly tables live in `packages/consts/atmosphere/{teasing,plain}/`. The startup gate fixes the process style together with the persona (`botAtmosphereState` in `cache/main/atmosphere.ts`): explicit `atmosphere` in `bot.json` takes priority (`mesugaki` teasing, `normal` ordinary). When omitted, use ordinary copy with `prompt/persona.md`, otherwise the default teasing copy. Parsing preserves omission, and the installer retains either the explicit value or omission when replacing identity fields. Notice style is independent of `isAIChatEnabled`. The main thread reads it through `chatAtmosphere()` in `infra/atmosphere.ts`, which throws before the gate completes; the AI and Anti-Raid Workers each keep only the same enum injected by `init` / `agentConfig`, the main thread replays the process snapshot on rebuild, and an uninjected Worker uses the configured default style. No per-message SQL, mirror synchronization, or request/reply is added.

- **Notice rendering reuses a local table reference.** Body text, labels, and buttons in the same message use the current table together. Avatar tasks retain only the target, command source, and generation; after the avatar operation finishes, only the latest uncancelled task renders its receipt from the result, and superseded or cancelled tasks send no receipt.

- **Menus and notices use the same style selection.** Startup registers the process-style menu for all group chats and clears the default scope, with no per-chat scopes; menu API failures are logged and the next startup registers again. Permission help/query, QA, buttons, command receipts and Worker notices use the same style and keep their existing retention boundaries. The AI rate-limit notice records the text actually sent. User content is only interpolated, and entity offsets are computed after rendering.

- **Ordinary inline fortune queries use the style configured for the Bot.** [InlineQuery](https://core.telegram.org/bots/api#inlinequery) has no target chat ID; signed receipts do not supply target identity during the query either. Never infer the target from the querying user, other cached groups, or `chat_type`.

- **Context persistence updates existing chats only.** Startup strictly reads `ai_context` through the same SQLite connection, restoring AI memory and the main-thread unacknowledged-snapshot mirror. Context and chat state enter the same shared transaction buffer, and the transaction writes chat state before the primary-key UPDATE of the context: a chat row created in the same batch exists first, and a late snapshot cannot resurrect a deleted chat; a failed transaction retains both for retry without an early durable ACK. State/persona writes preserve context. Memory deletion clears only `ai_context`; row deletion clears all three columns.

### Chat State and `chat_states`

- **The authority for per-chat state is the SQLite `chat_states` table; the main thread only keeps a hot read copy whose capacity is exactly `STATE_MANAGED_CHAT_LIMIT` (25)** (`packages/cache/main/chatState.ts`). `status` stores the seven feature switches (including `isProxySendEnabled`), `quietUntil`, the `lockdown` write-ahead record, the complete `botPermissions` snapshot, `title` and the translation sessions `translate`.

- **The capacity gate refuses; it never evicts.** Creating a 26th entry throws in `assertChatStateCapacity`. Startup decoding in `decodeStoredChatStates` checks capacity and proxy-target uniqueness, and the Disk I/O Worker independently checks capacity on writes. `hydrateChatStateCache` only installs decoded states into the hot read copy with a fixed object shape; the hot read copy is a plain `Map` with no eviction.

  **The hot read copy iterates in insertion order** (startup hydrate order, then creation order), and `get` does not change that order, so `getChatStateCache()` iteration order does not depend on read history — the connected-ban chat lists of `/block … enable` and `/block … disable` render it straight to the user. `getChatStateCache()` returns a `ReadonlyMap`; callers only read and iterate, and writes go through the `stateStore.ts` facade.

- **Capacity refusal belongs to `/init enable` alone, and it must be a reply.** That command is the only entry point that takes a new chat under management; over the limit it answers `INIT_CHAT_LIMIT_TEXT`. No other command may trigger a create — `/send <groupId>` therefore requires the target to already have a row and otherwise answers with one line. A capacity error escaping a command handler is a redelivery-driven restart loop: the update is never acknowledged, the process exits non-zero, Telegram redelivers the same command, and it throws again.

- **A record that returns to its defaults must disappear.** Every write runs `normalizeChatState` first (an expired `quietUntil` is reclaimed, and silence stretched past the limit by a wall-clock rollback is clamped to it); if `isEmptyChatState` (all switches `false`, all other fields `undefined`) then holds, the cache entry is dropped and a deletion tombstone is written. Encoding writes only switches that are `true`. `/init disable` must therefore clear `title` as well — a chat title is recorded only for a managed chat (`applyChatTitle` likewise requires `isInitEnabled === true`), and leaving it behind keeps the record non-empty forever, permanently consuming that slot with no command able to delete the residue.

- **At most one active proxy-send target** (`isProxySendEnabled`): validated independently on the write side and by the startup full-table recovery. The write side judges **inductively** — the invariant held before this write, so only a write that turns `isProxySendEnabled` on can break it, and every other write can skip scanning the other rows.

- Persistence uses the same write-through plus exact revision ACK as the identity tables: `persistChatState` is the durable barrier for authoritative decisions, `saveChatStateInBackground` is the low-priority write for reconstructible values such as a title refresh or an invalidated permission snapshot.

### Chat Q&A and `chat_qa`

- **The authoritative copy is the SQLite `chat_qa` table, and the main thread holds the only hot copy** (`packages/cache/main/qa.ts`). The primary key is the composite `(chat_id, q)` with an additional index on `q`: one question in one chat has exactly one answer, and letting SQLite express that uniqueness means the write path never has to look for duplicates. The whole table stays under 375 rows (managed chats × `CHAT_QA_MAX_PER_CHAT`), so startup reads it in one go rather than paging it like the removal outbox.

- **The per-chat ceiling is enforced independently in three places**: the main thread's `setChatQa`, the Disk I/O Worker before the transaction buffer, and full-table decode at startup. None of the three depends on the others — rows already in the database do not depend on main-thread admission, and a hand-edited database or a restored backup can carry over-limit data that would otherwise make `/qa set` refuse forever with no visible cause.

- **The form is keyed by chat and authorised by its opener.** `/qa set` gates on `isCanControllQaPermission` at the command side and records `openedById` (the visible identity, i.e. `sender_chat ?? from`); every later delivery is then checked only for "is this visible identity that one", with no second permission lookup. Both sides must use the same visible-identity rule — `resolveCommandActor` on the command side calls the very `visibleSenderChat(ctx.msg)` the delivery side uses, and the delivery side takes the id through `visibleSenderId`; a mismatch would mean anonymous admins and channel identities could never fill a form they opened themselves. **Channel identities being able to set Q&A rests entirely on both sides sharing that one rule.**

- **Session object identity governs form closure.** Recheck the current session after awaiting self-sent tracking, field deletion, or form editing. Closure before deletion leaves the message unclaimed. Once deletion begins, the form ingress keeps ownership so downstream processing cannot consume the same message, but a closed session receives no fields or receipts. Only the caller that successfully closes the current session may settle it; expired, replaced, torn-down, or cancelled deliveries cannot register an answer.

- **Form delivery and cleanup share the `qa/notices.ts` boundary.** Failed sends close the session. Register the remote message ID synchronously, handing a late result for a closed session back to deletion. Deletion relinquishes the ID synchronously, so repeated cleanup starts one request. Settlement cleans up after either a completed or failed receipt. Cleanup follows the shared Telegram cancellation and error boundary, without bypassing shutdown cancellation or creating a separate retry queue.

- **The delivery entry must reject the bot's own posts.** In a channel the bot's own post comes straight back as a `channel_post` (see `infra/selfSentTracker.ts`), and the form prompt itself contains the two example lines `问题:` and `回答:` — without the `isBotOwnMessage` guard the form would fill itself from its own example and commit it. The form's own `message_id` is a second guard. For the same reason the entry is registered on `["message", "channel_post"]` rather than `message` alone: a delivery inside a channel is a channel post, so listening only to `message` would leave channels unable to fill a form at all. **The synchronous `isBotOwnMessage` only covers what the main thread sent itself** (the form, the receipts, the board): the update runner is strictly serial, so their `markSelfSent` always lands before the echoed update is even fetched. Worker sends are registered on the main thread at the proxy boundary (see [Outbound requests and message safety](#outbound-requests-and-message-safety)), but that registration happens when the send's response lands, which has no ordering guarantee against the `channel_post` echo. A channel post's visible identity is the channel itself, which equals the `openedById` of a form opened by that channel identity, so the identity guard cannot stop it either. A bounded `needsBotOwnMessageWait` + `waitForBotOwnMessage` rendezvous therefore closes that window, matching `auto/message/index.ts` and `commands/cjkAction.ts`. **These guards are ordered by cost, not by importance**: the entry sits on the per-message spine, so the first step must be the `Map.get` keyed by chat id (numeric key, zero allocation, returns on a miss), with `isBotOwnMessage` behind it — that check is allocation-free too (`infra/selfSentTracker.ts` looks `(chatId, messageId)` up through two levels of integer keys instead of building a composite string), but it costs up to two such lookups per message, still more than the single `Map.get` that returns on a miss here; the cross-thread rendezvous is the most expensive one and therefore sits after every cheap guard and before any side effect. They all merely `return null`, so the order changes nothing about the conclusion, only what each message pays.

- **Code blocks in an answer are persisted as literal ``` fences** (`libs/codeFence.ts`). The Telegram client folds the fences into a `pre` entity before sending, leaving only the block body in the text; the entry restores them into literal fences for storage, and the direct-answer exit unwraps them back into text plus entities. Storing fences rather than entity offsets keeps `chat_qa.data` a single string and leaves the persisted format untouched. **The fences themselves count toward `CHAT_QA_ANSWER_MAX_CHARS`**, or "fits in storage" and "can actually be sent" would diverge at the boundary.

- **The form echo is bounded by the single-message limit too.** Questions and answers carry independent caps (256 / 3840) and arrive in different delivery messages, so the 4096-character limit on one inbound message does not bound their sum — with both fields at their caps the form body reaches 4216. The form is a single `editMessageText`, with **no pagination**, so exceeding the limit buys one 400 and a form frozen on stale content, and the failed result is discarded by `editQaForm` where nobody sees it. `renderQaFormPrompt` therefore truncates the **answer echo** to the remaining budget with an ellipsis; the question is never truncated (it is short, and it is how the author checks what they wrote). Only the echo is clipped — the authoritative value stays in the session, and that is what gets persisted.

- **The board truncates answers and never truncates questions.** `/qa query` clips each answer to `QA_QUERY_ANSWER_PREVIEW_MAX_CHARS` with an ellipsis while listing questions verbatim: a question is the argument to `/qa remove`, and a truncated one deletes nothing. Pages are packed at `QA_QUERY_PAGE_MAX_ENTRIES` (3) rows each, **not by a length budget** — budget packing crams short rows onto a single page, and `buildQaBoardKeyboard` returns `undefined` for a one-page board, so the paging bar never appears at all. A fixed count needs no second length gate: questions are bounded at 256 (enforced by `database/codec/chatQa.ts` on both the write and decode sides) and answers are clipped to 256 by the board preview, so a full three-row page stays far inside the single-message limit. The page number exists only inside `callback_data`, and every click repacks from the hot table — so an old board converges on current facts after a restart, after rows were added or removed, even after a chat was emptied, instead of rendering a snapshot that no longer exists.

- **Question text is trimmed at write time; the hot path performs no normalization.** The direct-answer check sits on the per-message spine and is built to cost nothing when it misses: a chat with no entries returns at the first `Map.get(chatId)` without ever reading `message.text`, and a hit is a second `Map.get` on the original string. Every allocation on this path is confined to the single branch where the first entity is a leading bot mention: two case-folds to compare the username, then one slice to take the body. **Case folding applies to the username only** (Telegram usernames are themselves case-insensitive, matching `infra/updateGate.ts`, `auto/message/facts.ts` and `commands/cjkAction.ts`); the question text still has to match exactly. The check stays synchronous so a miss never allocates a promise.

- **The direct answer runs before the AI triggers** and is not suppressed by `/quiet`: asking a registered question verbatim is a passive trigger, in the same class as a reply or an @mention (see how "Telegram prompt retention" scopes `/quiet`). A hit answers and stops all further handling of that message; otherwise one question would both receive the stored answer and trigger an AI round or a random echo. **Stopping also means neither the question nor the answer enters the AI rolling memory**: the payload handlers register rolling memory inside the AI section, and the direct answer returns before it. That matches how command messages behave — a direct answer is the text the operator stored, not something this round's model produced.

- **The two model-side query tools need no mirror**: the data `group_qa_query` and `group_qa_answer` read rides on the `trigger` message the main thread already sends per round (always present, `undefined` when empty, to keep that message monomorphic), so there is no push protocol and no worker-restart replay. Both tools are mounted every round; when the chat has no entries the round's tool status says so and the query returns an empty list. `group_qa_answer` does not fuzzy-match: a rewritten question returns not-found, because guessing the nearest entry would present an answer this chat never registered as one it did.

- Persistence uses the same write-through plus exact-revision ACK as the identity tables; after a worker rebuild, unacknowledged writes are replayed from the in-memory final values.

### Blocklist and Ad Detection

This section covers the [authoritative blocklist and the block command](#authoritative-blocklist-and-the-block-command), [ad-detection admission, classification, and disposal](#ad-detection-admission-classification-and-disposal), [bans and message revocation](#bans-and-message-revocation), the [blocklist-removal outbox](#blocklist-removal-outbox), [replay after permission restoration](#replay-after-permission-restoration), and [deleted-account detection in the blocklist](#deleted-account-detection-in-the-blocklist).

#### Authoritative blocklist and the block command

- The authoritative `/block` list is the SQLite `blocklist_entries` table. The main thread keeps only recently accessed identities in a bounded LRU plus unacknowledged final values. The blocklist remains a synchronous security boundary: a target's positive/negative policy state must be prefetched before mutation, and the write path publishes the final LRU value before posting its database revision. Reversing that order lets a join update arriving between the steps miss the new block. Entries never expire by time. They are deleted only by `/block disable` or by the automatic removal in [deleted-account detection](#deleted-account-detection-in-the-blocklist). Each row contains a strict complete record with `blockedAt` and Telegram metadata; the optional `participantInvalidCount` means 0 when absent and, when present, must be an integer from 1 to `BLOCKLIST_PARTICIPANT_INVALID_LIMIT - 1`. Out-of-range, non-integer, or mistyped values refuse startup.

  **`/block disable` performs a full unblock by default**: when the row exists, publish the negative cache entry and count, remove the id from pending batches and post the trimmed outbox snapshot, then post the deletion tombstone (`queueBlocklistDeletion`). The Disk I/O Worker handles messages in arrival order and any message can trigger a full-batch commit; with the snapshot first, a committed database never holds a frozen batch referencing a deleted entry, nor a sweep task after the list empties, either of which makes startup recovery refuse to start. When a Worker is rebuilt the two replay at separate domain priorities, and `storageFlushHold` keeps them in one transaction; regardless of row presence, lift the Telegram ban in every chat on the `managedAdminChatIds` list: the origin chat first (when a live check confirms the bot is admin there), then every chat that is `/init enable`d and where the bot is a confirmed admin (`isManagedAdminChat`) — the same list `/block enable`'s cross-chat ban and ad disposal use. The command requires `isCanUnBlock`. Cross-chat unbanning goes through `unbanChatMemberIfBanned` with `only_if_banned: true`, preventing accidental removal of a current member; channel identities use `unbanChatSenderChat`. A batch already running inside the Worker cannot be recalled, which remains a known short window.

  **Insiders cannot be blocklisted**: `isWhitelisted` covers permanent allowlist rows and the always-protected super administrator, and `/block`, `/mute`, and `/batch_kick` reuse that boundary. Temporary membership grants ad bypass only and is outside this permanent-protection boundary. `/white enable` also rejects an identity still in the blocklist. `runProtectedIdentityMutation` serializes "check disjointness + publish authoritative identity value" on one main-thread tail. Only identity checks and authoritative changes stay inside; Telegram effects and durable confirmation stay outside. The block path queues the temporary-activity tombstone before the blocklist final value; the Disk I/O transaction and startup hydration require the blocklist to be disjoint from both allowlists and fail closed on a conflict.

  Startup validates every canonical non-zero safe-integer primary key, strict JSONB payload, and cross-table reference. One invalid row refuses the complete identity database—nothing is truncated, dropped, or guessed. Persisted files still named after ids, such as `memory/wed/<chatId>.json`, retain their canonical-decimal filename checks so zero-padded aliases cannot collide in memory.

  When persistence fails, the `/block` reply must say so out loud: a write error inside the Worker is a `console.error` that by design never reaches `logs/`.
  **The one exception is a stalled daily-luck append**: once consecutive failures reach the threshold the Worker also posts a `luckAppendStalled` diagnostic to the main thread, and the luck owner records one `logger.error` in `logs/` (edge-triggered — one line per outage). It reports not a single failed `write(2)` but the fact that a domain has been losing data continuously, and luck loss is invisible everywhere else: the main-thread `dailyLuckCache` keeps hitting, so users see nothing wrong. There is no recursion risk: that log goes through the log domain, whose own write failures still end at `console.error`.

  **Persistence confirmation is scoped per domain.** `/block` awaits only `flushDiskIODomain("blocklist")`, and the Worker flushes only the SQLite transaction that holds the blocklist (`flushScope` in `workers/diskIO/domainFlush.ts` routes by domain), so an unrelated fault such as a chat whose `memory/wed/<chat>.json` has the wrong owner is neither triggered by this barrier nor makes it report "not written to disk".

  The unified flush at shutdown and before diagnostic rebuilds covers every domain, and its receipt carries `failedDomains` so the main thread can name the domain that actually broke — without naming it, nothing about the real failure reaches `logs/` at all. A single-domain barrier for any shared-SQLite domain commits the whole shared transaction, but its receipt carries only that domain's failure (pending values of that domain still uncommitted, or its rejected-write marker being taken); `all` / `business` report every domain. `flushStorageDatabase` returns commit success only, and `collectStorageDatabaseFailures` appends rejected-write markers to the receipt per domain. AI cache usage statistics (`memory/ai-daily-usage/`) and ad samples are flushed by the unified flush too, but they are side-channel data: a failed write is only `console.error`-ed by the Worker and that batch is dropped, and they **never enter `failedDomains`**. The final shutdown flush must not fail because statistics or samples could not be written.

  **A repeated `/block` is the retry after a failed persist**: when the target is already in the blocklist LRU but still has an unacknowledged `blocklist` revision, `/block` must re-post the final value through `requeueUnacknowledgedIdentityWrite("blocklist", id)` (without creating a new revision) and await confirmation again. Treating `persisted` as true just because "the LRU already has it" tells the administrator success twice while SQLite holds no such row.

  A blocklisted member who joins is always banned rather than merely kicked — the kick-without-ban rule exists to limit collateral damage from automatic anti-raid removal, whereas every id here was written by an administrator by hand.

  Whenever the conjunction **"bot is an administrator AND the chat is `/init enable`d"** holds, one sweep (`sweepBlockedMembers`) must run: when the block was issued the bot had no rights there, so the cascading ban skipped that chat, and the join-time kick only covers later join updates, never someone already sitting in the room. The trigger is the conjunction itself rather than any single update — either side changing counts — so both onboarding orders are covered.

  **The edge may only be consumed when the work lands, never when it is posted.** `recordBotChatPermissions` calls `sweepBlockedMembers` on every confirmed admin observation, and "has this chat been swept" is bookkept in `blocklistSweepState` (`packages/cache/main/blocklist.ts`) from the Worker's `blockedMembersRemoved` receipt — only `complete` records `sweptAt`. Hanging it off the status-change edge means one rate-limit failure leaves those members seated forever.

  Retries ride the same admin observations, which arrive with every join, so the `BLOCKLIST_SWEEP_RETRY_INTERVAL_MS` backoff gate is mandatory — **and that gate must sit in front of the ID-page read**: `readBlocklistSweepPage` is not a local read. It first asks the Disk I/O Worker for a `blocklist` domain flush (which ignores the batching threshold and commits the shared SQLite transaction immediately) and then fetches one page of keys across the thread boundary. Put the gate after that read and, in steady state, every `chat_member` update pays a SQLite commit and a cross-thread round trip for a page `prepareBlocklistSweep` is guaranteed to throw away — ruinous during a join flood. The eligibility decision has exactly one implementation (`isManagedAdminChat` / `isSweepSlotFree` / `canClaimSweep` in `infra/blocklist/sweepEligibility.ts`), shared by `prepareBlocklistSweep`, `sweepBlockedMembers`, `sweepManagedBlocklistChats`, `nextBlocklistSweepAt` and `hydrateBlocklist`; state can still change while the page is read, so `prepareBlocklistSweep` re-checks after the await and the caller's pre-check only removes the round trip that was guaranteed to be wasted. `/init` toggles, demotion and departure all go through `forgetChatBlocklistWork`, which clears that chat's sweep progress **and discards its in-flight batches**, so a re-adopted chat owes a fresh sweep; that step must run **before** the state write.

  Losing admin rights is an authoritative fact Telegram already reported and is not revoked by a failed `chat_states` write — but if the write rejects, the process exits with the persisted `botPermissions` snapshot still saying `isAdministrator: true`, startup recovery's filter cannot drop those batches, and the doomed removals are reposted on every restart and every Worker respawn. By the same rule, `resolveBotAdminStatus`'s fail-closed "treat a failed lookup as not-admin" covers the `getChatMember` call only: a state-persistence rejection must propagate unchanged.

  Folding it into "not an admin" makes callers skip the entire join guard (that `new_chat_members` batch gets no verification window, no message tracking, and no timeout kick) while the only diagnostic blames the Telegram API and the next call reads `true` back from memory, leaving the symptom unreproducible. **`sweptAt` is a latch, and there must be a path that opens it**: `requestBlocklistResweep` (`packages/infra/blocklist/sweep.ts`) resets it to null on any signal that blocklisted members are still in the chat — a failed `banChatMember` during `/block`, or a join-time removal receipt with `complete: false`.

  Without it, that person sits in an already-swept chat until the process exits: the join-time kick only covers later joins, and the sweep is blocked by the latch. If a batch is in flight the request may only record `resweepRequested` instead of touching `sweptAt` directly — that batch's `complete: true` receipt can arrive after the request and would write `sweptAt` back, dropping it.

  A resweep triggered by a failed join-time removal must carry backoff: a blocklisted account can rejoin repeatedly, and resweeping immediately on every failure is a request storm of O(blocklist size) probes. That backoff must also grow linearly with the chat's count of **consecutive unsettled sweeps**, up to `BLOCKLIST_SWEEP_RETRY_MAX_INTERVAL_MS`, with a `complete` receipt resetting the count.

  **That count must be advanced by every unsettled path, not just by the receipt**: after the three degraded paths in `sweepBlockedMembers` (the outbox refusing the entry, the delivery boundary throwing, and **delivery resolving normally while posting nothing at all**) no receipt will ever arrive to advance it (the claim is already cleared, and a late receipt takes the resweep-request path that leaves the count alone), so missing them means that while the executing owner keeps throwing — Worker unavailable, outbox full — every round is scheduled at the base interval and never reaches the cap, each round burning another outbox id and another error log.

  **The third is the sneakiest, which is why the executing owner must report how many messages it actually posted** (`BlockedMemberRemover` returns `Promise<number>`): when a concurrent `/block disable` keeps reshaping the outbox across `BLOCKLIST_REMOVAL_RECONCILE_MAX_ROUNDS` rounds, durable reconciliation withholds the entire `removeBlockedMembers` batch, a pure sweep batch is left as an empty array, and the delivery path early-returns on `length === 0` and resolves normally — nothing thrown, and nothing in flight either. Zero delivery must run the same aftermath as a throw (void the claim, record `delivery-boundary`, advance the backoff); trusting "it did not throw" leaves `removalId` at its old value while the receipt never comes, so `prepareBlocklistSweep` early-returns for that chat forever and it is never swept again for the lifetime of the process — only a full restart recovers it through `hydrateBlocklist` + `replayPendingBlockedRemovals`.

  **"Missing permission" must be a distinct failure class**: backoff still means retrying on a timer, but without ban rights a retry changes nothing except reprinting the same error and paying for another O(list length) sweep. `banChatMemberWithOutcome` (`packages/infra/telegram/actions.ts`) separates it from Telegram's response — every 403 counts, while 400 counts only when it names `not enough rights` (a 400 "user not found" must not, or a retryable batch would hang forever waiting for an authorization that will never come).

  The first id that hits it ends the remaining attempts.

  **But `forbidden` itself still conflates two causes and must be split once more**: Telegram answers "the target is an administrator of this chat" with that very same 400 `not enough rights`, and folding it into `permissionDenied` means one un-bannable admin latches the **entire chat's** sweep shut forever — sweeps early-return, resweep requests are refused, every Worker respawn skips the replay, and the only unlock edge is "the bot's ban rights changed", which is never going to happen.

  The Worker therefore confirms that one id with `probeChatAdmin` after a `forbidden`: a confirmed administrator **settles that target alone** (one named log line, the rest of the batch proceeds, and the batch settles as usual), while an inconclusive probe keeps the original verdict — without confirmation a chat-level latch is never downgraded into per-target retries.

  **But "this batch need not be re-sent" is not "this chat is clean"**: the receipt must carry a separate `targetIsAdmin` flag orthogonal to `complete`, on which the main thread declines to stamp `sweptAt` and keeps accumulating that chat's consecutive-failure count (without accumulation, one long-standing blocklisted administrator pins a full-list resweep to every five minutes).

  Without that flag the latch closes at the very moment the batch reports success: once the target is demoted to an ordinary member no sweep will ever clean them up again, while the bot claims they are blocked.

  A genuine permission failure carries `permissionDenied` back to the main thread, which records the mark in two places: `blocklistSweepState.permissionBlocked` in memory stops that chat's timed retries, fresh sweeps and Worker-respawn replay, while the durable outbox records the sweep batch as `missing-permission` and settles named batches such as instant kicks and ad disposals outright (the full-list sweep re-armed on the permission-restored edge clears blocklisted members still in the chat, and keeping those batches would only let a permission-less chat's batches pile up in the outbox with every join or ad disposal) — `missing-permission` is the only self-explanatory marker a stuck batch has, telling an operator to grant rights rather than to inspect the network or the disk.

  **If the chat has no sweep record yet, a minimal one must be created rather than dropping the mark**: sweep records are only ever created by `sweepBlockedMembers`, and a chat where the bot never had `can_restrict_members` is exactly the case that needs the mark most — without it the join-time permission refusal is never recorded, `replayPendingBlockedRemovals` re-posts that doomed batch on every Worker respawn, and the unlock edge has no record to unlock.

  Only one edge clears it: a *confirmed* ban-permission observation (a `my_chat_member` update or an on-demand `getChatMember`, see `packages/infra/botAdmin.ts` and `canRestrictMembers` in `libs/chatMember.ts`). When the permission bit is unavailable — the path that merely infers "I am an administrator" from someone else's `chat_member` update — the chat stays blocked; "not observed" must never be read as "has rights", and observing that rights are still missing does not clear it either.

  Being an administrator and being able to ban are different things, and an admin promotion without the restrict right is the most common cause of this state. A fixed interval cannot contain a target that can never be banned — when the target is itself a chat admin, or the bot is an admin without ban rights, every sweep is doomed, which means resweeping the entire list every five minutes for the life of the process. Those bans share the `kick` 429 category with verification-timeout kicks and accumulate together under a real cooldown.

  The cap is equally mandatory: the latch must always have a path that opens it, so a repaired permission must not have to wait for a process restart.

  **Removals have no state machine, so replay is their only way to survive.** Each batch is numbered by `trackBlockedRemoval` and mirrored in `pendingBlockedRemovals`, and an Anti-Raid Worker respawn reposts the whole table (repeated bans are idempotent, a dropped one means the person stays).

  **A mirror entry may be deleted only after the task completes or authoritative state makes it obsolete**, in four classes: a `complete: true` receipt; authoritative cancellation (`/block disable` removes the user or the chat loses supervision); the chat's sweep batch being superseded by a fresh sweep (the list only grows, so the new snapshot is a superset of the old batch); or a named batch rejected for missing ban rights, which the full-list sweep after the permission is restored takes over. When the mirror has confirmed `canRestrictMembers === false` for the chat, the Worker sends no bans or admin probes and acknowledges the whole batch as permission-blocked right away, while join counting and join-notice cleanup proceed as usual.

  Omitting the last two is unbounded growth: a chat lacking ban rights deposits a full `userIds` copy every backoff window, and every Worker respawn reposts all of them.

  **A throwing post call must not delete the task either**: `post()` returning false only proves the Worker did not receive it; the durable outbox remains a recovery boundary independent of Telegram update redelivery. On a barrier timeout or persistence failure the Worker may already be executing it, and deleting the mirror in any of these cases destroys cross-process replay.

  Before the catch writes `blocklistSweepState` back it must also reconcile that the `removalId` is still its own, or it stomps the `sweptAt` written by a receipt that arrived first.

  **Conversely, any path that discharges a batch instead of settling it must release that in-flight claim itself** (`releaseSweepClaim`): a non-null `removalId` is the only evidence that "this chat has a batch running", `sweepBlockedMembers` returns early on it, and after a discharge the receipt never arrives — the chat becomes unsweepable for the rest of the process, and `requestBlocklistResweep` cannot rescue it either (while a batch is in flight it only records `resweepRequested` and leaves `removalId` as it is, precisely because that path assumes a receipt is still coming).

  Release only `removalId`: `sweptAt` stays as it was (this batch never swept, so the debt stands) and `nextRetryAt` keeps the backoff written at dispatch, so a discharge does not immediately buy another sweep.

  **"Did not fully settle" must be logged, and that log must come before the `removalId` reconciliation**: a join-time batch does not match the sweep progress and returns early, and that path has no verification window to fall back on — a failure there is the entire reason the person is still in the room.

  **Loss of supervision is decided authoritatively by the main thread**: the Worker's `blocklistRemovalEpochs` lives only inside the isolate, resets to zero on respawn, and cannot gate a replay.

  Inside the Worker each id is retried with backoff up to `BLOCKLIST_REMOVAL_MAX_ATTEMPTS` — a blocklisted join opens no verification window and has no timeout kick to fall back on, so this removal is the only chance — and a membership probe **only skips on a confirmed absence**; a failed probe still bans (banning someone already gone is idempotent, skipping them is a silent pass).

  Sweeps run in `BLOCKLIST_SWEEP_BATCH_SIZE` batches that yield between batches, and every id re-checks that chat's removal epoch (`packages/cache/workers/antiRaid/blocklist.ts`): once the chat is `/init disable`d or the bot is demoted, an in-flight batch abandons immediately. The join-time path posts no `join`, so its removal message must carry `joinedAt` and the join announcement id — the Worker records the anti-raid join count and deletes that service message on its behalf.

  **But the count is recorded at the Worker's own observation time, not at `joinedAt` itself**: `joinedAt` is taken on the main thread *before* the durable outbox flush, so it necessarily precedes the joins the Worker has already recorded from its own clock, and the sliding window treats the timestamp it is handed as "now" — by contract it discards every queued entry that lands in the "future" as a clock rollback, so one back-fill wipes out the real joins recorded in the same batch and the threshold can never be reached.

  For the same reason a back-fill whose `joinedAt` already slid out of `JOIN_WINDOW_MS` is dropped outright: cross-process replay (startup recovery, Worker respawn) carries the previous process's join wave, and aligning it to now would invent a join that never happened.

  **But `joinedAt` may be carried only once per physical join.** The same join is claimed by both the `chat_member` and the `new_chat_members` path (both must be intercepted — a chat that hides join messages only delivers the former, and the former only arrives at all with admin rights), while ordinary joins are deduplicated by `joinCreatesNewRecord` and this path has no such gate.

  Carrying it on both means `recordJoin` runs twice, which effectively halves `ANTI_RAID_PER_MINUTE_LIMIT` for blocklisted accounts, forces the whole chat into lockdown early, and strips ordinary members of their right to speak along with it.

  Deduplication is keyed on `(chatId, userId)` in `recentBlockedJoinCounts` (`packages/cache/main/antiRaid/blocklistGuard.ts`), windowed by `JOIN_WINDOW_MS` and bounded by `BLOCKLIST_JOIN_DEDUP_MAX_ENTRIES`; the announcement id is still carried on both, because deleting an announcement is idempotent.

  **A failure to register the join-time removal (outbox full, id space exhausted) must degrade in place; the exception must never escape `claimBlockedJoiner`**: it runs inside update middleware, so throwing fails that update, holds back the offset, exits non-zero, and systemd restarts into the same update — a restart loop that can only be broken after stopping the service and repairing SQLite `pending_blocked_removals`, and a full outbox is usually the work of batches that can never be banned in the first place.

  Degrading means logging it by name, making that chat owe a sweep again, and still reporting "handled as blocklisted" — the list decision has not changed, so the member must not get a verification window instead.

  **A blocklisted joiner's removal *replaces* the `join` rather than accompanying it, so cancelling the removal must put that `join` back** (`ClaimBlockedJoinerParams.replacedJoin`): `claimBlockedJoiner` deliberately does not queue a `join` on a hit — the Worker will not open a verification window for someone about to be kicked.

  But that batch can still be deleted wholesale by a concurrent `/block disable` (`forgetUserBlocklistRemovals`) while the write-ahead flush is awaited, and `reconcileBlockedRemovalMessages` simply drops any message whose authoritative params are gone: without the fallback the joiner ends up with neither a removal nor a verification window — no reminder, no timeout kick, a missing raid-window join count — and nothing in the system ever opens one for them (worse on the `chat_member`-only path, where the whole batch becomes empty and nothing is posted at all).

  **Only the "batch actually vanished from the authoritative mirror" case needs the fallback**; the reconcile-exhausted case must not use it — the task is still in the durable outbox and the user is still slated for removal, so opening a verification window there would let someone still on the blocklist in.

  **This contract covers the whole delivery path, not just `claimBlockedJoiner`**: when `prepareDurableAntiRaidMessages` exhausts `BLOCKLIST_REMOVAL_RECONCILE_MAX_ROUNDS` it must not throw either — it is reached through `postAntiRaidDurably` from the same update middleware, so throwing is the same restart loop, and the trigger (a concurrent `/block disable` repeatedly trimming the same batch) still holds after redelivery.

  Nor may it fall back to posting the last reconciliation, which could contain a batch `/block disable` just cancelled — the very thing this reconciliation exists to catch. The correct degradation is to withhold the removal messages entirely, post the non-removal ones, log one error, and make the affected chats owe a resweep; the tasks themselves stay in the durable outbox and are not lost.

  **Decision and execution are split across threads.** The decision stays on the main thread — the list is main-thread state that the Anti-Raid Worker has no copy of, and it must be made before the join is posted, otherwise the Worker opens a verification window for someone about to be removed.

  The Anti-Raid Worker owns the business ordering of every membership probe and ban, sharing the same owner as verification-timeout kicks; each Telegram capability request then crosses the duplex boundary back to the main thread and enters the query or kick 429 lane. Returning blocklisted accounts and promotion sweeps still cost O(blocklist size) Bot API requests, but backoff in either category does not pause ordinary messages or unrelated categories.

  Removal messages travel with the same batch of join/left messages through `postAntiRaidDurably`, so the update is handed over only after the Worker drains its mailbox. The Worker runs the business steps asynchronously after dispatch and does not block its mailbox; only the main thread's unique client starts the Telegram HTTP, while the main-thread update handler does not await the full sweep. The infra layer must not statically depend on Anti-Raid business modules: the execution owner is registered into the single slot in `packages/cache/main/blocklist.ts`, mirroring `infra/chatTeardownRegistry.ts`.

  **The `/block` command's own cross-chat cascading ban is an explicit exception to this thread split**: after validating, writing the blocklist entry, and confirming persistence within the current update, the handler hands the fan-out together with the report to the background lane of the deferred command executor (`commands/blocklistFanOut.ts`), where the main thread performs `isChatMember` → `banChatMember` in order within each chat (on the default `bot.api`), while `runBoundedSettledBatch` runs at most five chats concurrently and settles each independently. Every result retains the chat id and input index; an unexpected rejection marks only that chat failed and hands it back to the sweep, without discarding outcomes already settled for other chats. Cleanup of the known replied-to sender-chat message is settled independently as well. This is necessary because the report distinguishes "kicked out" from "ban confirmed" per chat while the current Worker receipt carries only `complete`, so posting it to the Worker would lose the per-chat outcome.

  Every command performs a live membership lookup and retains no “previously confirmed kick” cache. Current absence proves only that this invocation did not remove the target; it cannot prove that the target never joined. The ban request is always resent regardless of the lookup result so Telegram applies `revoke_messages`.

  Before submission the fan-out takes a place, in command arrival order, in the per-identity blocklist queue (`runBlocklistIdentityMutation`) and starts only when its turn comes, so successive commands and ad disposals for the same identity settle in arrival order; when the executor is full or no longer admitting work it runs in place, still behind any same-identity fan-out waiting in the executor, and the executor releases the place when it cancels a task before it starts. The fan-out runs after the update is acknowledged: if shutdown cancels it or the process crashes, chats not yet handled are banned from the list by the full-list sweep after startup, and the report is not resent. The per-chat unbans of `/block disable` have no such persistent fallback and still complete within the current update, in the same queue turn as the list removal, before the reply. The cost is another membership lookup on repeated commands and no immediate retry for a failed call. This is accepted for a low-frequency administrator command to avoid stale cross-chat state. `requestBlocklistResweep` covers failures: chats where the ban failed owe another sweep and are re-swept on the next admin observation. This exception covers only `/block`; join-time kicks and sweeps are still always posted to the Worker.

#### Ad-detection admission, classification, and disposal

- `/ad_detect` ad detection is a **best-effort heuristic**, not a security boundary — but its disposal carries the exact weight of `/block`, so the boundaries must be drawn precisely.

  Submission is gated on a conjunction: the chat has `ChatState.isAdDetectEnabled === true`, the bot is an administrator there (the same `resolveBotAdminStatus` decision the join guard makes — without admin rights the ad cannot be deleted nor the sender banned, so a verdict would just burn quota), and the sender has no ad-detection bypass. The bypass depends on the individual `isCanBypassAdDetection` permission: setting it to false still permits classification, and the Worker may delete that detected message bundle. `SUPER_ADMIN_USER_ID` always holds it and therefore always bypasses, so the decision point no longer compares the identity separately.

  **The toggle itself must be re-read inside that same critical section.** The verdict is produced on the Worker; once it reaches the main thread it still has to queue behind the identity serialization before the blocklist write, and an `/ad_detect disable` can land in that gap — yet all it can clear is the Worker's not-yet-judged queue, never a verdict already published. Without the re-read, turning the feature off still ends with someone written into the permanent blocklist, banned across every managed chat, and named in a public notice. The check must sit immediately before `blockUser`: past that point the write is irreversible, and backing out later would leave a durable blocklist entry with no enforcement behind it. This is an expected race outcome, so it logs normally and never consumes the protected-sender alert.

  **Allowlist membership still protects the permanent blocklist unconditionally.** When a verdict returns to the main thread, disposal re-runs `isWhitelisted` inside the same `runProtectedIdentityMutation` critical section used by `/white` and `/block`. Whether the sender joined the allowlist while the verdict was in flight or was already allowlisted with bypass disabled, `blockUser`, cross-chat bans, and the ban announcement are refused; only the bundle deletion already completed by the Worker remains.

  An anonymous administrator wearing the current group as a costume (`sender_chat.id === chat.id`) is skipped for the same reason as in `/block`: Telegram never reveals who is behind the costume, so disposal could only try to ban the whole group identity.

  **Linked-channel auto-forwards (`is_automatic_forward`) and the bot's own posts bouncing back (`isBotOwnMessage`) are skipped too**: the sender of such a message is the channel itself, so disposal takes the `userId < 0` path and calls `banChatSenderChat` in every managed chat — one promotional channel post would tear the whole comment section out by the roots, and a post the bot itself made in its own channel could get that channel blocklisted.

  Whether a channel post is acceptable is the channel admins' call, not the discussion group's ad detector.

  **The bot's own inline results (`via_bot` pointing at itself) are classified on the query source text, never on the body that landed in the chat — and this applies to every inline feature alike**: a real person sent that message, but the body is rendered end to end by the bot. Gag runs `renderGagSpeech`, which **generates** the text by sprinkling random dots and substituting characters per grapheme cluster — landing squarely on rule B, "contact details or keywords deliberately deformed … seeing it is almost enough to answer true", the single strongest signal in the ruleset — while the hidden profile marker on the speech prefix is a `t.me` link that also satisfies rule C, "a landing point that takes people out of this group". Fortune is a greeting, a draw result, and an anti-forgery receipt, of which only the wish line was written by the user. Classifying the rendered output means blocklisting people one at a time for the bot's own formatting. This path swaps the classified text only: the message id, the sender identity, and disposal are unchanged, and what gets judged an ad is still that real message.

  The source text is obtainable only **at answer time** (Telegram never puts the inline query into the landed message and offers no field linking the two), so each feature calls `recordInlineResultSources(speaking identity id, source text, this answer's results)` after `answerInlineQuery` settles. When the Bot API explicitly rejects the answer with a 4xx (including 429, `isTelegramRequestRejected`), nothing is registered and the previously delivered registration stays; network failures, 5xx and other failures after which the results may have been delivered still register. Updates are processed serially, so a landed message is never handled before its registration. The speaking identity is the sender the results land under: the session target for gag (the user or the channel), the querying user for fortune. Ad detection looks only in the sender's own registration (`sender_chat?.id ?? from.id`) and matches the landed body there (`inlineResultSourceOf`); it never consults another identity's registration. **Every new inline feature must do the same**: skipping registration breaks nothing, but its results will never resolve a source text and therefore never enter ad classification. What is registered is a source of classified text and nothing else — it must never gate, bind, or authenticate a message.

  **One entry per speaking identity, overwritten wholesale, no history**: an inline query arrives on every keystroke and only the results of the last answer can actually be sent; the several results of one answer (the same person gagged in several chats at once) share one source text and must be registered together. Capacity is capped hard at `INLINE_RESULT_SOURCE_MAX_AUTHORS` (inline mode is open to anyone, so nothing else bounds how many identities are being typed for at once), and the least recently registered identity is evicted when it fills. The landed body must match a registered result body **byte for byte**: clients occasionally send the result rendered for the previous keystroke, and sending one query then immediately opening the next overwrites the registration, and in both cases treating the source as unavailable beats judging a real message by a different piece of text. **No source text always means no classification** (never registered, evicted by capacity, process restarted after the answer, body mismatch): missing one ad beats letting the bot's own rendering reach the classifier. An answer with an empty source text is likewise not registered, because no word in such a result was written by the user (a plain fortune, the probability card, the rate-limit notice).

  **That exemption must cover the quoted text as well**: in a discussion group every top-level comment's `reply_to_message` is that same channel post, so skipping only the post itself while copying its body into the quote context (`sampleQuote` / `sampleReplyTo`) means judging every commenter against the channel's own promotional copy — one channel promo could blocklist the entire comment section one member at a time, none of whom typed a word. `quote` is an excerpt cut from the replied-to message, so it is dropped along with it.

  **Chat administrators and owners are never disposed of**: disposal carries the full, irreversible weight of `/block` (permanent list + a ban in every managed chat + `revoke_messages` wiping recent messages), while an admin forwarding a partner's link or joking "add me on WeChat" is more than enough to read as promotion.

  The gate is two-stage — enqueue-time filtering against the Worker's admin cache (`freshAdminIds`) keeps known admins out of the quota, and a verdict is re-confirmed against `getChatAdministrators` before disposal, where **an inconclusive answer always means "do not dispose"** (letting one ad through costs far less than banning the group owner, and the next message re-enqueues anyway, by which time the cache is warm).

  **Both the verdict and its side effects run on the Anti-Raid Worker thread**: the main thread only performs the synchronous gate plus one `post` (not `postAntiRaidDurably` — the pending queue lives and dies with the isolate, so a cross-thread barrier per group message would buy no recovery whatsoever), and a rejected post does not fail the update; it is logged only on the edges where delivery turns from possible to rejected and back again (`adCandidatePostRejected`).

  **The queue holds only sender keys** (`chatId:senderId`); anything the same sender says while waiting joins the same `pendingAdMessages` bundle and does not take another queue slot; `pendingAdMessages` is a two-level numeric map from chat id to sender id, the key string lives only on the bundle's `key` for the queue, the entry count is kept in `pendingAdBundleCount`, and reads and writes go only through the accessors in `workers/antiRaid/adDetect/queueState.ts`. Pending ownership is represented jointly by `pendingAdMessages`, `adDetectQueue`, and `queuedAdDetectKeys`, which must be updated together — **the decision of whether to touch them lives in `packages/states/adDetectAdmission.ts`** (four pure gates: submission, requeue, capacity, in-flight), and the runtime only executes the verdict;

  shaping the bundle itself (trimming, capping, formatting the text sent for classification) lives in `packages/workers/antiRaid/adDetect/bundle.ts`, which guards a different invariant: only already-judged entries may be evicted; `AD_DETECT_MAX_PENDING_SENDERS` is a hard ceiling of 8,192 distinct keys — the number answers "how much can be resident and still survive", not "how many senders can be accepted": multiplied by the per-key message ceiling (`AD_DETECT_MAX_MESSAGES_PER_SENDER`, 15) and each entry's body/URL/sample-context ceilings it is the resident upper bound of the Anti-Raid Worker isolate, and join verification, lockdown and blocklist enforcement all live in that same isolate, so an OOM takes them down together with the best-effort heuristic. The two numbers were tuned together; changing either one means recomputing that product.

  At capacity, the 8,193rd new key is rejected before any Map, queue, or Set is mutated; an already accepted key is never evicted FIFO, while later messages for that key still merge under the existing per-key message and character budgets. An accepted key has no waiting TTL before at least one verdict attempt, and a periodic sweep may not remove it.

  Losing chat management, `/init disable`, `/ad_detect disable`, and Worker shutdown are the valid cancellation boundaries and must remove the key from the Map, queue, and related Sets together.

  **A failed delivery of that cleanup must be absorbed by the command itself and must never escape the update handler**: `post()` returns false only when the Worker has exhausted its restart budget or is respawning, and in both states the pending queue died with the old isolate, so there is nothing left to clear;

  letting it throw costs real damage — the toggle is already persisted, yet the update is marked failed, the offset is withheld, the process exits non-zero, and after the restart Telegram replays the same `/ad_detect disable` while the Worker is still unavailable, welding the restart loop shut (the same handling `/ai_chat disable` gives `invalidateAiChat`). **"This key holds a pending-dispatch slot" is expressed solely by `queuedAdDetectKeys`**, mutated in lockstep with `adDetectQueue` and released the moment a key is shifted out; dedup, capacity and requeue all read that one table. A key occupies at most one queue slot, so the queue's length is inherently bounded by the pending table's 8,192 ceiling, and the requeue gate neither needs nor may carry a separate capacity clause.

  The Anti-Raid Worker writes its own `performance.now()` to `recentlyDisposedAdKeys` immediately before dispatching disposal and uses the same clock for the 90-second TTL. Queue time and wall-clock changes do not affect this window. `setBoundedMapValue` caps the map at 8,192, evicting the oldest disposal when full. Reads expire stale keys; the periodic sweep reclaims dead records without adding a full-table scan to detection ticks.

  Every `AD_DETECT_QUEUE_TICK_MS`, the scheduler takes at most `AD_DETECT_BATCH_SIZE` keys from the one global FIFO and is additionally bounded by the global `AD_DETECT_MAX_IN_FLIGHT` gate; neither gate allocates quota per chat, and accepted keys blocked by the in-flight ceiling stay queued until capacity recovers.

  The 90-second `AD_DETECT_JUDGED_RETENTION_WINDOW_MS` limits only disposal suppression and consumed context — it is **not** "how often one sender gets judged"; repeat enqueueing is blocked by `queuedAdDetectKeys`, independent of any clock: unconsumed entries with `seq > checkedSeq` survive for any queue wait, while only consumed context with `seq <= checkedSeq` may be trimmed outside the window; **the periodic sweep must re-enqueue any key that still holds unconsumed content while sitting in neither the queue, nor in flight, nor under a claim** — claim-driven expiry cannot see such a bundle, and without that fallback it loses its scheduling slot permanently. `checkedSeq` is a monotonic “consumed through here” marker and trimming may not roll it back.

  Those 90 seconds are **not** "how often one sender gets judged": the claim is released the moment a key is dispatched and re-established as soon as a verdict settles with unjudged content left, so a continuously talking sender is judged once per "one tick plus one classification round-trip". The thread-wide request ceiling comes solely from `AD_DETECT_MAX_IN_FLIGHT` and the per-tick `AD_DETECT_BATCH_SIZE`; size provider quota against those two numbers, not against this window.

  **The submission character budget (`AD_DETECT_BUNDLE_MAX_CHARS`) only decides "how far this tick judges", never "which messages get judged"**: unjudged content is always packed starting from the oldest entry, whatever does not fit waits for the next verdict (the requeue that follows settlement), and any leftover budget is then filled with the adjacent already-judged context; the marker may only advance to the last entry actually submitted.

  Walking back from the newest entry instead is wrong — messages the budget excludes end up below the marker, get recorded as "judged" along with it and are then trimmed away, and the per-key message ceiling (15 entries x 512 chars = 7,680) is still wider than this budget (4,096), so one run of long messages is enough to trigger it. That is a missed verdict with no log trace anywhere, which is exactly what this rule forbids.

  **The per-sender message cap (`AD_DETECT_MAX_MESSAGES_PER_SENDER`) may likewise only evict consumed entries**; a burst can fill it before the first tick arrives, and then only unjudged entries remain to drop — their text is discarded but their message ids must move into `AdMessageBundle.pendingDeleteIds` (bounded by `AD_DETECT_MAX_PENDING_DELETE_IDS`; on overflow drop the oldest and log an error). **Discarding never-judged text must itself log an error** — once per sender, since past the cap every new message evicts another one and logging each would be its own flood. That content never reaches the classifier, making this the module's only content-level missed verdict; without the log, operators see only that detection looks lenient and cannot tell whether the model let it pass or the text never arrived. A 15-entry cap makes this path far from rare, so the trace is mandatory.

  Without that hand-off those messages reach neither the classifier nor the disposal delete set — the judged snapshot and the live bundle both miss them — so once the sender is flagged they stay in the chat forever, especially for channel vests (`banChatSenderChat` has no `revoke_messages`).

  **The union can therefore exceed the 100-id per-call ceiling of `deleteMessages`, so the caller must shard it**: that endpoint reports only whole-batch success, so handing it the full list gets the entire batch rejected and nothing deleted — worse than not carrying the ids at all.

  **A failed verdict counts as "no verdict this time" and marks the batch checked**: never guess `true` and never retry indefinitely (a provider outage would become a per-second request storm). Response parsing accepts only a real boolean `true`.

  **The quoted excerpt (`quote`) and the replied-to message must be submitted together with the body.** The dominant way ads are posted is: send a perfectly normal message that passes detection, edit it into an ad some time later, then resurface it with a reply or a quote — the ad body is never in any new message's `text`. Editing does not re-enqueue a verdict, so "the original was already judged when it was posted" does not hold for the edited content, and reading `text` alone leaves that route completely immune.

  **The collateral cost is known and deliberately accepted**: a member who quotes an ad to complain about it gets judged too — the classifier cannot separate "quoting an ad to denounce it" from "using a quote to resurface it", so it errs toward over-blocking, and the topical calibration stays with the deployment's `config/dynamic/ad_samples.json`.

  **One excerpt is kept only on the earliest entry that claims it** (`claimSampleContextParts`): the whole point of bundling is to gather split-up fragments into one submission, and that posting style almost always replies to the same message every time; copying the excerpt per entry lets a single entry consume the full body + URL + context quota, eating nearly half of `AD_DETECT_BUNDLE_MAX_CHARS` on duplicates, so fragments that belong in one verdict get cut across several rounds where the model only ever sees one individually harmless piece.

  Later messages still get selected on their own bodies and still read the same complete excerpt. The sample copy is **not** deduplicated — a verdict only needs to read it once, but the evidence must record what each message actually quoted. For the same reason a message counts as having nothing to judge only when body, URLs and context are all empty: the message that resurfaces the ad may well type nothing at all (a sticker, an uncaptioned photo).

  Conversely, URLs inside `text_link` entities must be appended to the submitted text: a hyperlink's visible words can be entirely innocuous ("click here") while the landing page exists only in the entity, so skipping them disables the hardest rule — "does this drag people out of the group" — for every ad that hides behind a hyperlink. **The one exception is the bot's own inline results (`via_bot` pointing at itself)**: those messages go out with explicit `entities` and whatever the user typed is plain text (a bare URL auto-detected by Telegram arrives as a `url` entity, not the `text_link` read here), so every `text_link` on them was attached by the bot, and appending it would invent a "landing point that takes people out of this group" for every fortune result. A link the user typed into the query stays in the source text and is classified as usual.

  URLs must cross the thread boundary **separately from the body, each with its own character budget** (`AdCandidateMessage.linkUrls`; the Worker appends them after truncating the body at `AD_DETECT_MESSAGE_MAX_CHARS`): if the main thread concatenated them onto the tail, the Worker's head-preserving truncation would cut off exactly those URLs — seven hundred characters of filler plus one hyperlink labelled "click here" is a zero-cost bypass.

  What is appended is the URL the message itself carries, with no system wording, so it introduces no forgeable structure into the body.

  **Senders already on the blocklist are never submitted again** (`isUserBlocked` in the submission gate): their removal is already queued, and they are still talking only because the ban has not landed yet — another verdict burns quota and buys a disposal identical to the previous one.

  **Only real users may be dropped on the main thread, though**: `banChatMember` carries `revoke_messages` and wipes the gap-window messages when it lands, while a channel vest is banned via `banChatSenderChat`, which has no such flag — dropping it on the main thread means every ad it races out has no cleanup path at all and stays in the chat permanently with no log line.

  Channel vests are therefore still submitted to the Worker, carrying the "already listed" fact along in `AdCandidateMessage.blocked` (the blocklist is main-thread state; the Worker has no mirror), and the submission gate turns that into `deleteStraggler` — deleted, but never charged against the verdict quota.

  This is the same exception as the `recentlyDisposedAdKeys` suppression below, only over a longer window: that one lives for a single dedup window, whereas "listed but the ban has not landed" can span windows and is not produced by this verdict alone (instant kicks, resweeps and removal batches queued in an earlier window all write the list first and then wait on the outbox flush and the mailbox barrier).

  The Worker adds a second, same-window suppression (`recentlyDisposedAdKeys`): a key judged as an ad is recorded the moment disposal is dispatched, covering the messages that slip in during the cross-thread gap between "disposal sent" and "main thread has written the blocklist entry"; each key expires on its own TTL. Blocklist enforcement reclaims it early once a ban is confirmed, but that reclamation must run **after** the removal receipt is published — a best-effort cleanup must never be able to veto an already-settled result, and placing it first means one throw rewrites the receipt as incomplete and makes the main thread redeliver a batch that actually finished.

  **For channel identities that suppression covers the verdict only, never the deletion**: `banChatSenderChat` has no `revoke_messages`, so that ban cannot take those messages with it, and no second verdict will run while suppression holds — without an extra delete inside the suppression branch, those ads stay in the chat permanently.

  **A repeat hit must not rerun the full disposal**: full disposal waits for one durable blocklist transaction and registers a snapshot-revision removal task per administered chat. Letting the same sender trigger it through repeated messages would repeat cross-thread traffic and database diffs in proportion to chat count.

  So when `blockUser` returns false (already listed), only the triggering chat gets a batch and durability is not awaited again. The first hit put the entry in the blocklist LRU and registered an unacknowledged revision; a failure is already named in the log, and Disk I/O Worker respawn replays the final value from the bounded unacknowledged map. Other chats' batches remain in the SQLite outbox awaiting retry.

  This does not conflict with `/block`'s retry semantics — there a repeat call is an administrator retrying after fixing the disk, whereas here it is the flooder driving it, and the two must not share the same cost. That single batch still passes the `isInitEnabled && botPermissions.isAdministrator` filter, since the bot may have lost administrator rights between the two hits.

  **Disposal is split across threads** exactly like the blocklist: the Worker deletes that bundle's messages and posts `adDetected` back; the main thread performs the part that must not be lost — `blockUser` plus `flushDiskIODomain("blocklist")`, then one `trackBlockedRemoval` batch per chat on the `managedAdminChatIds` list shared with `/block` (origin chat first, every chat `isInitEnabled && botPermissions.isAdministrator`), handed to the removal owner registered in `blockedMemberRemoverHolder.current` and delivered back to the Worker through the durable outbox, and finally the in-chat announcement.

  **The announcement must be sent only once the enforcement result is known**: its text asserts the sender was banned across every watched chat, yet registration can end with zero chats (a full outbox, a just-revoked admin status, `/init disable`), in which case nobody was removed and posting it would contradict what actually happened — with zero registrations it switches to asking an admin to check the bot's permissions.

  **A partial failure may not claim "every" chat either**: the sender is still sitting in the chats that failed, and the only trace is one error log nobody reads, so the text must report how many chats were actually enforced and name the shortfall — a guard that only fires on total failure still reports "two of three chats could not be enforced" as "banned across every watched chat".

  This is the same reasoning behind the Worker skipping the announcement when its channel back to the main thread is closed, except that half is satisfied automatically because the main thread never receives the event. The announcement goes through the unified temporary-message boundary `sendTemporaryMessageOnMain` (`infra/telegram/temporaryMessage.ts`), which registers its deletion after `COMMAND_MESSAGE_AUTO_DELETE_MS` in the same synchronous step that obtains the message id, so no permanent notice is left behind; as a bot-initiated announcement it carries no topic.

  Those main-thread tasks are registered in `inFlightAdDisposals` (`packages/cache/main/antiRaid/adDisposal.ts`) and awaited by every `drainAntiRaid` round; they must not be abandoned mid-flight with the event.

  **That wait draws on the same remaining budget as every other step in the round** and settles as `timedOut` when it runs out.

  Waiting unbudgeted is not acceptable: disposal internally performs `confirmBlocklistPersisted` (an fsync-backed domain flush) and removal delivery through `blockedMemberRemoverHolder.current` (write-ahead outbox flush plus a mailbox barrier), so the abnormal-exit path that zeroes every budget (`EMERGENCY_FLUSH_TIMEOUTS`) — which should settle instantly — would instead drag on to the 15-second force-exit line, killing the process mid-shutdown with a non-zero code, the instance lock unreleased and the offset unacknowledged.

  **Conversely, Worker-side verdict batches must never be registered in the Anti-Raid in-flight task set**: that set is what the shutdown drain waits on, with a budget in the `ANTI_RAID_DRAIN_TIMEOUT_MS` range of seconds, while all three providers apply their timeout **per SDK attempt**: one verdict request can run to `AD_DETECT_OPENAI_REQUEST_TIMEOUT_MS` / `AD_DETECT_GOOGLE_REQUEST_TIMEOUT_MS` / `AD_DETECT_ANTHROPIC_REQUEST_TIMEOUT_MS` (60s each) times their SDK attempt count (`AD_DETECT_OPENAI_REQUEST_MAX_RETRIES` + 1 / `AD_DETECT_GOOGLE_REQUEST_ATTEMPTS` / `AD_DETECT_ANTHROPIC_REQUEST_MAX_RETRIES` + 1, three each), times the `AD_DETECT_EMPTY_BODY_MAX_ATTEMPTS` empty-body retry — minutes, not seconds.

  Registering them means that any shutdown coinciding with an in-flight verdict times the drain out, so the lifecycle refuses to confirm the Telegram offset and exits non-zero — a best-effort heuristic buying a dirty exit plus a redelivered update. When the drain arrives the pipeline only quiesces its ticker (no new requests, no further deletions or announcements) and lets the in-flight verdict finish on its own.

  **Losing management of a chat, `/init disable`, and `/ad_detect disable` must all clear that chat's pending bundles**: the main-thread gate stops only future messages, and anything already queued in the Worker would keep producing blocklist entries after the switch was turned off. A verdict already in flight invalidates itself through object identity (its bundle is gone, so the captured reference no longer matches).

  **Before tightening any structural rule in the prompt, check it against the positive samples in `config/dynamic/ad_samples.json` one by one**: the rules decide *what makes something an ad* and the samples decide *which categories this deployment recognises*, but both describe the same calibration.

  When a rule says "usually not" while the sample list says "judge anything of this kind true", the model receives a pair of mutually contradicting instructions and the side that loses is always recall — an ad that gets waved through leaves no trace in any log, so nobody finds out.

  **Personal candidates include the sender's names and message body**: the Worker reads the per-message `firstName` and `lastName` from the flat fields of `AdCandidateMessage` (apart from `linkUrls` the candidate carries only primitive fields, staying on Bun's flat structured-clone fast path; the Worker rebuilds the bundle's metadata object only when a name changes), normalizes each to one line, and bounds each to `AD_DETECT_SENDER_NAME_MAX_CHARS` (128 UTF-16 code units) without splitting surrogate pairs or consuming the body budget. An unchanged name with only an already-claimed reference does not trigger another classification; renames remain eligible. Names are frozen per entry, count toward the bundle budget, and remain in hit samples; later renames do not rewrite accepted content. `directText` includes the sender's own names and non-forwarded body; a forwarder's names remain their own content. Promotional names follow direct-ad attribution, while ordinary names alone are not ads. Names and body only enter user data. Existing candidate filters, allowlist permissions, and administrator exemptions apply.

  **A link-only bundle is a hard negative that outranks every other heuristic signal**: after removing the per-line numbering added by `bundle.ts`, a bundle containing only one or more links, optionally accompanied by ordinary names, with no promotional, recruiting, or transactional copy in either names or body must be classified false. Proxy-node and subscription schemes such as `vless://`, `vmess://`, `trojan://`, and `ss://` are links too; URL length, query parameters, percent encoding, and fragment names cannot turn one into an ad on their own. This boundary protects only link-only bundles; genuine marketing copy next to a link is still judged against the positive samples and the remaining rules.

  The prompt **must contain the word "JSON"**: the OpenAI-compatible branch uses `response_format: json_object`, while the Google branch uses a structured response schema.

  **The prompt requires one unfenced JSON object, while the parser retains one compatibility shell for non-compliant endpoints**: when the complete response is not already a naked object, `parseAdVerdict` may extract a case-insensitive ```` ```json ... ``` ```` fence as the candidate JSON. A naked object takes precedence so fence text inside the `reason` string cannot truncate an otherwise valid response. Fence recovery strips presentation only; it adds no second classification semantics, and malformed JSON or a non-boolean `ad` still returns null.

  **The output budget must leave room for a reasoning model**: the model comes from `agent.ad_detect.model` in `config/dynamic/agent.json`; code keeps no default. OpenAI-compatible reasoning tokens share `max_tokens`, and a `length` result must not pass partial JSON to the classifier.

  The transport layer must therefore detect the `length` finish separately, name it in the log, and return null instead of handing back a partial body; otherwise this class of miss leaves no trace at all. Group text reaching the model is always data; `reason` only feeds logs and the announcement, never control flow.

  **Every hit also records one side-channel sample** (`memory/ad-detected/sample.json`, see `workers/diskIO/adSampleFile.ts`; it first enters an in-memory Disk I/O batch that appends at `FLUSH_MAX_ENTRIES` (256) entries or `FLUSH_INTERVAL_MS` (30 seconds) after the first one, and the unified shutdown flush writes it out as usual): the rules live in the prompt, but which topics this deployment recognises comes entirely from the examples in `config/dynamic/ad_samples.json`, and those can only be collected from real hits — without the raw material, a false positive can only be reported from memory.

  This is the one class in the whole persistence layer whose **sample contents are never read**: startup recovery does not hydrate it, and it is not in the failed-domain list of flush receipts (a purely diagnostic file failing to write must not make a persistence confirmation report failure). Post-startup maintenance and the unified local-midnight cron inspect directory entries only, while the first write remains a fallback. Orphan temporary files are scanned at most once per Worker isolate, and archive retention at most once per configured local date. It allows truncation self-repair; a failed batch write drops the whole batch with just a `console.error`, and batches not yet flushed are lost with the isolate when the Disk I/O Worker is rebuilt.

  The current file rotates at 8 MiB to `sample.<configured local date>[.<positive sequence>].json`; archives are retained by the date in their names for the latest 15 configured local calendar days, including today. The retention sweep runs at most once per day, deletes only strictly matching regular files, and neither a directory-scan nor an individual deletion failure may block side-channel appends.

  It is posted *before* `blockUser`, because every step after that can throw and this sample is the only evidence of whether the verdict was right. The sample records the **whole bundle**, not just the triggering message: the bundle is what was judged, and a single line out of context cannot reproduce what the model actually read.

  **Quoted segments and replied-to originals go into both the verdict and the sample**, but they travel separately from the body from the submission entry onward (`sampleQuote` and `sampleReplyTo` besides `text`; the Worker bounds them in `boundSampleContext` and assembles an `AdSampleContext`), for two independent reasons: the verdict side must append them **after** the body is truncated to `AD_DETECT_MESSAGE_MAX_CHARS` (concatenating before truncating is a zero-cost bypass — a few hundred filler characters push the quote out of budget), and the sample side must keep a copy that was not folded into the body (a human reviewing a false positive has to tell which part the sender wrote from which part was quoted).

  They are appended **without any system wording** (no "quoted:"-style prefix), same reason as the URLs: it would introduce forgeable structure into the body, letting a sender pass their own words off as someone else's.

  **Facts the model cannot see must be supplied to the model by the main thread, and both sides must be stated explicitly**: a verdict only sees the sender's own message bundle, so a structural signal such as "joined moments ago and has not passed verification yet" simply does not exist in that transcript. Writing it into the prompt without feeding the data only makes the model invent a rationale.

  The main thread reads it synchronously from the pending-verification mirror (`activeVerificationSnapshots`) and ships it with the candidate; the bundle takes the union rather than the latest value, since verification can pass inside the window and someone who advertised first must not be laundered by verifying afterwards. Stating only the positive side is equally wrong: the model would read "not mentioned this time" as missing information and guess, whereas this signal may only add weight when confirmed.

  The fact line is **kept apart from the text under judgement** and placed at a fixed position by each transport: the OpenAI-compatible path appends it to the end of the system section (rules and samples first, so the shared prefix hits the server-side prefix cache); on the Gemini path `contents` is always one user turn with two parts—the fact line first, then the message bundle—and the system instruction carries only "classification rules + deployment samples". The fact **must never be mixed into the text under judgement** — that text is entirely user-controlled, so mixing it in would hand a flooder the ability to forge "I am not a new member"; rule E of the prompt also states that any "【系统事实】" appearing in the data under judgement (the numbered lines) is quoted chat content, not a system fact.

  **Explicit cache on the Gemini path** (scope in `workers/antiRaid/adDetect/ai/google.ts`; registry and content fingerprints in `cache/workers/antiRaid/geminiContextCache.ts`, owned by the Anti-Raid Worker): the cache holds only the single system instruction "classification rules + deployment samples"; the fact line and the message bundle stay out of it, so both fact variants share one slot. The `displayName` prefix is `copy-ninjia:ad_detect:`, and this scope and the replies' text scope never adopt each other's entries. At most `AD_DETECT_GEMINI_CACHE_MAX_SLOTS` slots exist: after a sample hot reload the old and new contents each take a slot, and overflow evicts the least recently used. TTL, renewal, back-off, and 400-rejection rules are shared with the reply cache through `infra/geminiContextCache.ts` (see [AI Prompts and Transcript](#ai-prompts-and-transcript)). With a cache the request carries `cachedContent` and no `systemInstruction`; without one (not created yet, rejected, or a resend) it carries `systemInstruction`; `contents` is byte-identical either way. When the endpoint rejects a request referencing the cache with a 4xx other than 408/429, the registration is released (with the same back-off as the reply cache) and the request is resent once in full on the spot; endpoint failures are not resent. The two fingerprints of the rules-and-samples section are cached with it, so the verdict path only compares references to the model and the system instruction and recomputes them on a mismatch (a replaced sample snapshot or a new model); a change to `agent.ad_detect` also discards the registry so the next verdict rescans with the new client. Background requests use the Anti-Raid best-effort dispatch signal and are cancelled with it on shutdown. Creation input tokens are recorded in `usage.json` as `ad_detect` usage with 0 cached; when the content is below the model's explicit-cache minimum, the same content stops being created after 3 accumulated 400 rejections and classification then continues without the cache.

#### Bans and message revocation

- Blocklist bans always pass `revoke_messages: true`. `/block`, the instant kick when a blocklisted member joins, the sweep after the bot becomes an administrator, and an ad-detection hit all share the single `banChatMember` wrapper, and all four express the same judgement: this person should leave no trace in this chat, so deleting their messages is part of a complete disposal.

  Anti-raid's automatic expulsion uses `kickChatMember` (kick without ban, to limit false positives) and never goes through this path, so the rule does not touch it. Channel identities have no "member" concept and `banChatSenderChat` has no such parameter, which is why ad detection separately deletes the bundle it judged on inside the Worker — that deletion also covers channel costumes and accounts that already left on their own.

#### Blocklist-removal outbox

- Pending blocklist-removal batches must survive process restart. Before posting a removal to Anti-Raid, the main thread sends the current `pendingBlockedRemovals` snapshot to Disk I/O and waits in the distinct `blocklistRemovalOutbox` domain for the SQLite `pending_blocked_removals` snapshot revision ACK. Only the matching durable transaction may hand off the update. The Worker compares old and new snapshots into primary-key upserts/deletes and encodes only changed rows instead of rewriting a whole file on every settlement.

  **Sweep entries (`probeMembership: true`) must not persist `userIds`**: the outbox stores only the task "scan this chat against the current blocklist". Dispatch and replay read stable primary-key cursor pages in ascending order through the Disk I/O boundary, with at most 512 ids per page. The next page is not read until the previous one receives a complete receipt, and only the final page may settle the durable task. Before every page read, the main thread confirms that blocklist writes have flushed and been acknowledged (receipt-driven writes must stay outside that window; see [deleted-account detection](#deleted-account-detection-in-the-blocklist)); the Disk I/O Worker then overlays the committed SQLite page with at most 128 concurrent pending final values. Pages must never be joined back into a complete `Set` or array. A read or delivery failure on any page preserves the outbox task, releases the current claim, advances backoff, and replays safely from an empty cursor next time. Freezing the list into each chat task would multiply storage and structured-clone work by chats × blocklist length and would already be stale at replay. Conversely, `probeMembership: false` tasks must freeze the specific non-empty `userIds` known at creation time. A discriminated union and strict codec enforce both shapes.

  Main-thread state, the thread message, and the Disk I/O snapshot each keep only the copy their owner needs. The receiver encodes a row once and caches canonical text; change comparison must not stringify and parse every old row again. Diagnostic-only changes do not deep-copy the entire table independently and ride with the next authoritative snapshot, except the alert-threshold crossing, which is durable immediately. Crossing the threshold escalates diagnostics but never deletes a security task.

  Cancellation or trimming can race with write-ahead flush, so the main thread reconciles again before posting and re-flushes every changed revision until durable content equals the messages about to be sent; no `await` may remain between final reconciliation and synchronous posting. Startup restores from SQLite before the runner, filters against authoritative blocklist and `isInitEnabled && botPermissions.isAdministrator`, seeds the counter from the maximum `removalId`, and batch-replays. Strict decode failure, exceeding `BLOCKLIST_REMOVAL_OUTBOX_MAX_ENTRIES`, or transaction failure is fail-closed; the process never continues from an empty outbox.

  Disk I/O independently enforces the 4,096-entry limit while accumulating startup inspect pages and when receiving a new runtime snapshot revision. An oversized snapshot is rejected before allocating its pending table, committing, or acknowledging it. The first transition of a sweep batch's `lastFailure` to `missing-permission` queues the next durable snapshot immediately so the permission latch survives restart; a named batch lacking permission is deleted when rejected, which likewise queues the next snapshot. Both inter-user waits and request-retry waits in blocklist removal subscribe to the Worker shutdown signal; cancellation returns `complete: false` and retains the outbox for replay.

#### Replay after permission restoration

- Once `can_restrict_members` is authoritatively restored, replay, under its original `removalId`, every instant-kick/ad batch for that chat still in the outbox (those in flight during the latch and not yet acknowledged; named batches rejected for missing permission were already settled at rejection) before issuing a current full-list sweep, which clears the members of those settled batches and of failed direct `/block` bans. The sweep receipt may settle only its own ID; it must not erase outbox entries on behalf of the replayed batches. Each replayed batch remains until its own `complete` receipt arrives, and a failed sweep cannot settle it early.

#### Deleted-account detection in the blocklist

- Telegram answers both `getChatMember` and `banChatMember` for a deleted account with 400 `PARTICIPANT_ID_INVALID` (`isParticipantIdInvalid` in `packages/infra/telegram/actions/core.ts`), so a sweep over such an id never settles. While sweeping (`probeMembership: true`), the Worker records a user's outcome as `participantInvalid` only when every probe and every ban in all `BLOCKLIST_REMOVAL_MAX_ATTEMPTS` attempts returned that error and no shutdown cancellation cut the attempts short; everything else stays `failed`. `participantInvalid` is still unsettled: retry count and delays, `complete: false`, the `side-effect-incomplete` diagnostic, and sweep backoff are unchanged, and API errors are logged as before. Instant-kick and ad batches do not read membership and never produce this outcome; channel identities are excluded.

  Every `blockedMembersRemoved` receipt carries two user-id lists: `participantInvalidUserIds`, and `settledUserIds` for ids settled in the batch (banned, confirmed absent, or confirmed administrator). After `settleBlockedRemoval`, the main thread's `packages/infra/blocklist/participantInvalid.ts` appends the receipt to `blocklistParticipantInvalidQueue` and settles receipts serially in arrival order: each receipt adds 1 to `blocklist_entries.data.participantInvalidCount` for the former, and rewrites any entry in the latter that still carries the field without it. The unit is one sweep disposal in one chat, so with at least `BLOCKLIST_PARTICIPANT_INVALID_LIMIT` (5) managed chats a single sweep round can reach the limit. Ids that are not on the list are not counted.

  Reaching the limit never writes an out-of-range value. Instead, the removal joins the per-identity queue shared with ad-detection bans and `/block disable` through `runBlocklistIdentityMutation`. When it runs, it prefetches again and calls `unblockUser` only if the cached entry is still the same object seen at enqueue time. Following the `/block disable` order above, that publishes the negative cache, posts the trimmed pending-removal snapshot first (dropping sweep tasks too if the list becomes empty), then posts the deletion tombstone, and logs `Removed blocklisted user ...`. The removal is abandoned if the entry was cleared, rewritten, evicted and reread, or deleted by `/block disable` meanwhile; the next such receipt triggers it again. This path does not lift bans across chats. Shutdown does not wait for this chain, and count changes after the final flush are discarded with the process.

  `settledUserIds` can hold a full page (512 ids). When selecting entries that still carry a count, cached identities are only `peek`ed, which leaves LRU eviction order unchanged; cold ids go through `retainParticipantInvalidBlocklistIds`, which reads the database, overlays local unacknowledged final values, and **does not populate the identity LRU**, matching `retainCurrentlyBlockedIdentityIds`. Only the few identities that must be rewritten are passed to `prefetchIdentityPolicies`; a full sweep page must not displace the hot cache prefetched per update. A receipt's writes are all-or-nothing: if an identity is evicted from the LRU while waiting for the window below, the whole receipt is prefetched again, up to `BLOCKLIST_PARTICIPANT_INVALID_WRITE_ATTEMPTS` rounds, after which the receipt is skipped with an error log.

  Receipt-driven count writes are posted synchronously as soon as prefetching finishes, without waiting for sweep page reads: `readBlocklistSweepPage` records the identity revision before it sends the flush, and the check counts only unacknowledged blocklist writes at or below that revision. A continuation page read follows its receipt immediately; a count write that lands during its flush is not part of the batch that flush covers and does not fail the check. Page reads started afterwards cover those writes with their own flush.

### Fortune and AI-Memory Recovery

- Before switching the local-day owner for fortune persistence, the previous day's append buffer must flush successfully; failure retains the old owner and refuses rollover — **but the new-day draw that triggered the rollover must move into a deferral buffer and be replayed later, never dropped along with the failed rollover**: the main-thread `dailyLuckCache` has already recorded it as "drawn today" and issued a receipt, so dropping it means the day file permanently lacks that entry once the disk recovers while the user cannot draw again that day, and `onDiskIORespawn`'s full replay only covers Worker respawn, not "Worker alive but unable to write". The deferral buffer has an explicit bound; on overflow the oldest entry is dropped with a log line (never silently). A successful flush retry replays the deferred draws immediately instead of waiting for the next draw to drive it. When the target day already contains confirmed results, a missing key or a key for another day is an inconsistent backup and must block startup or rollover rather than silently generating a new key.

  **A startup mismatch between "today as the main thread computes it" and the credential's day is not that case and must never block startup.** The Disk I/O Worker computes the configured local day once at the startup boundary and the main thread computes it again in `restoreLuckState`, so a process starting right around 00:00 can naturally see the two differ by a day. Throwing here lets the exception escape `ApplicationLifecycle.init()` (the call site has no try/catch), so `run()` logs one line and exits with code 1 — one day rollover keeps the bot from starting until the process manager restarts it. The correct handling is to discard the stale credential together with that day's confirmed records: do not adopt it, leave the cache empty, and let `ensureLuckCacheFreshForToday` fetch today's key from the Worker on first use (every entry point already awaits it). Mark "the day rolled over inside this process" at the same time so that late confirmations without same-day proof all fail closed.
- AI-memory recovery accepts only version=1 snapshots within the current `AI_MEMORY_HYDRATE_BUFFER_MAX` and `MAX_SUMMARY_ROUNDS` limits—currently 255 verbatim messages and 7 cold-summary rounds. An oversized or malformed snapshot fails startup rather than being truncated. Raising a limit is compatible with existing snapshots; before lowering one, stop the old process and rewrite existing `chat_states.ai_context` snapshots in a SQLite transaction with the same strict codec so the old process's shutdown flush cannot overwrite the migration.

  Current messages and references require single-line names, usernames, forwarded sources, body text, and quotes; ordinary spaces are the only permitted whitespace. Body text is non-empty, and reference text/quote is limited to 500 UTF-16 code units. Preserve trailing spaces or a lone surrogate produced by truncation. `at` must be a valid local calendar time in `YYYY/MM/DD HH:mm:ss` form. `pendingImage` is optional (absent means the content state and the key is not written); when present it must contain exactly `origin` (`command` / `generated` / `referenceGenerated`) and a single-line `caption`. Summaries and pendingSummary may contain newlines. Disk I/O recovery and AI Worker hydration share the strict decoder: reject invalid fields with their specific paths, without sanitizing, dropping entries, or rewriting data.

- Startup hydration is bounded by `AI_MEMORY_MAX_CHATS`; any overflow is left on disk and reported once rather than deleted as a capacity side effect. `AI_MEMORY_MAX_CHATS` is `2 × STATE_MANAGED_CHAT_LIMIT` (50): the authoritative `chat_states` table holds at most 25 managed chats and up to 25 unfinished AI memory teardowns may briefly coexist with them, so capacity eviction never lands on a managed chat that is still in use.
- **When the AI Worker exhausts its restart budget and gives up, the replayable identity-injection record (`lastInitState.current`) must be cleared with it.** `flushAiMemory` uses exactly that record to decide "this line never came up, there is nothing to flush" and return `flushed` immediately. Leaving it set makes the shutdown flush bypass the short circuit, enter the barrier, and settle as `failed` when `post` fails, so `flushAllToDisk` returns false, `wait()` refuses to confirm the final offset, and Telegram redelivers every update after the last acknowledgement — re-running non-idempotent side effects such as echoes and command receipts. The agreed degradation for this feature is only "AI chat goes silently offline until the next restart"; it must not drag the whole shutdown's offset gate down with it.
- The message index, `chatMessageIndexes`, is derived entirely from rolling memory, is not persisted, and shares inner object references with the cache. Registration and deletion may occur only at the physical points where messages enter or leave the hot region—push, rotation, and hydrate in `rollingMemory.ts`; every other module is read-only. The index therefore covers only messages still in the hot region, is bounded by the rolling-cache limit, and has no independent eviction.

  The bot records reply edges for its own sent text and images only from the actual `reply_to_message` returned by Telegram. If a target leaves the hot region while a round is generating or queued, the bounded trigger snapshot captured before the round begins is used as fallback without expanding index coverage.

  Bodies in single-hop reply and trigger snapshots are bounded by `REPLY_REFERENCE_MAX_CHARS`, currently 500 characters. Exact quotes and forward origins remain in their existing message fields.

### Acknowledgement Boundary and Shutdown

- A Telegram update may advance the acknowledgement boundary only after its middleware completes; reaction synchronization awaits its Telegram action inside that middleware. Anti-Raid mailboxes, the avatar background owner, and StateStore, AI Worker, and Disk I/O Worker flushes all have explicit bounded drains. Any critical flush failure must report failure, block final-offset acknowledgement, and exit nonzero.

  **The update abandoned at shutdown counts too**: once the stop signal arrives the fetch loop no longer waits for the in-flight middleware (it may hang; draining is left to the lifecycle's bounded `size()` loop), so a later failure can only be expressed by an explicit runner flag — written in the same synchronous section where `handleUpdate` throws, so it is already in effect when `size()` reaches zero.

  The lifecycle must read it before confirming the final offset, withhold the offset and exit nonzero when it is set, and let Telegram redeliver after restart; judging solely by whether `task()` resolved normally acknowledges an update that was never processed successfully.
- Every runner `getUpdates` call uses `limit: 1`, and the next fetch with a higher offset starts only after the current middleware succeeds. If a later update fails, the previous non-idempotent side effect has therefore settled behind its own acknowledgement boundary and cannot be redelivered as a sibling (background work moved outside the acknowledgement boundary — deferred command executor tasks, the `/block enable` cross-chat fan-out, and the translation background chain — is excluded; see the corresponding entries for its shutdown and crash semantics). A source that violates the limit and returns multiple updates must fail closed before any handler runs. No later update may be fetched and no offset may advance after failure.
- `app/updateFetcher.ts` calls the public `api.getUpdates` with a 30-second long poll, a 15-hour retry window per fetch, exponential backoff starting at 100 ms and capped at 30 seconds (`UPDATE_POLL_MAX_RETRY_MS`), and the 429 `retry_after` wait, so fetching resumes at most one capped backoff after the network recovers; 401/409 fail immediately. Requests and every backoff share the same cancellation signal. The runner retains only the current middleware's stop waiter and detaches it on settlement. `stop()` ends fetching; `size()` and `abortActive()` define the in-flight drain boundary. Exponential backoff and 429 waits share the fetch's monotonic-clock budget. A `retry_after` greater than or equal to the remaining budget immediately throws the latest error without creating a wait.
- Linked-channel lookup uses a 15-second cancellation signal. The Telegram duplex proxy cancels the in-flight request and settles its waiter. Failure or timeout still returns `undefined`, writes no cache entry, and grants no exemption; same-chat deduplication, cache TTL, and generation isolation retain their own boundaries.
- The final-offset `getUpdates(timeout: 0)` is still a network request, and the server may hold it: it uses the same offset as the in-flight long poll, and when the same offset is requested again within 3 seconds of the previous `getUpdates` start, the Bot API server raises `timeout` to 3 seconds (`TELEGRAM_REPEATED_OFFSET_MIN_WAIT_MS`). The local deadline `FINAL_OFFSET_CONFIRM_TIMEOUT_MS` is that wait plus 5 seconds (8 seconds total) and is enforced through an `AbortSignal` that also bounds DNS, connection setup, and response reads.

  A rejection, timeout, or skip caused by an unsettled runner, maintenance owner, or persistence prerequisite permanently fails this lifecycle gate and forces a nonzero exit.

  **`runner.task()` throwing counts as a skip and must be recorded as a failure explicitly.** That exception skips the entire pre-confirmation gate while the gate flag is still at its initial `true`, so the `offsetConfirmed` that `dispose()` assembles is true and the round is judged a clean shutdown — the diagnostic line is not emitted, and operators grepping the logs see "everything normal" while that round neither confirmed anything nor kept an update, leaving the post-restart redelivery untraceable.

  **The shutdown outcome has three states, not two** (`classifyShutdown` in `packages/app/lifecycle/shutdown.ts`): `clean`, `offsetWithheld`, and `unsettled`. The middle state means "every owner drained and flushed and the Workers terminated; only the final-offset gate did not complete". Its handling must differ from `unsettled`:
  - Both exit nonzero and print the `Shutdown drain/flush results: …` diagnostic line — an unconfirmed offset means Telegram will redeliver after restart, and operators must see that;
  - but **only `unsettled` retains the instance lock**. The sole reason to retain it is "something may still be writing to the shared data directory", and under `offsetWithheld` the runner has drained, every owner has flushed, and the Workers have terminated, so that risk does not exist. Collapsing the two states leaves a stale `bot.lock` record after a shutdown whose data was fully persisted, while the line "a task did not drain or persistence did not flush" points operators at a Worker and a disk that are perfectly fine. Log one extra line before releasing to state that the release does not imply the offset was confirmed.

  The decision uses `dispose()`'s own `ShutdownResults`, not what `wait()` observed: a flush that failed in `wait()` and then succeeded in `dispose()`'s own pass is exactly the combination where the offset must be withheld while the lock may be released.

  A later `dispose()` may not overwrite that fact merely because the same owner settles on its second wait. With no processed update, no API call is required and the gate is successful.
- An Anti-Raid mailbox barrier proves only that earlier messages reached the dispatcher; it does not wait for Telegram network side effects started by that dispatcher, and update hot paths keep using this lightweight boundary. Lifecycle drain sends a separate `drain` message and waits for the Worker's registered in-flight task set to empty, with mailbox barriers and persistence flushes around it for a bounded fixed-point reconciliation. A normal barrier acknowledgement must never be interpreted as network completion.

  A chat's blocklist-removal epoch exists only while that chat still has an in-flight removal task and must be removed when the last task settles or the Worker stops, so historical disabled chats cannot accumulate forever.
- Before Anti-Raid shutdown drain takes its first snapshot of `inFlightAdDisposals`, it must send `drain` to the Worker and receive its acknowledgement. The Worker synchronously quiesces the ad-verdict ticker when handling that message. FIFO on the same Worker port guarantees that any earlier `adDetected` publication has already been registered on the main thread, while an in-flight verdict returning after the acknowledgement is barred from publishing by the stopping gate.

  Only after this stable boundary may shutdown await main-thread ad disposals, persistence flushes, receipt barriers, and their derived Worker tasks, continuing the fixed-point reconciliation as needed. `drainAntiRaid() === "flushed"` must imply that `inFlightAdDisposals` is empty; a disposal registered around the final Worker drain may not escape the round.

  **Failing to obtain that leading acknowledgement is not grounds for returning immediately**: when the Worker has given up or is respawning, `post()` fails synchronously and the barrier settles as `failed` — yet a main-thread disposal may well be sitting on `confirmBlocklistPersisted`, which is exactly the window where the block is queued but not yet on disk. Returning there drops it along with the pending blocklist write, and the sender is not on the list after a restart.

  The failure path must therefore still drain `inFlightAdDisposals` with the remaining budget (with no acknowledgement there is no stable boundary, so that pass covers only what is in flight right then — best effort) and then hand the original failure reason back to the caller; the return value is never rewritten by this salvage attempt.
- Each active Telegram update owns a cancellation signal. After the normal drain deadline, shutdown aborts all active handlers and gives them a bounded settlement window; Telegram calls and authoritative state writes must observe that signal. A handler that still does not settle blocks final-offset acknowledgement and forces a nonzero exit after best-effort disposal.
- Both normal and abnormal shutdown first quiesce title, avatar, translation, new-gag, wed, deferred-commands, cron, blocklist-resweep, and config-reload entry points and stop the runner, then perform bounded drains. Failures from the nine quiesce calls must be caught independently: a throw from one must not skip the others, and that attempt's failure must block final-offset acknowledgement and instance-lock release. A later `wait()` or `dispose()` may retry all nine idempotent entry points. A resweep timer can start Anti-Raid network work and outbox writes, so it must be stopped before the Anti-Raid pre-drain rather than only in terminal `dispose()`. **Quiescence must never be cached as done** — `init()` re-arms those same nine owners, so a stop signal during startup that latched success would short-circuit every later quiesce, leaving owners accepting work throughout shutdown while the result still reports clean.

  The translation client is constructed lazily only on the first real request, every RPC has a short project-wide timeout, and drain is followed by explicit `close()` and clearing of the project parent/client reference. A translation drain timeout or close failure blocks instance-lock release just like any other critical owner failure. Before acknowledging the final Telegram offset, the normal path must first drain Anti-Raid, gag notices, `/qa set` forms, wed interactions, and unified delayed deletions, then flush AI, drain Telegram outbound work, and flush Disk I/O plus StateStore.

  Final disposal is: flush AI → terminate AI → drain Telegram outbound → flush Disk I/O → terminate Anti-Raid and Disk I/O → flush StateStore. If a fatal error occurs while normal disposal is already in progress, the emergency path may reuse that Promise but must impose the current independent 15-second absolute forced-exit deadline so an existing drain cannot hold the process indefinitely. When the budget expires, abort in-progress Telegram requests, media downloads, and 429 sleeps, then settle work that has not started.

  After abort, no message, avatar change, or group-title write may occur. The abnormal-exit path uses a maintenance budget of 0, so every drain must accept a zero budget as valid input: settle as `flushed` when idle, and abort immediately and settle as `timedOut` when work is still in flight—never throw a validation error. An unfinished title refresh must likewise be aborted when it is skipped.

  Every owner in disposal must also be failure-isolated: an exception is folded into `failed` and counted in the summary, and no single throw may skip the owners that follow it, `flushStateToDisk`, or instance-lock disposal.
- In-process elapsed-time budgets for lifecycle, Anti-Raid draining, and the `getUpdates` retry window (`app/updateFetcher.ts`) are computed through `packages/libs/monotonicDeadline.ts` using `performance.now()`. Wall-clock rollback must not extend drain, cancellation-settlement, retry, or shutdown deadlines; business state, protocol deadlines, and persisted absolute timestamps continue to use `Date.now()` according to their semantics.
- Worker flushes and mailbox barriers all use `packages/libs/flushBarrier.ts` to manage IDs, waiter tables, timeouts, late acknowledgements, and crash-wide settlement. Domain caches must not expose resolver Maps again.
- A domain flush may reinterpret only another domain's failure from the same acknowledged flush request; stale global failure state and transport failures must never be converted to success. Instance-lock release is also a durability boundary: owner-verification or unlink failure propagates, keeps the lock acquired in lifecycle state, and forces a nonzero exit.

### File Permissions and Schema

- The project workspace itself may retain the permissions needed by collaborating editors and automation, but an explicitly configured data root is a sensitive-data boundary. Startup requires the root, `memory/`, and `logs/` to be no broader than `0755`, forbidding group and other write bits. The sole exception is SQLite `database/`: deployment tooling may create a setgid collaboration directory at `02770`, while the main database and WAL/SHM use `0660` on first creation. Startup accepts a directory owned by the runtime UID or by an effective runtime group with complete group `rwx`, while still rejecting all `other` access. Deployment tooling owns owner/group setup and manual migration of existing directories; the runtime must not chmod them silently.
- New artifacts under `memory/` default to `0644`; stricter existing modes such as `0600` and `0640` survive adoption, append, compaction, and atomic replacement. Startup validates that the runtime account can read and write them and fails closed instead of repairing their permissions. Sensitivity is controlled jointly by file and directory permissions, deployment isolation, and backup policy.
- **An atomic replace must not reset the target file's permission bits.** The temporary file in `tmp + fsync + rename` is freshly created, so its `0666 & ~umask` has nothing to do with the target's existing mode. Both asynchronous and synchronous atomic writes read and reuse the existing target mode. A caller-supplied `mode` is only the first-creation default when the target does not exist, so ordinary writes, compaction, and key rotation cannot silently widen operator-tightened `memory/global/state.json`, `bot.lock`, and other `memory/` files.
- Persistence schemas do not perform speculative automatic migration. Incompatible input blocks startup so empty state cannot overwrite real data.

## Compatibility Entry Points

Top-level barrels retained after splitting large files exist only for gradual migration. New production code should import from the relevant domain file. Compatibility entry points must not own state, parse configuration, or introduce import-time side effects.

Luck receipts carry no legacy-format branch. Verification requires the day embedded in the receipt to equal the current configured local date, and the daily key rotates every midnight, so a receipt from any other day can never verify—legacy-format receipts became unverifiable the day after the display-label format shipped. Recognition, stripping, and verification all accept only the current format: the label prefix, a fixed-length HMAC digest, and the original receipt carried by a `text_link` entity over the same range.

**A decode failure on the verification path must be normalised into "malformed".** The whole receipt comes from a group message entity, its length and alphabet bounded only by the protocol regex, and `Uint8Array.fromBase64` throws `SyntaxError` for any input whose length is ≡ 1 (mod 4). The confirmation middleware runs ahead of every gate and is reachable by any user in any chat, so an escaping exception is rethrown by `bot.catch`, the acknowledged runner exits with the offset unconfirmed, and Telegram redelivers the same message — exactly the redelivery restart loop forbidden above, entered through protocol parsing. All three decodes on the verification path therefore go through one normalising helper and return `undefined`; only the deployment key keeps fatal-error semantics, because that is configuration rather than user input.
