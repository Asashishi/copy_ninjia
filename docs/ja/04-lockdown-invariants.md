# 04 · ロックダウンミラーと終端フラグ

[简体中文](../cn/04-lockdown-invariants.md) · [English](../en/04-lockdown-invariants.md) · [日本語](../ja/04-lockdown-invariants.md)

[← 04 実行時の正式な不変条件](04-invariants.md)

- **ロックダウン指紋と意図（Intent）の同一性**：
  - ロックダウンの永続化ハンドシェイクで使用する指紋（`lockdownFingerprint`）は、`phase`、`intentId`、`announced` の 3 フィールドで構成されます。
  - `phase` と `intentId` は、特定のロックダウン意図の安定した同一性を識別します。
  - `announced` はクラッシュ復旧後に解除アナウンスを送信可能かを決定するため、永続化の ACK は必ずこのフラグをカバーしなければなりません。
  - 遅延して届いた結果が現在の意図に属するかを緊急権限復旧が判定する際は、`phase` と `intentId` のみを照合します（アナウンスフラグの永続化によって新しい権限意図が生成されることはありません）。
  - いずれの指紋にも `expiresAt` を含めてはなりません。

- **カウントダウンと照合ループ**：
  - カウントダウンタイマーはミラーの `expiresAt` に保持され、状態の引き継ぎ（adopt）時にそこから `remainingMs` が算出されます。
  - 永続化の照合ループは最大 `LOCKDOWN_PERSIST_RECONCILE_MAX_ROUNDS` 周回までに制限されます。
  - 永続化の実行中に新たなイベントが到着した場合は再実行待ちフラグがセットされます。
  - 周回上限に達した場合、実行中のタスクはエラーログを出力してマイクロタスクを一度譲渡し、その後に最新ミラーから自動的に新規タスクを開始します（外部からの新規イベントを待つことなく自律復旧します）。

- **メインスレッドによる緊急引き継ぎ**：
  - Anti-Raid Worker が自己修復を断念した場合、メインスレッドの `recoverAbandonedLockdowns` はスナップショットのクローンを行わず、チャット状態のインメモリキャッシュ（`cache/main/chatState.ts` の `chatStateCache`）を直接走査します（特定の走査順序には依存しません）。
  - 復旧パイプラインは最初の `await` より前に各グループのエントリを同期的に読み取ります。ロックダウン中のグループは 1 回のみ処理され、引き継ぎジャーナルにも 1 回のみ記録されます。
  - 同一グループの復旧タスクがすでに登録済みであり、かつ `phase` と `intentId` が一致している場合、`startEmergencyLockdownRecovery` は何もしきい値を変更せず即座に復帰します。異なる意図が検知された場合は、古い復旧処理を安全に破棄した上で新規に開始します。

- **ミラー検証と省略可能フィールド**：
  - 有効なロックダウンミラーには `phase` と正の整数 `intentId` が必須です。`announcementMessageId` は `announced` が true のときに限り、かつ必ず存在します。
  - 参加認証のスナップショットには `phase` と `trackedMessageTimes` が必須です。
  - `reminderMessageId` と `announcementMessageId` は任意（optional）です。これらが欠落している場合は、リマインダーがまだ正常送信されていないか、入室アナウンスが検知されなかったことのみを意味し、復旧時はそれぞれの再送・クリーンアップパスが適用されます。
  - 返信リマインダーの 3 フィールドは相互に検証します。`pending` フェーズでは `replyReminderRequested`、`reminderSuperseded`、「`welcomeAnchorMessageId` が既知」がすべて真かすべて偽で、それ以外のフェーズは `false`、アンカーなし、`true` でなければなりません。`expelling` の 4 つの通知・確認フラグは省略か `true` のみを受け付けます。
  - それ以外の未定義フィールドや形式不一致は厳格なデコードで拒否されます。旧バージョンのデータはオフラインで手動マイグレーションする必要があり、本番の読み込みパスに後方互換用フォールバックロジックを残してはなりません。

- **終端通知の 3 つの独立した永続化フラグ**：
  - `successNoticeSent`：キックおよび処置の成功報告が配信済みであることを記録。
  - `failureNoticeSent`：キックの失敗または `can_restrict_members` 権限の不足を記録。
  - `unconfirmedNoticeSent`：メンバーの在籍またはチャット種別が確認不能であったことを記録。
  - 3 種類の通知はいずれも、メインスレッドが送信成功後に `COMMAND_MESSAGE_AUTO_DELETE_MS`（30秒）で自動削除します。
  - 各フラグは、Worker 再起動やプロセス再起動を挟んだ場合でも同一通知が重複送信されるのを防止します。フラグはステートマシンのイベント（`expelNoticeSent`、`removalConfirmed`）で書き込み、通知の `await` が終わった時点でまだ現在の終端状態であるエントリにのみ適用します。フラグの更新は新しい revision を発行し、終端のリトライループはその永続化完了を待機します。

- **キック確認と処置報告のアトミック性**：
  - **キック自体は成功したものの処置報告の送信に失敗した場合、その処理を完了扱いにしてはなりません。**
  - スナップショットに `removalConfirmed` を記録した上でバックオフを挟んでリトライします。次回のメンバー確認で「グループに不在」が返された際、このフラグを根拠として Bot 自身がキックを完了させたと判定し、処置報告の再送を継続します。
  - `removalConfirmed` は永続化が必須ですが、書き込みが発生するのは処置報告の送信に失敗した例外時のみです。通常の正常系ではキックと処置報告が同一ラウンド内で完結するため、余計なディスク I/O は発生しません。

- **BAN 権限不足時の短絡（ショートサーキット）**：
  - 「BAN 権限がないことが確定したため以降の API リクエストを遮断する」短絡最適化は、関連メッセージのクリーンアップが完全に完了していること（`cleanupSettled`）を前提とします。
  - `botCanRestrictIn` が false の場合、`failureNoticeSent` と `cleanupSettled` の両方が true のときにのみ早期リターン（短絡）します。このときも各サイクルで在室照会を 1 回送り、退出済みなら精算し、在室ならバックオフを続けます。
  - 私密モードの即時キック（`kickPending`）も BAN 権限がない場合はまず在室を照会します。退出済みなら精算してその記録を解放し、在室ならログを残してキック要求を送らずにバックオフします。
  - クリーンアップが未完了の間は、処置サイクル全体を通常通り実行します（キックは `canRestrict` により、処置報告は `failureNoticeSent` により、メッセージ削除は `can_delete_messages` 不足時にスキップされ、実行可能で再試行が必要な削除タスクのみが実際にリクエストを発行します）。
  - `executionStarted` と同様に、`cleanupSettled` は **Worker ローカルのインメモリ冪等ゲートであり、ディスクスナップショットには永続化しません**。
